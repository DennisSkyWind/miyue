## 第一章 数据治理的本质：不是治数据，是治责任

### 很多企业做数据治理都搞错了方向

常见做法：
- 买一套数据治理平台
- 建一个主数据管理系统
- 招聘一批数据治理工程师
- 制定一堆数据标准文档

结果：平台买了没人用，系统建了没人管，标准定了没人执行。

### 问题的根源

数据治理的本质是**治责任**，不是治数据。

```
数据治理 = 让每一笔数据都能找到责任人

找不到责任人的数据 = 没人管的数据 = 乱数据
能找到责任人的数据 = 有人管的数据 = 好数据
```

### 一个简单的测试

问：你们公司的"客户"数据，谁负责？

A. 没人负责（CRM算吗？销售算吗？）
B. 数据部门负责（他们管得了业务吗？）
C. 业务部门负责（哪个业务部门？）
D. 有明确的部门和岗位负责（恭喜你，做对了）

如果你选了A/B/C，说明你们的数据治理还没入门。

### 产品主数据确权：不是问谁"需要"，是问谁最"受不了"

产品主数据谁都用：质量要标准、生产要BOM、销售要定价、采购要规格、财务要成本。

那到底谁是主责？

错误答案：
- **IT部门** → 数据治理是业务决策，不是技术问题
- **研发单独主责** → 懂技术但不懂市场和质量

正确逻辑：**不是问谁"需要"这个数据，而是问谁最"受不了"这个数据出错。**

| 部门 | 用什么 | 数据出错谁最受伤 |
|------|--------|-----------------|
| 质量 | 产品标准、规格、有效期、GMP要求 | **质量部门** |
| 生产 | 物料清单BOM、工艺路线 | 生产部门 |
| 销售 | 产品名称、销售分类、定价区间 | 销售部门 |
| 采购 | 物料关联、供应商规格 | 采购部门 |
| 财务 | 成本核算、定价 | 财务部门 |

**答案：质量部门应该是产品主数据的DO（Data Owner）。**

理由：
1. 质量是产品最核心的属性——名称、规格、标准、有效期都是"质量语言"
2. 质量部门相对中立——不是最大受益者，也不是最大"制造者"
3. 质量有监管压力（GMP等）——有内驱力管好数据
4. 质量做不好，谁都跑不掉——倒逼有责任感

### 供应商主数据确权：分类比统一更重要

供应商比产品更难确权——因为供应商类型太多了。

只要是签合同、付款的都可以称为供应商：原材料采购、IT设备采购、服务类采购……每个类型引入的部门不同。

问：**谁在"制造"供应商？**

| 供应商类型 | 谁引入的 | 谁主导关系 |
|-----------|----------|-----------|
| 原材料/辅料采购 | 采购部 | 采购部 |
| IT设备/软件 | IT部 | IT部 |
| 行政服务 | 行政部 | 行政部 |
| 销售服务 | 销售部 | 销售部 |
| 财务专业服务（审计/税务） | 财务部 | 财务部 |

**没有哪个部门能单独做所有供应商的DO。** 这是供应商和产品最本质的区别。

**正确解法：分类确权**



![diag_013](file:///home/ubuntu/hf-demo/diagram-img/diag_013.png)



**为什么采购做一级供应商的DO？**

- 采购是唯一所有类型供应商都"经过"的部门
- 采购有成本视角——供应商出问题最终反映在采购成本上
- 采购有"付款控制权"——倒逼供应商配合

### 员工供应商：主数据分级的终极难题

有一类供应商很特殊——员工。

报销、差旅等支出走员工信息，员工既是"人"又是"供应商"。



![diag_014](file:///home/ubuntu/hf-demo/diagram-img/diag_014.png)



**最大风险：两个系统各自维护一套"员工供应商"信息——HR改了名字，财务系统里还是旧的。**

这恰恰说明了一个关键原则：

> **主数据分级不是为了分类，是为了分清"谁负责"——不分级的主数据治理，最终是一本糊涂账。**

如果把所有数据都当一级主数据来管：
- 量大管不过来 → 数据部门变成"审批部门" → 阻塞业务
- 责任分散 → 没人真正负责
- 投入产出不成正比 → 失去高层信任

**一级主数据解决"有人管"的问题，二级主数据解决"管到位"的问题。**



### 本章小结

> 数据治理的核心不是技术，是责任。
> 没有责任心的技术方案，都是在浪费钱。
> 没有责任心的数据标准，都是废纸。

## 第二章 主数据治理与数据治理：到底谁先谁后

### 一个流传很广的"正确做法"

很多企业做数据治理，路径出奇地一致：

```
第一步：先做主数据治理
        （通常是HR主数据，因为"所有业务都落实到人"）
第二步：主数据搞清楚了，再做其他数据的治理
第三步：最后建设数据平台，把各类数据归集治理
```

这个路径听起来非常合理，甚至有点优雅：

- 主数据是核心，先抓核心没错
- 主数据见效快，容易向领导汇报
- 主数据问题最扎眼：员工重名、客户重复、编码冲突
- 而且有大量"别人家就是这么干的"可以参照

**它几乎成了一种行业默认共识。**

但我要说一句可能得罪人的话：

> **这个顺序，在大多数企业里是错的。**

### 为什么它会被当成"正确答案"？

因为它同时满足了三种直觉：

| 直觉 | 听起来对吗 | 实际上 |
|------|-----------|--------|
| "主数据最重要，所以先做它" | 是 | 主数据重要，但它**重要不代表你能先认出它** |
| "主数据搞清楚了，其他自然清楚" | 是 | 其他数据的问题不在"清不清楚"，在"谁负责" |
| "别人都这么干" | 是 | 别人家的顺序是**结果**，不是**规律** |

这个路径背后藏着三个从没被检验的假设：

```
假设①：我可以照搬以往企业的经验，直接定出主数据清单
假设②：把主数据治好了，其他数据的治理就自然顺了
假设③：主数据治理和数据治理是两个可以先后开工的独立项目
```

**三个假设，全都在现实里被击穿。**

---

### 真实关系：主数据治理是数据治理的一个环节，不是并列的起点

先把关系摆正。这不是两件事谁先谁后的问题，是**包含关系**：



![diag_015](file:///home/ubuntu/hf-demo/diagram-img/diag_015.png)



**主数据治理是数据治理的必经之路，但它不是数据治理的起点。**

这个区别不是文字游戏，它直接决定了两件事：

```
决定一：主数据清单不是"规划出来的"，是"盘点出来的"
        → 先有全量数据视图，才有主数据判断

决定二：主数据治理的"范围"不能拍脑袋定
        → 范围由数据现状、指标需求、业务价值共同圈定
```

所以正确的表述应该是：

> **数据治理一定先于主数据治理启动和规划实施。**

不是因为主数据不重要，而是因为——

> **你不可能在没看过全量数据之前，宣布哪些数据是主数据。**

### 为什么"数据入湖"本身就是数据治理的开始

这是最关键的一环，也是最多人跳过的一环。

#### 入湖之前，你手上只有"半张地图"

很多企业的数据资产盘点，做法是这样的：

```
翻系统清单 → 按业务模块分分类 → 挑出"重要"的那些
                ↓
        认定为主数据
```

看起来很合理。问题在于，你挑出"重要的"这一步，用的是**经验**，不是**事实**。

经验是什么？是"上一家药企这么做，所以我们也这么做"。

而真实的主数据定义，只有两个来源：

```
① 跨系统一致性   —— 这个实体在几个系统里出现？口径冲突吗？
② 业务决策依赖度 —— 业务做决策时，会不会因为这条数据不一致而出错？
```

**这两条，都必须看到全量数据才能回答。**

在入湖之前，你甚至不知道：

```
• 你以为的客户主数据，在财务系统里叫"往来单位"
• 你以为的产品主数据，在三个系统里有四套编码
• 你以为已经消灭掉的重复，在某个历史系统里还躺着 3 万条
• 你以为该治的"非主数据"，其实是另一个部门的核心主数据
```

**这些不是靠调研能问出来的，只能靠数据碰面。**

#### 入湖的过程，本身就是一次治理

这是很多人没意识到的：数据入湖不是"搬数据"，是**让所有数据第一次碰面**。

```
数据入湖
    ↓
各系统的数据第一次被放在同一张地图上
    ↓
冲突、重复、缺失、口径不一 自动暴露
    ↓
这些"问题"就是治理的起点清单
    ↓
问题清单 → 反推治理范围 → 圈定主数据
```

**换句话说：治理范围是"问题暴露"出来的，不是"规划"出来的。**

这就是老周说的"入湖就已经是数据治理的开始"的技术含义。

#### 入湖的产出直接喂给主数据判断

书里第八章补充（续）讲的"入湖问题处理流程"，其实是这个机制的落地版本：



![diag_016](file:///home/ubuntu/hf-demo/diagram-img/diag_016.png)



**这条闭环说明了一件事：主数据的分级判断，是入湖之后由 DO 做出的实时决策，不是入湖之前照搬经验做出的预设。**

而这恰恰也是为什么"先做主数据治理"的路径走不通——**你在没有 DO 判断、没有入湖证据的情况下就宣布了主数据清单，这张清单从第一天就是错的。**

### 第二个必要条件：指标

只有入湖还不够。

入湖解决的是"数据长什么样"，但要确认"哪些是**真的**主数据、什么时候治、治到什么深度"，还需要一个外部标尺——**指标**。

因为主数据的价值，最终要通过业务指标兑现：

```
某个数据字段是不是主数据，看它在不在关键指标的计算链路里

• 在"客户主数据"里 → 客户怎么算收入？算留存？算客单价？
   → 它是不是真主数据，指标会告诉你

• 不在任何指标链路里 → 那它就是一个"重要的参考数据"
   → 治理的优先级和深度，都该往下调
```

**指标给主数据治理提供了三件事：**

| 指标提供 | 具体作用 |
|---------|---------|
| **范围确认** | 哪些字段进入了关键指标计算链路，则优先纳入治理 |
| **时机确认** | 哪个指标的业务压力大，则这个主数据域先治 |
| **深度确认** | 指标要什么精度，则决定治到什么程度（唯一性校验？标准统一？还是跨系统自动分发？） |

所以老周那句话要完整地读：

> **根据前文的数据指标确认，才能真正确认哪些是真的主数据，哪些主数据在什么时候、做到何种深度的治理。**

翻译成大白话就是：

> **主数据清单，不是拍出来的，是"盘出来 + 指标筛出来"的。**

而这个"盘"（数据资产盘点与入湖）本身，就是数据治理的第一块砖。

### 回到起点：看企业数据成熟度

那么，是不是所有企业都不该先做主数据治理？**不是。**

要看你现在站在哪一级。老周常用的划法是四级，我们把它落成可判断的信号：

| 成熟度 | 典型状态 | 正确的起点 | 常见错误 |
|--------|---------|-----------|---------|
| **L0 无体系** | 没有数据管理制度、没有专门组织、没有资产清单 | **先建体系**：制度 → 组织 → 摸家底 | 上来就买平台、就定标准 |
| **L1 有制度无全景** | 有《数据管理办法》、有数据办，但说不清有多少数据、在哪些系统 | **先入湖 + 资产盘点**：让数据见面 | 直接挑主数据开工 |
| **L2 有全景有标准** | 资产清楚、标准已成体系、平台在跑 | **主数据治理可作为突破口**，但范围须由指标复核 | 把已有清单当定论，不再验证 |
| **L3 治理常态化** | 治理已是日常运营、按业务价值滚动排期 | **主数据按指标价值滚动排期**，不再有"起点"问题 | 还在纠结"先做什么" |

**这张表回答了"要看企业数据成熟度再聊这个话题"：**

```
L0/L1 → 起点是数据治理本身（体系 + 全景）
L2    → 起点可以是主数据治理，但清单要复核
L3    → 不存在起点问题，只有排期问题
```

**给不同成熟度企业的一句话：**

| 成熟度 | 一句话 |
|--------|--------|
| L0 | 先确权建组织，别急着治具体数据 |
| L1 | 先让数据见面（入湖+盘点），再谈治谁 |
| L2 | 可以从主数据切入，但用指标复核范围 |
| L3 | 主数据治理已经是日常运营的一部分，别再当"项目"做 |

### 落地建议：怎么在管理层面前讲这套逻辑

因为这套顺序和行业惯例相反，推的时候容易被质疑"你凭什么"。给你三句话的讲法：

**第一句（承认共识的合理性）**：

> "先做主数据治理的思路本身没错，主数据确实是数据治理的必经环节。"

**第二句（指出共识的盲区）**：

> "但主数据清单不是规划出来的，是盘点出来的。在数据全量见面之前，我们定出来的清单只是照搬经验，范围很可能一开始就错了。"

**第三句（给出路径）**：

> "所以我们的顺序是：数据入湖 → 资产盘点 → 问题清单 → 指标筛出治理范围 → 主数据治理。看起来慢一步，但省掉的是后面全部的返工。"

这三句的核心是：**不否定对方，只是把"顺序"这件事从信念拉回到依据。**

### 常见反驳与回应

**反驳一："领导就批了主数据这块预算，不做说不过去。"**

> 预算批的是"主数据治理"这件事，不是"现在就能定出主数据清单"。可以先立项，但第一步的交付物应该是**盘点报告**，不是**主数据清单**。清单等盘点出来再定。

**反驳二："我们已经有主数据平台了，说明我们已经在做主数据治理。"**

> 平台是容器，不是判断依据。平台上线不等于主数据范围正确。**要问的是：这个平台里装的主数据清单，是盘点出来的，还是照搬来的？** 如果是后者，它装的是一个未经检验的假设。

**反驳三："数据入湖太慢了，我们等不起。"**

> 入湖不是一次性大项目，是**持续的盘点手段**。而且它可以和其他工作并行：一边接数据源，一边把已经进来的那部分先盘出结论，不用等全部接完才动。

**反驳四："别人家都是先做主数据的。"**

> 别人家的顺序是**他们自己数据成熟度决定的**，不是通用规律。**抄别人的顺序，等于抄了别人的前提条件。** 他们的前提是数据已经接进来了，你的可能还没有。

**反驳五："我们数据挺干净的，直接治不行吗？"**

> "干净"是相对于你已知的问题。真正的问题恰恰藏在没进过你视野的那部分数据里。

---

### 本章小结

```
数据治理 ⊃ 主数据治理

先做数据治理，再做主数据治理
理由：主数据清单是"盘出来"的，不是"规划出来的"

盘点靠两件事：
① 数据入湖 —— 让全量数据碰面，问题自己暴露
② 指标   —— 筛出真的主数据，确认范围、时机、深度

企业成熟度决定起点：
L0 → 先建体系
L1 → 先入湖盘点
L2 → 可从主数据切入，但清单需指标复核
L3 → 无起点问题，只有排期问题
```

### 核心金句

> **主数据治理不是数据治理的起点，是数据治理摸清家底之后的第一个突破口。**

> **你不可能在没看过全量数据之前，宣布哪些数据是主数据。**

> **治理范围不是规划出来的，是问题暴露出来的。**

> **主数据清单，不是拍出来的，是"盘出来 + 指标筛出来"的。**

> **抄别人的顺序，等于抄了别人的前提条件。**

## 第三章 数据治理规划：先出规划，再谈落地

### 上一章留下的坑

上一章我们讲清了"数据治理的本质是治责任"。

但知道本质是一回事，能不能做起来是另一回事。

现实中大量企业的数据治理是这样的：

```
领导一句"要搞数据治理"
   ↓
IT部门买一套平台
   ↓
各业务部门被要求配合填报
   ↓
半年后，平台上线，数据还是乱的
   ↓
项目结项，报告写着"一期建设完成"
   ↓
二期不知道该做什么，因为没人说得清一期为什么这么定
```

**问题出在哪？缺规划。**

> **前两章定下的两件事，在这里汇合：**
> 第一章说治理的本质是治责任；第二章说主数据清单是盘出来的、不是规划出来的。
> 所以这份规划的第一件事，不是列"要治哪些主数据"，而是**先规划怎么把家底盘清楚**——
> 也就是下面三大前置工程里的第二块：数据资产与标准基线。

### 为什么必须先有规划

没有规划的数据治理，本质是"边打边想"：

| 维度 | 没有规划 | 有规划 |
|------|----------|--------|
| 治理范围 | 谁催得紧就先治谁 | 按业务价值和治理难度排优先级 |
| 资源投入 | 每年重新申请，到处挤牙膏 | 有多年预算，人员稳定 |
| 目标设定 | "完成主数据治理" | "3年建成客户、产品、供应商三条主线" |
| 效果评估 | 交付了多少标准 | 业务指标改善了多少 |
| 责任划分 | 干到哪算哪 | 每条主线都有明确的DO |

**一句话：规划不是写给领导看的PPT，是用来对齐三年的目标、资源和责任。**

### 规划的两层结构

一份完整的数据治理规划，是两层楼：



![diag_017](file:///home/ubuntu/hf-demo/diagram-img/diag_017.png)



**顺序不能颠倒：先有体系，才谈计划；先有计划，才谈落地。**

大多数企业的错误是跳过第一层直接写第二层——规划里列了一堆要做的事，但组织没建、标准没定、平台没升级，执行时全线卡壳。

### 第一块：数据治理组织 + Data COE 团队组建 + 技术平台迭代升级

这是三大前置工程里**最需要提前启动**的一块，因为它涉及人和组织，周期最长。

#### 1.1 三层治理组织架构



![diag_018](file:///home/ubuntu/hf-demo/diagram-img/diag_018.png)



**关键在决策层。** 没有高层的决策层，数据治理就退化成IT部门的技术活。

#### 1.2 Data COE 团队的组建

**先说清楚 Data COE 是什么、不是什么。**

```
❌ 不是：新增一个行政机构，多几个编制多开会
❌ 不是：给现有IT人员换个抬头
✅ 是：一支有明确授权、有能力模型、能对业务输出标准动作的团队
```

**COE = Center of Excellence（卓越中心）。它不是"帮别人干活的人"，是"定义标准并让别人照着干的人"。**

**COE 的三大职能：**

| 职能 | 做什么 | 谁来承担 |
|------|--------|----------|
| **治理** | 定标准、建体系、控质量 | 数据标准专家 + 数据质量专家 |
| **技术** | 建平台、做集成、供服务 | 数据架构师 + 平台与集成工程师 |
| **应用** | 让数据真正被用起来 | 数据应用 + 数据运营 |

**第三块"数据应用"最容易被漏掉，但它决定 COE 是"成本中心"还是"价值中心"。**

只会治理不会应用的 COE，做出来一堆标准和模型，业务部门没有获得任何好处——三年后一定被质疑"花这么多钱治了个寂寞"。

数据应用要做的是：把治理好的数据变成业务能直接用的东西（指标、标签、看板、API、预警），让业务部门**主动来找 COE 要数据**，而不是 COE 天天催业务填数据。

**组建五步：**

**第一步：定编制与角色分工**

一支能打的数据治理 COE，团队规模在 **6~15 人**之间，具体取决于企业规模和数据复杂度，而不是取决于拍脑袋。

| 角色 | 人数 | 核心职责 | 能力要求 |
|------|------|----------|----------|
| COE 负责人 | 1 | 对外代表COE、跨部门协调、汇报高层 | 业务理解+项目管理+向上沟通 |
| 数据架构师 | 1~2 | 域划分、模型设计、总体架构 | 数据建模、领域经验 |
| 数据标准专家 | 2~3 | 制定标准、维护标准体系 | 业务+标准方法论 |
| 数据质量专家 | 2~3 | 稽核规则设计、质量运营、问题闭环 | SQL、规则引擎思维 |
| 平台与集成工程师 | 2~3 | 平台配置、接口开发、集成实施 | 技术工程能力 |
| 数据应用 | 1~2 | 数据服务化、场景落地、需求响应 | 业务场景+数据思维 |
| 数据运营 | 1~2 | 日常运营、通报、考核数据支撑 | 细致+沟通 |

**按企业规模选档：**

| 档位 | 团队规模 | 适用企业 | 配置特点 |
|------|----------|----------|----------|
| 精简型 | 6~8人 | 小型/单一业务企业，主数据域 ≤3 | 角色高度兼任，平台用成熟产品 |
| 标准型 | 9~12人 | 中型制造业，多主数据域并行 | 全角色齐备，标准与质量专人负责 |
| 完整型 | 12~15人 | 大型集团/多法人、多系统集成复杂 | 分组作业（标准组/质量组/平台组） |

**关键：一定要有"懂业务的人"在里面。**

纯技术出身的 COE 建不出业务认账的标准——他们不知道财务结账要什么字段、销售开单要什么颗粒度。

**第二步：区分专职与兼职（不要一人一岗）**

**不是每个角色都必须配一个专职。** 这一点是 COE 能不能"低成本启动"的关键。



![diag_019](file:///home/ubuntu/hf-demo/diagram-img/diag_019.png)



**兼职的判断标准：这个角色是否需要"跨项目、持续性"投入？**

- 需要持续跟、跨域协调、需要沉淀方法论的 → 专职
- 有明确交付物、按项目节奏走的 → 兼职足够

**兼职的三个前提条件（否则兼职一定失败）：**

1. **有明确的产出承诺**——兼职要交付什么、什么时间交，写清楚
2. **本岗领导认可**——兼职是给现有岗位加活，必须先谈好优先级，否则做不动
3. **有 COE 侧的兜底**——COE 专职人员要能接住兼职没做完的部分，不能默认兼职一定靠谱

**兼职的真实价值：**

| 好处 | 说明 |
|------|------|
| 成本可控 | 小企业不必养一支全专职队伍 |
| 业务贴近 | 兼职的人本来就在业务现场，标准更靠谱 |
| 影响力扩散 | 兼职者回到本部门就是"数据治理的火种" |
| 减少抵触 | 比从外部空降一个团队更容易被接受 |

**但要警惕：兼职超过一半，COE 就会变成"兼管"。** 那就回到老路了——谁都不全职管，谁都管不好。

> **兼职是压缩固定成本的工具，不是降低管理标准的借口。**

**第二步：定授权边界（COE 有没有牙齿）**

没有授权的 COE 只能"建议"，建议没人听。至少要拿到三样：

| 授权 | 说明 | 没有会怎样 |
|------|------|-----------|
| 标准发布权 | 经COE审核通过的数据标准，业务系统必须采纳 | 标准变成建议文档 |
| 稽约否决权 | 不符合标准的系统上线，COE有权卡 | 治理沦为事后追认 |
| 考核建议权 | 数据质量结果纳入部门KPI，COE出数据、提建议 | 质量好坏与部门无关 |

**第三步：定运作机制（怎么和业务部门协作）**

COE 和业务部门的关系是最容易搞错的一环：

```
❌ 错：COE → 业务部门（我来管你的数据）
✅ 对：COE → 业务部门（我给你标准和工具，你自己治）
```

具体机制：

- **需求受理制**：业务提治理需求 → COE 评估（是否在规划范围内、复杂度、依赖）→ 排期 → 交付
- **标准共创制**：标准草案由 COE 起草，业务部门评审定稿，**不搞"下发即生效"**
- **联合攻坚制**：跨域难题（如客户与订单打通）组建联合小组，COE出方法，业务出人力
- **月度例会制**：COE 全体 + 各域数据责任人，通报质量、评审需求、排优先级
- **季度复盘制**：回顾季度目标、暴露问题、调整下季度优先级

**第四步：定能力模型与培养路径**

COE 的人不是招来就有的。三种来源混合最健康：

| 来源 | 优势 | 风险 | 补强方式 |
|------|------|------|----------|
| 内部数据管理岗 | 熟悉业务、留得住 | 思维固化、缺方法论 | 外派培训+引入外部方法论 |
| 外部咨询/实施 | 方法论强、上手快 | 成本高、不了解组织、留不住 | 用作"传帮带"，方法论内化 |
| 技术骨干 | 工程能力强 | 不懂业务话语 | 强制轮岗到业务场景 |

**培养路径**（专职与兼职的要求不同）：

```
专职人员：
第1年：COE 内部标准作业训练（每人都要独立完成一个域的标准制定）
      + 到业务部门轮岗2周（不是参观，是蹲点）
第2年：主导1条主线的完整治理，成为域专家
第3年：带教新人，开始向其他COE输出方法论

兼职人员：
第1年：只做"用得上的"——参与标准评审、稽核规则确认
      重点是理解标准怎么来的、为什么要这么定
第2年：承担本部门的一级主数据落地，成为业务侧的数据责任人
第3年：把本部门经验带回COE，参与标准迭代
```

**兼职人员不要求制定标准，但要求能"用标准、问标准"。**

**第五步（关键）：建"不靠 COE 也能跑"的机制**

COE 最大的风险是**变成瓶颈**——所有事都要经过它。

必须同步建设：

- **业务侧自助能力**：业务部门的 DC 能自己维护自己领域的数据，COE 只管标准和稽核
- **方法论沉淀**：把每条主线的做法固化成模板、清单、工具，让第二个人能做
- **轮岗机制**：COE 人员定期下沉业务，避免闭门造车
- **数据服务化**：把数据做成业务直接可调用的服务（接口、看板、指标），让需求方绕开 COE 就能拿到数据——**这是化解瓶颈最有效的办法**

> **COE 的成功标志不是"数据治理做得最多"，而是"离开 COE，治理也能继续转"。**

> **COE 的第二成功标志是"业务不用排队等 COE 就能用上数据"——数据应用做起来了，COE 才会从成本中心变成价值中心。**

#### 1.3 技术平台的迭代升级

规划里必须写清楚平台每年要演进什么，而不是"买一套平台"就完事：

```
第1年：主数据平台基础能力（编码、模型、CRUD、权限）
第2年：数据质量稽核（规则库、质量报告、问题工单闭环）
第3年：服务化与集成（标准接口、数据分发、订阅式取数）
第4~5年：智能化（自动查重、异常识别、AI辅助稽核）
```

**平台不是一次性项目，是持续演化的产品。** 规划里没有"平台迭代路线"，就等于没有平台规划。

### 第二块：数据资产与标准基线（摸清家底）

这一块回答第一章遗留的问题：**我们现在在哪？**

**必须盘出来的四张清单：**

1. **系统清单**：全企业有多少个系统在跑数据？包括那些没人管的自主开发系统、Excel台账、外包系统
2. **数据资产清单**：每个系统管着什么数据？数据量、更新频率、责任人是谁
3. **主数据范围清单**：哪些是主数据？属于哪个域？谁是DO？哪些是二级属性？
4. **质量现状基线**：关键字段的完整率、准确率、唯一性——没有基线，年底无法证明治理有效

**再加一张标准基线**：

- 现有的编码规则（有没有？是否冲突？）
- 现有的数据标准（有多少条是真正在用的，多少条是躺在文档里的？）
- 现有流程（谁在维护、变更走什么流程、多久能完成一次变更？）

**这一步的产出是《数据资产现状基线报告》，是三年工作的起点线。**

没有基线，明年你无法回答"我们治理得怎么样"——因为没有参照物。

### 第三块：数据治理体系与管理体系的建立

前两块备齐"人和工具"，这一块立"规矩"。

**数据治理体系（治什么、怎么治）**



![diag_020](file:///home/ubuntu/hf-demo/diagram-img/diag_020.png)



**管理体系（谁来管、怎么管、怎么考核）**

| 机制 | 内容 |
|------|------|
| 责任机制 | DO/DC 岗位职责、提名与确认流程、变更审批权限 |
| 运行机制 | 例会制度、问题上报与闭环流程、质量通报周期 |
| 考核机制 | 数据质量纳入部门KPI、纳入年度评优 |
| 变更机制 | 标准变更、编码变更、主数据新增/停用的流程与时限 |
| 争议裁决 | 跨部门数据争议的上诉与终裁机制（数据治理委员会） |

**这一块最容易被跳过，也最致命。**

体系不建，治理就永远是"临时运动"——每次靠领导发话推动，靠 Excel 跟踪，人一走就断档。

### 三块齐备后：编制3~5年执行计划

三大前置工程就位，才能编制真正的执行计划。

**执行计划的核心是排序和节奏：**



![diag_021](file:///home/ubuntu/hf-demo/diagram-img/diag_021.png)



**三年到五年的典型节奏：**

| 年份 | 定位 | 关键动作 |
|------|------|----------|
| 第1年 | 奠基 | 三大前置工程落地；1~2条主线试点（验证方法论、暴露真问题） |
| 第2年 | 复制 | 方法论修正为标准动作；扩展到第二、三条主线 |
| 第3年 | 铺开 | 主数据域基本覆盖；平台进入服务化阶段 |
| 第4~5年 | 运营 | 从项目制转为常态运营；平台智能化；数据资产化 |

**每个年度还要有资源计划**：COE 团队编制（6~15人，含专职与兼职比例）、各业务部门投入人力（最低标准是"每条主线至少1名业务骨干"）、预算金额、平台迭代需求。

**以及度量计划**——预先定好指标，否则年底无法交账：

- 覆盖率：主数据中已确权、已落标准、已入平台的比例
- 质量：关键字段完整率、准确率、唯一性
- 效率：报表取数从"3天"缩短到"3分钟"
- 业务：因数据错误导致的返工、损失、客诉下降了多少

### 执行计划必须走公司的战略规划确认流程

**这是最容易被跳过、但杀伤力最大的一步。**

一份只存在于IT部门内部的规划，执行率接近于零。原因很简单：

- 没进公司战略规划 → 不在公司的资源盘子 → 要钱要人要不上
- 没进年度经营计划 → 业务部门没有 KPI 压力 → 配合度全看人情
- 没有高层背书 → 执行遇阻无人拍板 → 逐个业务单元谈崩

**正确路径：**

```
三大前置工程方案
      ↓
3~5年执行计划初稿
      ↓
纳入公司战略规划 / 五年规划编制
      ↓
纳入年度经营计划与预算（按年分解）
      ↓
管理层 / 数据治理委员会评审、签字背书
      ↓
按部就班、逐年推进
```

**签字的这一刻，才算规划成立。** 在此之前，它只是一份建议书。

### 规划必须由技术部门牵头，但不能由技术部门独写

**这是最容易出错的地方。**

技术部门牵头是对的——因为技术部门是唯一能看到全局数据流向的角色。

但如果规划完全由技术部门闭门造车，一定失败。原因是：

- 技术部门不知道哪些数据对业务最重要
- 技术部门不知道业务部门愿意投入多少
- 业务部门不认账的规划，等于没有规划

**正确做法：技术部门搭框架，业务部门做填空，管理层做裁决。**

```
技术部门（Data COE）：出《数据治理规划框架》
   - 三大前置工程方案
   - 全企业系统清单和数据流向图
   - 主数据域划分建议
   - 平台架构和迭代路线
   - 分期优先级初排
        ↓
各业务部门：认领自己的责任
   - "我们部门的数据，我们来治"
   - 确认数据质量现状
   - 承诺投入资源
   - 提出本部门最痛的三个问题
        ↓
管理层/数据治理委员会：裁决
   - 优先级排序（有争议时拍板）
   - 资源分配
   - 规划终稿签字背书
```

**没有管理层签字的规划，执行率会低于30%。**

### 规划的三个常见坑

**坑一：规划写成"技术建设规划"**

最典型的症状：通篇讲平台要买什么、系统要建几个、技术架构怎么设计。

数据治理规划的主体不是技术方案，而是**业务治理路径**。平台只是承载手段。

**坑二：规划写成"理想蓝图"，没有分期**

一次性规划五年所有事情，看起来很有魄力，实际是"没有取舍"。

没有取舍的规划意味着：所有事情都重要、所有事情都要做、所有事情都做不好。

**一个检验标准：如果你的规划里没有"第4年才做"的項目，那它一定不是规划，是许愿。**

**坑三：规划做完就扔进抽屉**

规划写完，业务部门不认，年度计划不照着排，预算不按它来——等于没做。

**规划必须成为三件事的输入：年度部门计划、预算申请、项目立项排序。**

### 和主业工作的关系：规划先行，但不是规划全部

规划的作用是"对齐"，不是"包办"。

规划给出的是"三大前置工程 + 三年主线 + 每年重点 + 谁负责"，具体到某个治理域怎么治、选什么工具、怎么落地，那是实施阶段的事。

**不要用规划拖延启动，也不要用启动否定规划。**

正确的节奏是：

```
第1年：三大前置工程 + 规划 + 试点一条主线（验证方法论，暴露真问题）
第2年：规划 + 复制到第二三条主线（修正方法论，形成标准动作）
第3年：规划 + 沉淀为常态运营机制（从项目制转为运营制）
```

### 一句话总结

> **数据治理不是项目，是一场三年起步的战役。**
> **三大前置工程不齐，执行计划就是空中楼阁；**
> **执行计划不进战略规划，就是抽屉里的废纸；**
> **有规划的治理，每一年都在为下一年的加速铺路。**

### 本章小结

> 规划的价值不在于文档有多厚，而在于三年后回看时，每一年都知道自己在干什么。
> 先备齐组织（核心是Data COE团队组建）、摸清数据资产基线、建立治理与管理体系，再编制3~5年执行计划——顺序不能颠倒。
> 技术部门牵头搭框架，业务部门填空，管理层签字——三者缺一，规划就是废纸。
> 规划是给未来的自己留路标，不是给领导看的表演。


## 第四章 主数据二级分类模型：谁该管、谁不该管

### 传统主数据治理的问题

传统思路：把所有主数据列出来，用同一套方法治理。

问题：
- 主数据种类太多，边界模糊
- 不同主数据的业务价值完全不同
- 用同一套方法治理所有主数据，成本高、效率低
- 很多主数据都有系统在管了，还在重复建设

### 二级主数据分类模型



![diag_022](file:///home/ubuntu/hf-demo/diagram-img/diag_022.png)



### 两级的核心区别

| 维度 | 一级主数据 | 二级主数据 |
|------|-----------|-----------|
| 稳定性 | 核心稳定，变更极少 | 随业务变化，变更频繁 |
| 共享范围 | 全集团跨系统共享 | 本业务系统内部使用 |
| 治理主体 | 数据治理委员会统一管控 | 业务部门自行管理 |
| 平台依赖 | 必须有主数据管理平台 | 不需要，可随业务系统管理 |
| 管理成本 | 高（集中管理） | 低（分布式管理） |
| 典型示例 | 组织/人员/银行账号/税号 | 产品分类/销售区域/客户细分 |

### 核心洞察

**二级主数据的真正价值不是"治理"，而是"嵌入业务系统功能设计"。**

传统思路：先建主数据平台，再谈应用
米悦说说思路：
- 一级主数据 → 平台统一管理（标准动作）
- 二级主数据 → 在业务系统设计时就把数据架构考虑进去

### 关键判断标准

如何判断一个主数据是"一级"还是"二级"？



![diag_023](file:///home/ubuntu/hf-demo/diagram-img/diag_023.png)



### 核心金句

> 一级主数据靠平台，二级主数据靠嵌入。

> 二级主数据治理的最高境界，是让业务系统"忘记"主数据的概念——觉得数据就是功能的一部分。

    ↓

    ↓

    ↓
业务响应快，不阻塞
```

## 第八章 主数据内部的治理顺序：为什么HR主数据要优先

> **先厘清本章的位置**：第二章讲的是"数据治理与主数据治理谁先谁后"——那是**大顺序**，答案是数据治理先启动。
> 本章讲的是**小顺序**：在主数据治理内部，先治哪个域最容易见效、阻力最小、带动最广。
> 大顺序确定之后，才谈得上小顺序。

### 传统企业的通病

很多企业做**主数据治理**时的习惯顺序：
```
① 先治产品主数据
② 再治客户主数据
③ 最后治供应商主数据
```

**结果：治了半天，数据还是乱。因为忽略了最核心的东西。**

### 核心洞察：所有业务都落实到人和组织

```
产品 → 谁生产？谁销售？
客户 → 谁负责？谁维护？
供应商 → 谁采购？谁对接？
订单 → 谁审批？谁执行？
```

**产品、客户、供应商，最终都是"什么人、什么组织、什么岗位"在负责。**

### 主数据内部的正确顺序



![diag_029](file:///home/ubuntu/hf-demo/diagram-img/diag_029.png)



> **注意**：这个顺序的前提，是主数据范围已经由盘点确认（见第二章）。
> 如果主数据清单是照搬经验得来的，那么"先治HR"这个排序本身也就失去了依据——
> 先要确认的，不是"先治哪个"，而是"到底哪些是主数据"。

### 为什么HR主数据最难治理？

| 难点 | 说明 |
|------|------|
| 相对独立 | HR系统往往不受IT管辖 |
| 权力较大 | 核心部门，谁都得罪不起 |
| 数据敏感 | 人员信息涉及隐私 |
| 系统封闭 | SAP SuccessFactors、Workday等接口难开放 |

## 第九章补充：撬动HR主数据治理的完整路径（实战深化版）

### HR主数据治理的组织体系



![diag_033](file:///home/ubuntu/hf-demo/diagram-img/diag_033.png)



### 为什么入湖是前置工作？

```
传统做法（❌）：
先定义标准 → 再建平台 → 再分配责任
结果：标准落不了地，因为不知道现状

正确做法（✅）：
先入湖（所有HR系统数据）→ 分析现状 → 分清一级/二级 → 再定标准

好处：
- 不会把本该二级的主数据强加给HR管
- HR不会觉得数据治理是"被强加的任务"
- 责权清晰，落地容易
```

### 协商式治理

```
传统IT做法（❌）：
IT制定标准 → 强制HR执行 → HR不配合 → 推不动

米悦说说实践（✅）：
先入湖看现状 → 邀请HR一起分析 → HR说管不了就下沉为二级 → 共同认可才执行

核心：不是告诉HR"你该管什么"，是和HR一起"商量我们能管什么"
```

### 完整路径图

```
第一步：确权 → 《数据管理办法》
第二步：建组织 → 治理委员会 + HR小组 + DC（分一级/二级）
第三步：入湖（前置！）→ HR所有系统数据入湖
第四步：分析分类 → 入湖后识别一级/二级主数据
第五步：协商定标 → 与HR共同制定标准
第六步：执行考核 → DC推动 + 委员会监督
```

### 核心金句

> **入湖是撬动HR主数据治理的前置条件，不是技术工作，是治理方式变革的起点。**

> **协商式治理的核心是：不是告诉HR"你该管什么"，而是和HR一起"商量我们能管什么"。**

> **如果HR说管不了，那就不是一级主数据，是二级主数据，让它回归业务系统。**

### 聚焦打透的核心原则

```

选方向的标准：
1. 一把手最关注的
2. 当前企业最痛的
3. 能快速出成果的
4. 成功后影响力大的

> **从一把手最关注的点切入，成功了就是最好的背书。**

> **聚焦一个方向，做出成果，建立信任，再扩展下一个。**

> **数据治理是长期滚动迭代的过程，不是一锤子买卖。**

|--------|---------|------|
| 企业数据管理文化 | 萌芽阶段 | 增加培训，从"汗水驱动"迈向"智慧驱动" |
| 数据战略 | 初始级 | 建立数据战略决策组织 |
| 数据治理 | 初始级 | 成立数据治理委员会 |

### 三大痛点

**痛点01：报表层级错位，高层获得感不足**
- 现有报表缺高层全局视图
- 管理者需手动整理信息，难快速掌握业务全貌

**痛点02：指标口径不一致，跨模块比对困难**
- 指标定义与计算逻辑不统一
- 例如：库存，生产关注数量，财务关注金额

**痛点03：数据治理"有框架、无落地"**
- 有制度但执行不到位

### 项目组织（已脱敏）

- **项目领导小组组长**：某高管
- **副组长**：若干高管
- **项目经理**：项目负责人
- **项目PMO**：PMO负责人

### 解决方案：三驾马车战略

```
战略决策层：高层挂帅，拍板口径、调配资源
业务执行层：每个指标有明确Owner，负责定义与解释
技术支持层：负责技术落地
```

## 第十二章 数据治理的11条实战军规

```
1. 数据治理的本质是治责任，不是治数据
2. 一级主数据靠平台，二级主数据靠嵌入
3. 主数据平台是质检站+高速公路，不是审批关卡
4. 能通过业务系统管理的，就不要搬到主数据平台
5. 数据治理的第一步是确权，不是买平台
6. 数据治理先于主数据治理启动：主数据清单是盘出来的，不是规划出来的
7. HR主数据是主数据治理内部的锚点，不是数据治理的起点
8. 源端治理的本质是让数据在产生的地方就被管好
9. 业务响应速度是检验数据治理成效的核心指标
10. 没有考核的数据治理都是耍流氓
11. 数据治理是长期工程，先易后难，先核心后外围
```

> 第6条与第7条是一对，容易记混：
> **第6条讲"大顺序"（数据治理 → 主数据治理），第7条讲"小顺序"（HR主数据 → 其他主数据域）。**
> 顺序对了，先后才能对。
