# 【新增】引言：AI时代，数据治理的第三次浪潮

> 本章为全书开篇，阐述AI时代为什么数据治理变得前所未有的重要

## 三次浪潮

```
数据治理的三次浪潮

├── 第一波：ERP时代
│   └── 核心问题：各系统数据不一致
│
├── 第二波：大数据时代
│   └── 核心问题：数据孤岛、数据资产看不见
│
└── 第三波：AI时代 ⬅️ 我们正在经历的
    └── 核心问题：AI要落地，数据是基础
    └── 本体论、知识图谱、关联关系...都是数据
    └── 没有数据治理，AI转型无从落地
```

## AI落地的四大基石

```
当AI落地企业时，真正有价值的是四样东西：

  ① 数据    ← 一切的基础
  ② 流程   ← 最终也是数据
  ③ 知识   ← 最终也是数据
  ④ 规则   ← 最终也是数据

关键洞察：不管怎么分类，流程、知识、规则
最终在数字化系统里，都是「数据」的形式呈现
```

## 为什么数据治理是AI转型的基础？

```
AI落地企业，需要回答三个问题：

问题1：数据是什么？
问题2：关联关系是什么？
问题3：规则在哪里？

结论：
如果没有数据治理
连数据都说不清
AI转型就是空谈
```

## 核心金句

> **当AI落地企业时，数据、流程、知识、规则最终都是数据的形式呈现——数据治理成了重中之重。**

> **本体论的根基是数据，没有数据治理，本体论就是空中楼阁。**

> **AI转型不是买一套AI系统，数据治理才是AI转型的入场券。**

# 【新增核心章节】数据治理的真正阻力：不是技术，是政治

> 本章是全书方法论的升华，揭示数据治理失败的真实原因

## 技术问题往往不是真正的问题

```
数据治理表面上是技术问题：
├── 数据标准不统一
├── 数据质量差
├── 系统之间不互通
└── 平台工具不好用

但这些往往是借口，不是真正的原因

真正的原因藏得更深：
└── 责权的博弈
└── 权力的让渡
└── 工作方式的改变
```

## 主数据治理阻力不大，原因很简单

```
主数据治理为什么阻力不大？

因为：
└── 主数据是"别人的数据"
└── 各部门用别人的数据
└── 用好了，大家都受益

举例：
├── 组织架构主数据 → 各部门都要用
├── 客户主数据 → 销售、市场、客服都要用
└── 供应商主数据 → 采购、财务、仓库都要用

结论：
└── 主数据治理，各部门都能受益
└── 阻力自然不大
```

## 真正的阻力在哪里？

```
真正的阻力来自：

┌──────────────────────────────────────┐
│         一线业务数据和实际业务数据       │
│  （这些数据掌握在业务部门手里）         │
└──────────────────────────────────────┘

这些数据的特点：
├── 代表部门的业绩
├── 代表部门的责权
├── 代表部门的价值
└── 动了这些数据 = 动了部门的"蛋糕"
```

## 阻力来源一：部门不愿公开数据

```
典型心态：
"这些数据是我们部门的核心竞争力"
"一旦公开，其他部门都能看到我们的业绩"
"那我们还有什么话语权？"

深层原因：
├── 数据透明 = 业绩透明
├── 业绩透明 = 压力透明
└── 某些部门宁愿数据不准，也不愿透明

举例：
├── 销售部门：不愿公开客户跟进记录
├── 客服部门：不愿共享服务数据
└── 采购部门：不愿公开供应商议价数据
```

## 阻力来源二：数据管理部门不愿放权

```
典型心态：
"如果数据都归业务部门管"
"我们数据管理部门的价值在哪里？"
"我们的职能会不会被弱化？"

深层原因：
├── 担心管理职能被架空
├── 担心部门价值被边缘化
└── 担心既得利益受损

这种心态不仅业务部门有
数据管理部门自己也可能有
```

## 阻力来源三：工作方式的改变

```
习惯的力量是强大的：

很多部门：
├── 习惯用Excel管理数据
├── 习惯手工台账
├── 习惯"我说了算"的数据
└── 不习惯系统化管理

转变的痛苦：
├── 要学新系统
├── 要遵守新标准
├── 要改变旧习惯
└── 阻力可想而知
```

## 阻力来源四：责权的博弈与再分配

```
数据治理的本质是责权的重新分配

数据治理前：
└── "这个数据是我们部门的"
└── "这个数据我说了算"

数据治理后：
├── 数据要共享
├── 标准要统一
├── 权限要重新划分
└── "那我的权力是不是被削弱了？"

这是最核心的阻力：
├── 不是技术问题
├── 不是工具问题
├── 是权力格局的重塑
└── 是利益分配的再平衡
```

## 三类阻力的对比

```
┌────────────────┬─────────────────────┬─────────────────┐
│    阻力类型     │       表现          │     本质        │
├────────────────┼─────────────────────┼─────────────────┤
│ 部门不愿公开    │ 数据藏着不共享      │ 业绩怕透明      │
├────────────────┼─────────────────────┼─────────────────┤
│ 数据部门不放权  │ 抓着数据不放手       │ 担心职能弱化    │
├────────────────┼─────────────────────┼─────────────────┤
│ 工作方式改变    │ 不想用系统、想手工   │ 习惯难改       │
├────────────────┼─────────────────────┼─────────────────┤
│ 责权再分配     │ 都不想动既有权力格局 │ 利益格局重塑   │
└────────────────┴─────────────────────┴─────────────────┘
```

## 如何应对这些阻力？

```
应对策略一：借力打力
├── 从一把手最关注的点切入
├── 用一把手的权威推动
└── 阻力自然变小

应对策略二：先易后难
├── 先推主数据（阻力小）
├── 做出成果再说
└── 不要一开始就碰敏感数据

应对策略三：协商共建
├── 不是"IT强推"
├── 而是"一起定规则"
├── 让业务部门有参与感
└── 阻力自然减小

应对策略四：证明价值
├── 让阻力方看到数据治理的好处
├── 好处要具体、可感知
└── 不是"对公司好"，而是"对你好"

应对策略五：换人不如换思路
├── 不能换人的情况下
├── 改变工作方式
└── 用系统减少手工，用数据减少摩擦
```

## 核心金句

> **数据治理的阻力从来不是技术问题，是政治问题。**

> **主数据治理阻力小，是因为大家都在"用别人的数据"；真正阻力大的，是那些掌握在一线部门手里的、代表部门责权的数据。**

> **数据治理的本质不是治理数据，是重新分配责权、重塑利益格局。**

> **不理解这一点，再好的数据治理方案都会失败。**

## 第一章 数据治理的本质：不是治数据，是治责任

### 很多企业做数据治理都搞错了方向

常见做法：
- 买一套数据治理平台
- 建一个主数据管理系统
- 招聘一批数据治理工程师
- 制定一堆数据标准文档

结果：平台买了没人用，系统建了没人管，标准定了没人执行。

### 问题的根源

数据治理的本质是**治责任**，不是治数据。

```
数据治理 = 让每一笔数据都能找到责任人

找不到责任人的数据 = 没人管的数据 = 乱数据
能找到责任人的数据 = 有人管的数据 = 好数据
```

### 一个简单的测试

问：你们公司的"客户"数据，谁负责？

A. 没人负责（CRM算吗？销售算吗？）
B. 数据部门负责（他们管得了业务吗？）
C. 业务部门负责（哪个业务部门？）
D. 有明确的部门和岗位负责（恭喜你，做对了）

如果你选了A/B/C，说明你们的数据治理还没入门。

### 治数据的三个层次

```
第一层：技术治数
└── 建平台、定标准、管数据
└── 大多数企业的做法

第二层：流程治数
└── 定流程、分责任、立考核
└── 少数企业的做法

第三层：责任治数（最高境界）
└── 每一笔数据都有明确的责任人
└── 数据是业务的一部分，不是独立的"治理对象"
└── 极少数企业的做法
```


### 产品主数据确权：不是问谁"需要"，是问谁最"受不了"

产品主数据谁都用：质量要标准、生产要BOM、销售要定价、采购要规格、财务要成本。

那到底谁是主责？

错误答案：
- **IT部门** → 数据治理是业务决策，不是技术问题
- **研发单独主责** → 懂技术但不懂市场和质量

正确逻辑：**不是问谁"需要"这个数据，而是问谁最"受不了"这个数据出错。**

| 部门 | 用什么 | 数据出错谁最受伤 |
|------|--------|-----------------|
| 质量 | 产品标准、规格、有效期、GMP要求 | **质量部门** |
| 生产 | 物料清单BOM、工艺路线 | 生产部门 |
| 销售 | 产品名称、销售分类、定价区间 | 销售部门 |
| 采购 | 物料关联、供应商规格 | 采购部门 |
| 财务 | 成本核算、定价 | 财务部门 |

**答案：质量部门应该是产品主数据的DO（Data Owner）。**

理由：
1. 质量是产品最核心的属性——名称、规格、标准、有效期都是"质量语言"
2. 质量部门相对中立——不是最大受益者，也不是最大"制造者"
3. 质量有监管压力（GMP等）——有内驱力管好数据
4. 质量做不好，谁都跑不掉——倒逼有责任感

**DO和DC分工：**

```
DO（质量部门）
├── 裁判员：判断这个属性该不该是一级主数据
├── 拍板：决定"产品主数据管理办法"
└── 监督：核查分发出去的数据质量是否合规

DC（各业务领域）
├── 运动员：负责自己领域的扩展属性录入和维护
├── 研发DC → 技术参数、配方相关
├── 销售DC → 销售分类、市场定位
├── 生产DC → BOM、工艺路线
└── 财务DC → 成本中心、定价
```

### 供应商主数据确权：分类比统一更重要

供应商比产品更难确权——因为供应商类型太多了。

只要是签合同、付款的都可以称为供应商：原材料采购、IT设备采购、服务类采购……每个类型引入的部门不同。

问：**谁在"制造"供应商？**

| 供应商类型 | 谁引入的 | 谁主导关系 |
|-----------|----------|-----------|
| 原材料/辅料采购 | 采购部 | 采购部 |
| IT设备/软件 | IT部 | IT部 |
| 行政服务 | 行政部 | 行政部 |
| 销售服务 | 销售部 | 销售部 |
| 财务专业服务（审计/税务） | 财务部 | 财务部 |

**没有哪个部门能单独做所有供应商的DO。** 这是供应商和产品最本质的区别。

**正确解法：分类确权**

```
供应商主数据
├── 一级（商业通用属性）
│   ├── 统一编码
│   ├── 企业名称/税号/银行账户
│   └── 基本联系信息
│   └── DO：采购部（统一管控，有成本视角）
│
└── 二级（业务分类属性）
    ├── 原材料类 → 资质/交货条款 → DO：采购部
    ├── IT类 → 配置/维保条款 → DO：IT部
    ├── 服务类 → 服务条款/验收 → DO：各需求部门
    └── 财务专业类 → 审计/税务条款 → DO：财务部
```

**为什么采购做一级供应商的DO？**

- 采购是唯一所有类型供应商都"经过"的部门
- 采购有成本视角——供应商出问题最终反映在采购成本上
- 采购有"付款控制权"——倒逼供应商配合

### 员工供应商：主数据分级的终极难题

有一类供应商很特殊——员工。

报销、差旅等支出走员工信息，员工既是"人"又是"供应商"。

```
员工供应商
├── 作为"人" → HR主数据管辖
│   ├── 人员基本信息（HR系统）
│   ├── 组织归属（HR系统）
│   └── 薪资/考勤（HR系统）
│
└── 作为"供应商" → 供应商主数据管辖
    ├── 报销账号（财务系统）
    ├── 税号/银行（财务系统）
    └── 合同关系（采购/法务系统）
```

**最大风险：两个系统各自维护一套"员工供应商"信息——HR改了名字，财务系统里还是旧的。**

这恰恰说明了一个关键原则：

> **主数据分级不是为了分类，是为了分清"谁负责"——不分级的主数据治理，最终是一本糊涂账。**

如果把所有数据都当一级主数据来管：
- 量大管不过来 → 数据部门变成"审批部门" → 阻塞业务
- 责任分散 → 没人真正负责
- 投入产出不成正比 → 失去高层信任

**一级主数据解决"有人管"的问题，二级主数据解决"管到位"的问题。**



### 本章小结

> 数据治理的核心不是技术，是责任。
> 没有责任心的技术方案，都是在浪费钱。
> 没有责任心的数据标准，都是废纸。

## 第二章 数据治理规划：先出规划，再谈落地

### 上一章留下的坑

上一章我们讲清了"数据治理的本质是治责任"。

但知道本质是一回事，能不能做起来是另一回事。

现实中大量企业的数据治理是这样的：

```
领导一句"要搞数据治理"
   ↓
IT部门买一套平台
   ↓
各业务部门被要求配合填报
   ↓
半年后，平台上线，数据还是乱的
   ↓
项目结项，报告写着"一期建设完成"
   ↓
二期不知道该做什么，因为没人说得清一期为什么这么定
```

**问题出在哪？缺规划。**

### 为什么必须先有规划

没有规划的数据治理，本质是"边打边想"：

| 维度 | 没有规划 | 有规划 |
|------|----------|--------|
| 治理范围 | 谁催得紧就先治谁 | 按业务价值和治理难度排优先级 |
| 资源投入 | 每年重新申请，到处挤牙膏 | 有多年预算，人员稳定 |
| 目标设定 | "完成主数据治理" | "3年建成客户、产品、供应商三条主线" |
| 效果评估 | 交付了多少标准 | 业务指标改善了多少 |
| 责任划分 | 干到哪算哪 | 每条主线都有明确的DO |

**一句话：规划不是写给领导看的PPT，是用来对齐三年的目标、资源和责任。**

### 规划的两层结构

一份完整的数据治理规划，是两层楼：

```
┌─────────────────────────────────────────────┐
│  第一层：三大前置工程（先把"家伙什"备齐）      │
│                                             │
│  ① 数据治理组织 + Data COE + 技术平台迭代升级  │
│  ② 数据资产与标准基线（摸清家底）             │
│  ③ 数据治理体系与管理体系（立规矩）           │
│                                             │
│  没有这三块，执行计划就是空中楼阁              │
└─────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────┐
│  第二层：3~5年执行计划                        │
│                                             │
│  纳入公司战略规划 / 年度经营计划走确认流程     │
│  然后按部就班、逐年推进                        │
└─────────────────────────────────────────────┘
```

**顺序不能颠倒：先有体系，才谈计划；先有计划，才谈落地。**

大多数企业的错误是跳过第一层直接写第二层——规划里列了一堆要做的事，但组织没建、标准没定、平台没升级，执行时全线卡壳。

### 第一块：数据治理组织 + 技术侧 Data COE + 技术平台迭代升级

这是三大前置工程里**最需要提前启动**的一块，因为它涉及人和组织，周期最长。

**组织架构：三层设计**

```
决策层：数据治理委员会（或数据治理领导小组）
   │  主任：分管高管    成员：各业务部门负责人
   │  职责：定方向、裁决争议、批资源、考核结果
   │
管理层：数据治理工作组 / 办公室（设在IT或数字化部门）
   │  职责：日常推进、跨部门协调、跟踪考核
   │
执行层：各领域数据责任人（DO / DC）
   │  职责：数据标准落地、质量核查、问题整改
```

**关键在决策层。** 没有高层的决策层，数据治理就退化成IT部门的技术活。

**技术侧 Data COE（Center of Excellence）**

COE 不是一个"挂名的管理机构"，而是一个**能力中心**，承担四件事：

| 职责 | 具体内容 |
|------|----------|
| 方法论沉淀 | 把每次项目的做法、模板、踩过的坑固化成可复用的标准动作 |
| 工具与平台演进 | 主数据平台、数据质量工具、稽核规则库的迭代规划与版本管理 |
| 能力建设与认证 | 培训业务部门的数据责任人，形成"懂业务+懂数据"的内生力量 |
| 疑难攻坚 | 各条主线的技术攻坚、跨域问题定级、平台需求评审 |

**为什么 COE 必须是"技术侧"的？**

因为只有技术侧能同时看到：哪些数据在流、哪些接口在传、哪些系统在重复造轮子。

业务侧看数据价值，COE 看数据链路——**两个视角缺一不可，但技术视角必须有人系统性承担。**

**技术平台的迭代升级**

规划里必须写清楚平台每年要演进什么，而不是"买一套平台"就完事：

```
第1年：主数据平台基础能力（编码、模型、CRUD、权限）
第2年：数据质量稽核（规则库、质量报告、问题工单闭环）
第3年：服务化与集成（标准接口、数据分发、订阅式取数）
第4~5年：智能化（自动查重、异常识别、AI辅助稽核）
```

**平台不是一次性项目，是持续演化的产品。** 规划里没有"平台迭代路线"，就等于没有平台规划。

### 第二块：数据资产与标准基线（摸清家底）

这一块回答第一章遗留的问题：**我们现在在哪？**

**必须盘出来的四张清单：**

1. **系统清单**：全企业有多少个系统在跑数据？包括那些没人管的自主开发系统、Excel台账、外包系统
2. **数据资产清单**：每个系统管着什么数据？数据量、更新频率、责任人是谁
3. **主数据范围清单**：哪些是主数据？属于哪个域？谁是DO？哪些是二级属性？
4. **质量现状基线**：关键字段的完整率、准确率、唯一性——没有基线，年底无法证明治理有效

**再加一张标准基线**：

- 现有的编码规则（有没有？是否冲突？）
- 现有的数据标准（有多少条是真正在用的，多少条是躺在文档里的？）
- 现有流程（谁在维护、变更走什么流程、多久能完成一次变更？）

**这一步的产出是《数据资产现状基线报告》，是三年工作的起点线。**

没有基线，明年你无法回答"我们治理得怎么样"——因为没有参照物。

### 第三块：数据治理体系与管理体系的建立

前两块备齐"人和工具"，这一块立"规矩"。

**数据治理体系（治什么、怎么治）**

```
数据治理体系
├── 数据标准体系     基础标准、主题标准、指标标准
├── 主数据体系       分类模型、确权机制、编码规则、维护规范
├── 数据质量体系     质量维度定义、稽核规则、评分与考核办法
├── 数据集成体系     接口规范、交换频率、时效与血缘管理
└── 数据安全体系     分级分类、权限管控、脱敏与审计
```

**管理体系（谁来管、怎么管、怎么考核）**

| 机制 | 内容 |
|------|------|
| 责任机制 | DO/DC 岗位职责、提名与确认流程、变更审批权限 |
| 运行机制 | 例会制度、问题上报与闭环流程、质量通报周期 |
| 考核机制 | 数据质量纳入部门KPI、纳入年度评优 |
| 变更机制 | 标准变更、编码变更、主数据新增/停用的流程与时限 |
| 争议裁决 | 跨部门数据争议的上诉与终裁机制（数据治理委员会） |

**这一块最容易被跳过，也最致命。**

体系不建，治理就永远是"临时运动"——每次靠领导发话推动，靠 Excel 跟踪，人一走就断档。

### 三块齐备后：编制3~5年执行计划

三大前置工程就位，才能编制真正的执行计划。

**执行计划的核心是排序和节奏：**

```
              业务价值高
                  ↑
                  │
   优先做  ←──────┼──────→  后做
                  │
                  ↓
              业务价值低

治理难度：先做"高价值+低难度"的（打鸡血），再做"高价值+高难度"的（啃硬骨头）
```

**三年到五年的典型节奏：**

| 年份 | 定位 | 关键动作 |
|------|------|----------|
| 第1年 | 奠基 | 三大前置工程落地；1~2条主线试点（验证方法论、暴露真问题） |
| 第2年 | 复制 | 方法论修正为标准动作；扩展到第二、三条主线 |
| 第3年 | 铺开 | 主数据域基本覆盖；平台进入服务化阶段 |
| 第4~5年 | 运营 | 从项目制转为常态运营；平台智能化；数据资产化 |

**每个年度还要有资源计划**：专职团队编制、各业务部门投入人力（最低标准是"每条主线至少1名业务骨干"）、预算金额、平台迭代需求。

**以及度量计划**——预先定好指标，否则年底无法交账：

- 覆盖率：主数据中已确权、已落标准、已入平台的比例
- 质量：关键字段完整率、准确率、唯一性
- 效率：报表取数从"3天"缩短到"3分钟"
- 业务：因数据错误导致的返工、损失、客诉下降了多少

### 执行计划必须走公司的战略规划确认流程

**这是最容易被跳过、但杀伤力最大的一步。**

一份只存在于IT部门内部的规划，执行率接近于零。原因很简单：

- 没进公司战略规划 → 不在公司的资源盘子 → 要钱要人要不上
- 没进年度经营计划 → 业务部门没有 KPI 压力 → 配合度全看人情
- 没有高层背书 → 执行遇阻无人拍板 → 逐个业务单元谈崩

**正确路径：**

```
三大前置工程方案
      ↓
3~5年执行计划初稿
      ↓
纳入公司战略规划 / 五年规划编制
      ↓
纳入年度经营计划与预算（按年分解）
      ↓
管理层 / 数据治理委员会评审、签字背书
      ↓
按部就班、逐年推进
```

**签字的这一刻，才算规划成立。** 在此之前，它只是一份建议书。

### 规划必须由技术部门牵头，但不能由技术部门独写

**这是最容易出错的地方。**

技术部门牵头是对的——因为技术部门是唯一能看到全局数据流向的角色。

但如果规划完全由技术部门闭门造车，一定失败。原因是：

- 技术部门不知道哪些数据对业务最重要
- 技术部门不知道业务部门愿意投入多少
- 业务部门不认账的规划，等于没有规划

**正确做法：技术部门搭框架，业务部门做填空，管理层做裁决。**

```
技术部门（Data COE）：出《数据治理规划框架》
   - 三大前置工程方案
   - 全企业系统清单和数据流向图
   - 主数据域划分建议
   - 平台架构和迭代路线
   - 分期优先级初排
        ↓
各业务部门：认领自己的责任
   - "我们部门的数据，我们来治"
   - 确认数据质量现状
   - 承诺投入资源
   - 提出本部门最痛的三个问题
        ↓
管理层/数据治理委员会：裁决
   - 优先级排序（有争议时拍板）
   - 资源分配
   - 规划终稿签字背书
```

**没有管理层签字的规划，执行率会低于30%。**

### 规划的三个常见坑

**坑一：规划写成"技术建设规划"**

最典型的症状：通篇讲平台要买什么、系统要建几个、技术架构怎么设计。

数据治理规划的主体不是技术方案，而是**业务治理路径**。平台只是承载手段。

**坑二：规划写成"理想蓝图"，没有分期**

一次性规划五年所有事情，看起来很有魄力，实际是"没有取舍"。

没有取舍的规划意味着：所有事情都重要、所有事情都要做、所有事情都做不好。

**一个检验标准：如果你的规划里没有"第4年才做"的項目，那它一定不是规划，是许愿。**

**坑三：规划做完就扔进抽屉**

规划写完，业务部门不认，年度计划不照着排，预算不按它来——等于没做。

**规划必须成为三件事的输入：年度部门计划、预算申请、项目立项排序。**

### 和主业工作的关系：规划先行，但不是规划全部

规划的作用是"对齐"，不是"包办"。

规划给出的是"三大前置工程 + 三年主线 + 每年重点 + 谁负责"，具体到某个治理域怎么治、选什么工具、怎么落地，那是实施阶段的事。

**不要用规划拖延启动，也不要用启动否定规划。**

正确的节奏是：

```
第1年：三大前置工程 + 规划 + 试点一条主线（验证方法论，暴露真问题）
第2年：规划 + 复制到第二三条主线（修正方法论，形成标准动作）
第3年：规划 + 沉淀为常态运营机制（从项目制转为运营制）
```

### 一句话总结

> **数据治理不是项目，是一场三年起步的战役。**
> **三大前置工程不齐，执行计划就是空中楼阁；**
> **执行计划不进战略规划，就是抽屉里的废纸；**
> **有规划的治理，每一年都在为下一年的加速铺路。**

### 本章小结

> 规划的价值不在于文档有多厚，而在于三年后回看时，每一年都知道自己在干什么。
> 先备齐组织（含Data COE）与技术平台迭代、摸清数据资产基线、建立治理与管理体系，再编制3~5年执行计划——顺序不能颠倒。
> 技术部门牵头搭框架，业务部门填空，管理层签字——三者缺一，规划就是废纸。
> 规划是给未来的自己留路标，不是给领导看的表演。


## 第三章 主数据二级分类模型：谁该管、谁不该管

### 传统主数据治理的问题

传统思路：把所有主数据列出来，用同一套方法治理。

问题：
- 主数据种类太多，边界模糊
- 不同主数据的业务价值完全不同
- 用同一套方法治理所有主数据，成本高、效率低
- 很多主数据都有系统在管了，还在重复建设

### 二级主数据分类模型

```
主数据
├── 一级主数据（强管控）
│   ├── 核心稳定、跨系统共享、变更不频繁
│   ├── 典型示例：
│   │   ├── 组织架构（公司、部门、分子公司）
│   │   ├── 人员主数据（员工编号、姓名、岗位）
│   │   ├── 银行账号
│   │   └── 税号
│   ├── 治理方式：平台统一管理
│   └── 特点：有明确的主数据管理委员会管控
│
└── 二级主数据（嵌入式）
    ├── 与业务系统深度绑定、随业务变化
    ├── 典型示例：
    │   ├── 产品分类（随市场变化）
    │   ├── 销售区域（随业务调整）
    │   ├── 客户分类（随业务战略调整）
    │   └── 物料分类（随产品变化）
    ├── 治理方式：嵌入业务系统功能，随系统一起管理
    └── 特点：不需要单独建平台，不单独治理
```

### 两级的核心区别

| 维度 | 一级主数据 | 二级主数据 |
|------|-----------|-----------|
| 稳定性 | 核心稳定，变更极少 | 随业务变化，变更频繁 |
| 共享范围 | 全集团跨系统共享 | 本业务系统内部使用 |
| 治理主体 | 数据治理委员会统一管控 | 业务部门自行管理 |
| 平台依赖 | 必须有主数据管理平台 | 不需要，可随业务系统管理 |
| 管理成本 | 高（集中管理） | 低（分布式管理） |
| 典型示例 | 组织/人员/银行账号/税号 | 产品分类/销售区域/客户细分 |

### 核心洞察

**二级主数据的真正价值不是"治理"，而是"嵌入业务系统功能设计"。**

传统思路：先建主数据平台，再谈应用
米悦说说思路：
- 一级主数据 → 平台统一管理（标准动作）
- 二级主数据 → 在业务系统设计时就把数据架构考虑进去

### 关键判断标准

如何判断一个主数据是"一级"还是"二级"？

```
问自己三个问题：

1. 这个数据会变吗？
   ├── 几乎不变（3年一动）→ 一级
   └── 经常变（半年一动）→ 二级

2. 全公司都用吗？
   ├── 跨多个业务系统共享 → 一级
   └── 本业务系统内部使用 → 二级

3. 变更影响大吗？
   ├── 影响核心业务流程 → 一级
   └── 只影响本部门业务 → 二级
```

### 核心金句

> 一级主数据靠平台，二级主数据靠嵌入。

> 二级主数据治理的最高境界，是让业务系统"忘记"主数据的概念——觉得数据就是功能的一部分。

## 第四章 治理模式选择：集中制、联邦制还是混合制

### 两种传统模式的问题

```
集中制（所有主数据统一到主数据平台管理）
├── 优点：标准统一、管控到位
└── 缺点：业务响应慢，平台审批链路长，容易阻塞业务

联邦制（各业务系统各自管理）
├── 优点：业务响应快
└── 缺点：标准难统一，数据质量参差不齐
```

### 现代企业的现实

在现代企业中，几乎所有主数据都有系统在管理了：

| 主数据类型 | 已有系统 |
|-----------|---------|
| 人员主数据 | HR系统（SAP SuccessFactors、Workday等） |
| 客户主数据 | CRM系统 |
| 供应商主数据 | SRM系统或ERP系统 |
| 物料主数据 | ERP系统 |
| 财务主数据 | 财务系统 |

**结论：在现代企业中，几乎没有"没有系统管理的主数据"了。**

### 混合制模式：现代企业的主流选择

```
混合制 = 源端治理 + 平台兜底

针对已有系统管理的主数据
└── 源端治理（首选方式）
    ├── 在数据源头进行治理
    ├── 业务系统负责维护和标准化
    ├── 主数据平台只做"分发"和"共享"
    └── 好处：快速响应业务变化，快速发现异常

针对没有系统管理的主数据
└── 才放到主数据平台进行统一管理
    └── 因为没有系统管，所以才需要平台管
```

### 为什么源端治理更好？

集中制的问题：
```
业务系统需要主数据
    ↓
向主数据平台申请
    ↓
平台审批确认
    ↓
数据标准化
    ↓
返回业务系统
    ↓
业务等待...（阻塞！）
```

源端治理的好处：
```
业务系统在数据产生时就完成治理
    ↓
数据变更实时生效
    ↓
异常快速发现
    ↓
平台只做分发，不做审批
    ↓
业务响应快，不阻塞
```

---

## 第五章 源端治理四步法

```
第一步：定标准
└── 在源头系统定义数据标准
└── 标准要嵌入业务流程，不是单独的审批流程

第二步：强执行
└── 源端系统强制执行数据校验
└── 不符合标准的数据进不去

第三步：快响应
└── 数据变更在源端实时生效
└── 不用等平台审批

第四步：平台只分发
└── 主数据平台负责数据分发和共享
└── 不是数据的"审批关卡"
```

---

## 第六章 主数据平台定位：核查+分发

### 主数据平台的两大核心定位

```
主数据平台
├── ① 标准的核查（质检站）
│   └── 数据质量把关
│   └── 不是审批数据的"生死簿"
│   └── 是数据进场的"质检关"
│
└── ② 数据的分发（高速公路）
    └── 把高质量数据快速送达各业务系统
    └── 是数据的"高速公路"
    └── 不是数据的"收费站"
```

### 常见误区

```
❌ 误区1：主数据平台是"数据仓库"
   └── 平台不是存储所有主数据的地方

❌ 误区2：主数据平台是"审批关卡"
   └── 所有数据都要平台审批才能用
   └── → 导致业务阻塞

❌ 误区3：主数据平台要"治理"所有数据
   └── 平台只管分发和质检
   └── 真正的治理在源端
```

### 核心金句

> 主数据平台 = 质检站 + 高速公路

> 平台不做数据的主人，只做数据的快递员。

---

## 第七章 数据治理的正确顺序：为什么HR主数据要优先

### 传统企业的通病

很多企业做数据治理的习惯顺序：
```
① 先治产品主数据
② 再治客户主数据
③ 最后治供应商主数据
```

**结果：治了半天，数据还是乱。因为忽略了最核心的东西。**

### 核心洞察：所有业务都落实到人和组织

```
产品 → 谁生产？谁销售？
客户 → 谁负责？谁维护？
供应商 → 谁采购？谁对接？
订单 → 谁审批？谁执行？
```

**产品、客户、供应商，最终都是"什么人、什么组织、什么岗位"在负责。**

### 数据治理的正确顺序

```
① HR主数据（最优先！）
   ├── 人员：员工编号、姓名、部门、岗位、汇报线
   ├── 组织：组织架构、分子公司、部门层级
   └── 原因：所有业务都落实到人和组织

② 产品主数据
   └── 谁生产、谁销售、谁负责

③ 客户主数据
   └── 谁负责、谁维护、谁跟进

④ 供应商主数据
   └── 谁采购、谁对接、谁审核
```

### 为什么HR主数据最难治理？

| 难点 | 说明 |
|------|------|
| 相对独立 | HR系统往往不受IT管辖 |
| 权力较大 | 核心部门，谁都得罪不起 |
| 数据敏感 | 人员信息涉及隐私 |
| 系统封闭 | SAP SuccessFactors、Workday等接口难开放 |

## 第八章 撬动HR主数据治理：从确权到建组织的路径

### 核心思路：先确权，后建组织

```
数据治理的第一步，不是技术，是"确权"

确权 = 确立数据管理部门对全公司数据管理的职责和权限

路径：
① 先出《数据管理办法》（一级概要性制度）
   └── 不用很细，是一级概要性制度
   └── 核心：确立数据管理部门的责权

② 再通过这个制度去组建治理组织
   └── 用制度作为"尚方宝剑"
```

### 《数据管理办法》核心内容

```
《数据管理办法》（一级制度）
├── 第一条：目的和依据
├── 第二条：适用范围
├── 第三条：数据管理的定义和原则
├── 第四条：数据管理部门的职责和权限  ← 核心！
│   ├── 有权制定数据标准
│   ├── 有权监督各业务域数据质量
│   ├── 有权协调跨部门数据问题
│   └── 有权考核各业务域数据治理成果
├── 第五条：各业务领域的职责
└── 附则：实施时间和解释权
```

### 两层组织架构

```
第一层：领导小组（决策层）
└── 公司高层高管：董事会/党委会/总经理办公会
└── 职责：重大事项决策、资源协调、重大问题裁决

第二层：数据管理办公室（执行层）
└── 可以是虚拟组织，也可以是实体组织
└── 职责：
    ├── 技术标准制定
    ├── 质量标准制定
    ├── 组织协调（跨部门数据问题）
    ├── 跟踪监督（各业务域执行情况）
    └── 评价考核（各业务域数据治理成果）

业务领域（执行层）
└── HR、产品、质量、营销、财务、供应链...
└── 根据企业实际灵活调整
```

### 撬动HR主数据治理路径

```
第一步：确权 → 出台《数据管理办法》
第二步：建组织 → 领导小组 + 数据管理办公室 + HR治理小组
第三步：定标准 → HR主数据标准
第四步：推执行 → 跟踪监督 + 评价考核
```

## 第八章补充：撬动HR主数据治理的完整路径（实战深化版）

> 本章为米悦说说实战经验补充，是第八章的深化内容

### HR主数据治理的组织体系

```
HR领域数据治理组织架构

├── HR领域数据治理小组
│   ├── 负责人：HR部门负责人
│   └── 执行人员：各HR子系统管理员
│
├── DC（Data Coordinator，数据协同和协作人）
│   ├── 一级DC：负责一级主数据的跨系统协调
│   └── 二级DC：负责二级主数据的日常协调
│   └── DC不是数据所有者，是数据流转中的协调节点
│
└── 核心职责：推动标准落地、协调质量问题、沟通业务需求
```

### 为什么入湖是前置工作？

```
传统做法（❌）：
先定义标准 → 再建平台 → 再分配责任
结果：标准落不了地，因为不知道现状

正确做法（✅）：
先入湖（所有HR系统数据）→ 分析现状 → 分清一级/二级 → 再定标准

好处：
- 不会把本该二级的主数据强加给HR管
- HR不会觉得数据治理是"被强加的任务"
- 责权清晰，落地容易
```

### 协商式治理

```
传统IT做法（❌）：
IT制定标准 → 强制HR执行 → HR不配合 → 推不动

米悦说说实践（✅）：
先入湖看现状 → 邀请HR一起分析 → HR说管不了就下沉为二级 → 共同认可才执行

核心：不是告诉HR"你该管什么"，是和HR一起"商量我们能管什么"
```

### 完整路径图

```
第一步：确权 → 《数据管理办法》
第二步：建组织 → 治理委员会 + HR小组 + DC（分一级/二级）
第三步：入湖（前置！）→ HR所有系统数据入湖
第四步：分析分类 → 入湖后识别一级/二级主数据
第五步：协商定标 → 与HR共同制定标准
第六步：执行考核 → DC推动 + 委员会监督
```

### 核心金句

> **入湖是撬动HR主数据治理的前置条件，不是技术工作，是治理方式变革的起点。**

> **协商式治理的核心是：不是告诉HR"你该管什么"，而是和HR一起"商量我们能管什么"。**

> **如果HR说管不了，那就不是一级主数据，是二级主数据，让它回归业务系统。**

## 第八章补充（续）：入湖问题处理与DO/DC职责分工

### 数据入湖问题处理流程

```
数据入湖发现问题
    ↓
所有问题统一反馈到一级主数据的DO（Data Owner）
    ↓
DO判断：是/否属于一级主数据？
    ├── 是 → 纳入一级主数据管理
    └── 否 → 下沉为二级主数据
            ↓
    二级主数据由DC（Data Coordinator）统一管理和确定
```

### DO vs DC：两个角色的核心区别

```
角色对比

├── DO（Data Owner，数据所有者）
│   ├── 定位：一级主数据的最终决策者
│   ├── 来源：通常是业务高管或核心部门负责人
│   ├── 核心职责：
│   │   ├── 确定哪些数据属于一级主数据
│   │   ├── 决策数据标准
│   │   ├── 审批跨系统数据共享
│   │   └── 接收入湖过程中发现的问题
│   └── 决策方式：判断"是否需要跨系统统一管理"
│
└── DC（Data Coordinator，数据协同和协作人）
    ├── 定位：二级主数据的日常管理者
    ├── 来源：各业务领域的数据接口人
    ├── 核心职责：
    │   ├── 管理本领域的二级主数据
    │   ├── 接收下沉来的二级主数据
    │   ├── 协调数据质量问题的整改
    │   └── 推动二级标准在业务系统中落地
    └── 工作方式：嵌入式，随业务系统一起管理
```

### 入湖问题处理的完整闭环

```
┌─────────────────────────────────────┐
│           数据入湖                    │
│  （HR所有系统数据接入数据湖）          │
└────────────────┬────────────────────┘
                 ↓
        ┌────────────────┐
        │  发现数据问题   │ ← 口径不一致/缺失/错误/重复
        └───────┬────────┘
                ↓
        ┌────────────────────────┐
        │  反馈到一级主数据DO      │
        │  （数据所有者）          │
        └───────────┬────────────┘
                    ↓
            DO判断决策
           /                      / 一级主数据     \ 二级主数据
        /                  ┌───────↓────────┐  ┌───────↓────────┐
│  纳入一级管理    │  │  下沉为二级      │
│  统一标准       │  │  由DC承接       │
│  平台分发       │  │  嵌入业务系统    │
└────────────────┘  └───────▲────────┘
                           │
                      DC负责日常管理
                      确定标准落地
                      协调质量问题
```

### 核心金句

> **DO是"裁判员"，决定哪些数据该管；DC是"运动员"，负责把该管的数据管好。**

> **入湖发现问题不是终点，是DO和DC协同工作的起点。**

## 第九章：经营指标推动法——用指标体系驱动数据治理

### 传统数据治理的困境

```
问题：不知道哪些数据需要治理，哪些不需要

传统做法：
├── 列出一堆主数据目录
├── 建一套数据标准
├── 上一个数据平台
└── 结果：治理了但没人用，价值看不见

核心痛点：
└── 数据治理的成果怎么体现？
└── 业务部门说"我用不上"
└── 领导说"花了这么多钱，有什么用？"
```

### 经营指标推动法的核心思想

```
核心思想：用高价值场景驱动数据治理

思路转变：
├── 不是"先治理，再想怎么用"
├── 而是"先确定要什么指标，再倒推需要治理什么数据"
└── 从"供给驱动"变成"需求驱动"
```

### 三级指标管理体系

```
指标体系三级架构

├── 集团级指标（最先做！）
│   ├── 定义：集团层面关心的核心经营指标
│   ├── 示例：
│   │   ├── 经营指标（营收、利润、现金流）
│   │   ├── 发货指标（发货量、发货及时率）
│   │   ├── 营销指标（销售额、市场占有率）
│   │   └── 采购成本指标（采购金额、供应商准时率）
│   ├── 特点：数量少（10-20个），价值高，全集团通用
│   └── 谁定：集团战略部门/数据治理委员会
│
├── 公司级指标
│   ├── 定义：各分子公司根据集团指标拆解
│   ├── 特点：承接集团指标，结合本公司业务
│   └── 谁定：各公司数据管理部门
│
└── 部门级指标
    ├── 定义：各部门根据公司指标分解
    ├── 特点：落实到具体业务操作
    └── 谁定：各部门数据接口人/DC
```

### 经营指标推动法的实操路径

```
Step 1：确定集团级指标
├── 集团战略部门牵头
├── 确定集团最关心的10-20个核心经营指标
├── 这些指标必须能回答：
│   ├── 集团今年的经营目标是什么？
│   ├── 各BU的业绩怎么衡量？
│   └── 哪些数据是集团决策必须的？
└── 输出：《集团级指标清单》

Step 2：倒推数据源
├── 每个指标需要哪些源数据？
├── 例如：
│   ├── "发货量"指标
│   │   └── 需要：OMS系统发货记录
│   ├── "采购成本"指标
│   │   └── 需要：SRM系统采购订单数据
│   └── "营收"指标
│       └── 需要：财务系统收入数据
└── 输出：《指标-数据源映射表》

Step 3：评估数据源现状
├── 数据源有没有？
├── 数据质量怎么样？
├── 能不能自动获取？
└── 输出：《数据源成熟度评估报告》

Step 4：缺口就是治理机会
├── 有数据源但质量差 → 治理这个数据
├── 有数据源但没打通 → 治理这个系统
├── 没有数据源 → 发现新治理需求
└── 10个指标 → 可能发现3-5个数据治理机会

Step 5：用指标价值推动治理
├── "这个指标是集团领导关心的"
├── "这个指标现在算不出来，因为XX数据不准"
├── "治理了XX数据，这个指标就能看准了"
└── 用指标的价值，倒逼业务部门配合数据治理
```

### 关键洞察：从"供给驱动"到"需求驱动"

```
传统数据治理（供给驱动）：
┌──────────────┐
│  建平台      │
│  定标准      │
│  管数据      │
└──────┬───────┘
       ↓
   治理了一堆数据
       ↓
   不知道给谁用
       ↓
   没人用，没价值

经营指标推动法（需求驱动）：
┌──────────────┐
│  确定指标     │ ← 集团关心的
└──────┬───────┘
       ↓
   倒推需要什么数据
       ↓
   发现数据缺口
       ↓
   缺口就是治理机会
       ↓
   治理能直接产生价值
```

### 完整路径：从指标到治理

```
集团确定指标
     ↓
指标需要什么数据？
     ↓
数据在哪里？
     ↓
有没有数据源？
   /           有          没有
   ↓           ↓
 质量行不行？   发现新需求
   ↓           ↓
  差 → 治理    作为新治理机会
     ↓
 治理后指标能看
     ↓
 指标产生价值
     ↓
 证明数据治理有价值
     ↓
 推动更大范围治理
```

### 核心金句

> **经营指标推动法的本质：从"我有什么数据"变成"我需要什么指标"。**

> **用指标的价值，倒逼数据治理的落地。**

> **数据治理不是目的，通过指标体系让数据产生业务价值才是目的。**

> **10个核心指标，可能驱动50个数据治理需求，这就是杠杆效应。**

```

第二章 数据治理规划        → 三大前置工程 + 3~5年执行计划 ← 新增
第三章 二级分类模型        → 明确谁管、怎么管
第四章 治理模式            → 混合制、源端治理
第五章 源端治理四步法      → 定标准→强执行→快响应→平台分发
第六章 平台定位            → 核查+分发，不是审批关卡
第七章 治理顺序            → 先HR主数据

```

## 第九章补充：聚焦重点 + 长期滚动迭代

### 为什么必须"选择重点"？

```
数据治理不能面面俱到

原因：
├── 资源有限：IT/数据团队人不多
├── 精力有限：不能同时推10个方向
├── 政治有限：各业务部门都有自己的优先级
└── 信任有限：数据治理刚起步，不能贪多

面面俱到的结果：
├── 10个方向同时推
├── 每个都推不动
├── 业务部门觉得"又来搞事情"
└── 数据治理失去信任，以后推什么都难
```

### 为什么从"一把手最关注的点"开始？

```
选择重点的两个标准：

标准1：集团一把手最关注的
├── 一把手关注 → 资源好协调
├── 一把手关注 → 政治阻力小
├── 一把手关注 → 成功了影响力大
└── 一把手关注 → 能快速证明价值

标准2：当前企业最痛的方向
├── 哪个业务问题最突出？
├── 哪个数据问题投诉最多？
├── 哪个指标的缺口最影响决策？
└── 从最痛的点切入

示例：
├── 营销指标不准 → 先从营销数据治理开始
├── 财务数据不一致 → 先从财务主数据开始
├── 库存账实不符 → 先从库存数据开始
```

### "同一优先级排序"是什么意思？

```
不能把面铺得太广

错误做法（❌）：
├── 营销数据要治理
├── 财务数据要治理
├── HR数据要治理
├── 采购数据要治理
└── 同时推4个方向，每个都很慢

正确做法（✅）：
├── 营销数据最重要 → 先推营销
├── 其他等营销做出成果再说
└── 集中资源打透一个点

本质：
└── 在同一个优先级排序上做事
└── 不是"这个也重要、那个也重要"
└── 而是"这个最重要，先做这个"
```

### 数据治理是长期滚动、不断迭代的过程

```
关键认知：数据治理没有终点

❌ 错误理解：
└── "数据治理做完就结束了"
└── "建好平台就完事了"

✅ 正确理解：
└── 数据治理是一个持续的过程
└── 制度治理会一直在做
└── 每年/每季度选择一个新的重点方向

长期滚动模式：
```
┌─────────────────────────┐
│  第一阶段：聚焦一个方向    │ ← 如：营销主数据
│  做出成果，证明价值        │
│  建立信任                │
└────────┬────────────────┘
         ↓
┌─────────────────────────┐
│  第二阶段：扩展到第二个方向 │ ← 如：财务主数据
│  借用第一阶段的成功经验    │
│  继续做出成果            │
└────────┬────────────────┘
         ↓
┌─────────────────────────┐
│  第三阶段：继续扩展       │ ← 如：HR主数据
│  ...以此类推            │
└────────┬────────────────┘
         ↓
    长期滚动迭代
    每阶段都聚焦、都出成果
```

### 聚焦打透的核心原则

```
一个时间周期（建议一季度）只聚焦一个方向

选方向的标准：
1. 一把手最关注的
2. 当前企业最痛的
3. 能快速出成果的
4. 成功后影响力大的

执行原则：
├── 集中70%资源在重点方向
├── 留30%资源处理日常事务
├── 做出成果再扩展
└── 切忌"同时推很多个，都做不出成果"
```

### 核心金句

> **数据治理不能贪多，贪多嚼不烂，还失去信任。**

> **从一把手最关注的点切入，成功了就是最好的背书。**

> **聚焦一个方向，做出成果，建立信任，再扩展下一个。**

> **数据治理是长期滚动迭代的过程，不是一锤子买卖。**

## 第十章 实战案例：某药企数据治理项目复盘

> 注：以下案例来自真实企业，已做脱敏处理

- **时间线**：
  - 2023：平台采购与试点落地（大数据平台、数据治理平台、BI平台）

  - 2025：组织建立与业务赋能

- **数据资产**：22套业务系统 / 6.5TB / 34.4亿条记录
- **制度建设**：11项已发布制度

### 三大痛点

**痛点01：报表层级错位，高层获得感不足**
- 现有报表缺高层全局视图
- 管理者需手动整理信息，难快速掌握业务全貌

**痛点02：指标口径不一致，跨模块比对困难**
- 指标定义与计算逻辑不统一
- 例如：库存，生产关注数量，财务关注金额

**痛点03：数据治理"有框架、无落地"**
- 有制度但执行不到位

### 项目组织（已脱敏）

- **项目领导小组组长**：某高管
- **副组长**：若干高管
- **项目经理**：项目负责人
- **项目PMO**：PMO负责人

### 解决方案：三驾马车战略

```
战略决策层：高层挂帅，拍板口径、调配资源
业务执行层：每个指标有明确Owner，负责定义与解释
技术支持层：负责技术落地
```

## 第十一章 数据治理的10条实战军规

```
1. 数据治理的本质是治责任，不是治数据
2. 一级主数据靠平台，二级主数据靠嵌入
3. 主数据平台是质检站+高速公路，不是审批关卡
4. 能通过业务系统管理的，就不要搬到主数据平台
5. 数据治理的第一步是确权，不是买平台
6. HR主数据是一切数据治理的锚点
7. 源端治理的本质是让数据在产生的地方就被管好
8. 业务响应速度是检验数据治理成效的核心指标
9. 没有考核的数据治理都是耍流氓
10. 数据治理是长期工程，先易后难，先核心后外围
```
