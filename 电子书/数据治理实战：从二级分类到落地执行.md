## 第一章 数据治理的本质：不是治数据，是治责任

### 很多企业做数据治理都搞错了方向

常见做法：
- 买一套数据治理平台
- 建一个主数据管理系统
- 招聘一批数据治理工程师
- 制定一堆数据标准文档

结果：平台买了没人用，系统建了没人管，标准定了没人执行。

### 问题的根源

数据治理的本质是**治责任**，不是治数据。

```
数据治理 = 让每一笔数据都能找到责任人

找不到责任人的数据 = 没人管的数据 = 乱数据
能找到责任人的数据 = 有人管的数据 = 好数据
```

### 一个简单的测试

问：你们公司的"客户"数据，谁负责？

A. 没人负责（CRM算吗？销售算吗？）
B. 数据部门负责（他们管得了业务吗？）
C. 业务部门负责（哪个业务部门？）
D. 有明确的部门和岗位负责（恭喜你，做对了）

如果你选了A/B/C，说明你们的数据治理还没入门。

### 治数据的三个层次

```
第一层：技术治数
└── 建平台、定标准、管数据
└── 大多数企业的做法

第二层：流程治数
└── 定流程、分责任、立考核
└── 少数企业的做法

第三层：责任治数（最高境界）
└── 每一笔数据都有明确的责任人
└── 数据是业务的一部分，不是独立的"治理对象"
└── 极少数企业的做法
```

### 本章小结

> 数据治理的核心不是技术，是责任。
> 没有责任心的技术方案，都是在浪费钱。
> 没有责任心的数据标准，都是废纸。

## 第二章 主数据二级分类模型：谁该管、谁不该管

### 传统主数据治理的问题

传统思路：把所有主数据列出来，用同一套方法治理。

问题：
- 主数据种类太多，边界模糊
- 不同主数据的业务价值完全不同
- 用同一套方法治理所有主数据，成本高、效率低
- 很多主数据都有系统在管了，还在重复建设

### 二级主数据分类模型

```
主数据
├── 一级主数据（强管控）
│   ├── 核心稳定、跨系统共享、变更不频繁
│   ├── 典型示例：
│   │   ├── 组织架构（公司、部门、分子公司）
│   │   ├── 人员主数据（员工编号、姓名、岗位）
│   │   ├── 银行账号
│   │   └── 税号
│   ├── 治理方式：平台统一管理
│   └── 特点：有明确的主数据管理委员会管控
│
└── 二级主数据（嵌入式）
    ├── 与业务系统深度绑定、随业务变化
    ├── 典型示例：
    │   ├── 产品分类（随市场变化）
    │   ├── 销售区域（随业务调整）
    │   ├── 客户分类（随业务战略调整）
    │   └── 物料分类（随产品变化）
    ├── 治理方式：嵌入业务系统功能，随系统一起管理
    └── 特点：不需要单独建平台，不单独治理
```

### 两级的核心区别

| 维度 | 一级主数据 | 二级主数据 |
|------|-----------|-----------|
| 稳定性 | 核心稳定，变更极少 | 随业务变化，变更频繁 |
| 共享范围 | 全集团跨系统共享 | 本业务系统内部使用 |
| 治理主体 | 数据治理委员会统一管控 | 业务部门自行管理 |
| 平台依赖 | 必须有主数据管理平台 | 不需要，可随业务系统管理 |
| 管理成本 | 高（集中管理） | 低（分布式管理） |
| 典型示例 | 组织/人员/银行账号/税号 | 产品分类/销售区域/客户细分 |

### 核心洞察

**二级主数据的真正价值不是"治理"，而是"嵌入业务系统功能设计"。**

传统思路：先建主数据平台，再谈应用
老周思路：
- 一级主数据 → 平台统一管理（标准动作）
- 二级主数据 → 在业务系统设计时就把数据架构考虑进去

### 关键判断标准

如何判断一个主数据是"一级"还是"二级"？

```
问自己三个问题：

1. 这个数据会变吗？
   ├── 几乎不变（3年一动）→ 一级
   └── 经常变（半年一动）→ 二级

2. 全公司都用吗？
   ├── 跨多个业务系统共享 → 一级
   └── 本业务系统内部使用 → 二级

3. 变更影响大吗？
   ├── 影响核心业务流程 → 一级
   └── 只影响本部门业务 → 二级
```

### 核心金句

> 一级主数据靠平台，二级主数据靠嵌入。

> 二级主数据治理的最高境界，是让业务系统"忘记"主数据的概念——觉得数据就是功能的一部分。

## 第三章 治理模式选择：集中制、联邦制还是混合制

### 两种传统模式的问题

```
集中制（所有主数据统一到主数据平台管理）
├── 优点：标准统一、管控到位
└── 缺点：业务响应慢，平台审批链路长，容易阻塞业务

联邦制（各业务系统各自管理）
├── 优点：业务响应快
└── 缺点：标准难统一，数据质量参差不齐
```

### 现代企业的现实

在现代企业中，几乎所有主数据都有系统在管理了：

| 主数据类型 | 已有系统 |
|-----------|---------|
| 人员主数据 | HR系统（SAP SuccessFactors、Workday等） |
| 客户主数据 | CRM系统 |
| 供应商主数据 | SRM系统或ERP系统 |
| 物料主数据 | ERP系统 |
| 财务主数据 | 财务系统 |

**结论：在现代企业中，几乎没有"没有系统管理的主数据"了。**

### 混合制模式：现代企业的主流选择

```
混合制 = 源端治理 + 平台兜底

针对已有系统管理的主数据
└── 源端治理（首选方式）
    ├── 在数据源头进行治理
    ├── 业务系统负责维护和标准化
    ├── 主数据平台只做"分发"和"共享"
    └── 好处：快速响应业务变化，快速发现异常

针对没有系统管理的主数据
└── 才放到主数据平台进行统一管理
    └── 因为没有系统管，所以才需要平台管
```

### 为什么源端治理更好？

集中制的问题：
```
业务系统需要主数据
    ↓
向主数据平台申请
    ↓
平台审批确认
    ↓
数据标准化
    ↓
返回业务系统
    ↓
业务等待...（阻塞！）
```

源端治理的好处：
```
业务系统在数据产生时就完成治理
    ↓
数据变更实时生效
    ↓
异常快速发现
    ↓
平台只做分发，不做审批
    ↓
业务响应快，不阻塞
```

## 第四章 源端治理四步法

```
第一步：定标准
└── 在源头系统定义数据标准
└── 标准要嵌入业务流程，不是单独的审批流程

第二步：强执行
└── 源端系统强制执行数据校验
└── 不符合标准的数据进不去

第三步：快响应
└── 数据变更在源端实时生效
└── 不用等平台审批

第四步：平台只分发
└── 主数据平台负责数据分发和共享
└── 不是数据的"审批关卡"
```

## 第五章 主数据平台定位：核查+分发

### 主数据平台的两大核心定位

```
主数据平台
├── ① 标准的核查（质检站）
│   └── 数据质量把关
│   └── 不是审批数据的"生死簿"
│   └── 是数据进场的"质检关"
│
└── ② 数据的分发（高速公路）
    └── 把高质量数据快速送达各业务系统
    └── 是数据的"高速公路"
    └── 不是数据的"收费站"
```

### 常见误区

```
❌ 误区1：主数据平台是"数据仓库"
   └── 平台不是存储所有主数据的地方

❌ 误区2：主数据平台是"审批关卡"
   └── 所有数据都要平台审批才能用
   └── → 导致业务阻塞

❌ 误区3：主数据平台要"治理"所有数据
   └── 平台只管分发和质检
   └── 真正的治理在源端
```

### 核心金句

> 主数据平台 = 质检站 + 高速公路

> 平台不做数据的主人，只做数据的快递员。

## 第六章 数据治理的正确顺序：为什么HR主数据要优先

### 传统企业的通病

很多企业做数据治理的习惯顺序：
```
① 先治产品主数据
② 再治客户主数据
③ 最后治供应商主数据
```

**结果：治了半天，数据还是乱。因为忽略了最核心的东西。**

### 核心洞察：所有业务都落实到人和组织

```
产品 → 谁生产？谁销售？
客户 → 谁负责？谁维护？
供应商 → 谁采购？谁对接？
订单 → 谁审批？谁执行？
```

**产品、客户、供应商，最终都是"什么人、什么组织、什么岗位"在负责。**

### 数据治理的正确顺序

```
① HR主数据（最优先！）
   ├── 人员：员工编号、姓名、部门、岗位、汇报线
   ├── 组织：组织架构、分子公司、部门层级
   └── 原因：所有业务都落实到人和组织

② 产品主数据
   └── 谁生产、谁销售、谁负责

③ 客户主数据
   └── 谁负责、谁维护、谁跟进

④ 供应商主数据
   └── 谁采购、谁对接、谁审核
```

### 为什么HR主数据最难治理？

| 难点 | 说明 |
|------|------|
| 相对独立 | HR系统往往不受IT管辖 |
| 权力较大 | 核心部门，谁都得罪不起 |
| 数据敏感 | 人员信息涉及隐私 |
| 系统封闭 | SAP SuccessFactors、Workday等接口难开放 |

## 第七章 撬动HR主数据治理：从确权到建组织的路径

### 核心思路：先确权，后建组织

```
数据治理的第一步，不是技术，是"确权"

确权 = 确立数据管理部门对全公司数据管理的职责和权限

路径：
① 先出《数据管理办法》（一级概要性制度）
   └── 不用很细，是一级概要性制度
   └── 核心：确立数据管理部门的责权

② 再通过这个制度去组建治理组织
   └── 用制度作为"尚方宝剑"
```

### 《数据管理办法》核心内容

```
《数据管理办法》（一级制度）
├── 第一条：目的和依据
├── 第二条：适用范围
├── 第三条：数据管理的定义和原则
├── 第四条：数据管理部门的职责和权限  ← 核心！
│   ├── 有权制定数据标准
│   ├── 有权监督各业务域数据质量
│   ├── 有权协调跨部门数据问题
│   └── 有权考核各业务域数据治理成果
├── 第五条：各业务领域的职责
└── 附则：实施时间和解释权
```

### 两层组织架构

```
第一层：领导小组（决策层）
└── 公司高层高管：董事会/党委会/总经理办公会
└── 职责：重大事项决策、资源协调、重大问题裁决

第二层：数据管理办公室（执行层）
└── 可以是虚拟组织，也可以是实体组织
└── 职责：
    ├── 技术标准制定
    ├── 质量标准制定
    ├── 组织协调（跨部门数据问题）
    ├── 跟踪监督（各业务域执行情况）
    └── 评价考核（各业务域数据治理成果）

业务领域（执行层）
└── HR、产品、质量、营销、财务、供应链...
└── 根据企业实际灵活调整
```

### 撬动HR主数据治理路径

```
第一步：确权 → 出台《数据管理办法》
第二步：建组织 → 领导小组 + 数据管理办公室 + HR治理小组
第三步：定标准 → HR主数据标准
第四步：推执行 → 跟踪监督 + 评价考核
```

## 第九章 实战案例：昆药集团数据治理项目复盘

### 项目背景

- **时间线**：
  - 2023：平台采购与试点落地（联想大数据平台、数据治理平台、帆软BI）
  - 2024：部门级需求数据入湖与团队能力沉淀
  - 2025：组织建立与业务赋能

- **数据资产**：22套业务系统 / 6.5TB / 34.4亿条记录
- **制度建设**：11项已发布制度

### 数据成熟度评估结果

| 评估项 | 当前水平 | 建议 |
|--------|---------|------|
| 企业数据管理文化 | 萌芽阶段 | 增加培训，从"汗水驱动"迈向"智慧驱动" |
| 数据战略 | 初始级 | 建立数据战略决策组织 |
| 数据治理 | 初始级 | 成立数据治理委员会 |

### 三大痛点

**痛点01：报表层级错位，高层获得感不足**
- 现有报表缺高层全局视图
- 管理者需手动整理信息，难快速掌握业务全貌

**痛点02：指标口径不一致，跨模块比对困难**
- 指标定义与计算逻辑不统一
- 例如：库存，生产关注数量，财务关注金额

**痛点03：数据治理"有框架、无落地"**
- 有制度但执行不到位

### 项目组织

- **项目领导小组组长**：钟江
- **副组长**：孟丽、孙志强、韩玉林、孙成、梁化成、黄元红
- **项目经理**：许睿
- **项目PMO**：周泓武

### 解决方案：三驾马车战略

```
战略决策层：高层挂帅，拍板口径、调配资源
业务执行层：每个指标有明确Owner，负责定义与解释
技术支持层：负责技术落地
```

## 第十章 数据治理的10条实战军规

```
1. 数据治理的本质是治责任，不是治数据
2. 一级主数据靠平台，二级主数据靠嵌入
3. 主数据平台是质检站+高速公路，不是审批关卡
4. 能通过业务系统管理的，就不要搬到主数据平台
5. 数据治理的第一步是确权，不是买平台
6. HR主数据是一切数据治理的锚点
7. 源端治理的本质是让数据在产生的地方就被管好
8. 业务响应速度是检验数据治理成效的核心指标
9. 没有考核的数据治理都是耍流氓
10. 数据治理是长期工程，先易后难，先核心后外围
```
