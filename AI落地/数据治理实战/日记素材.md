## 日记1：数据治理——先内后外，顺序不能颠倒

**标签**：[[数据治理]] [[方法论]] [[CIO]] [[企业数字化]]

### 核心观点

很多公司都有数字化部门，CIO 请咨询公司来做方案然后上系统实施。
这个思路是对的，但也不完全正确。

### 为什么这样说？

**第三方咨询的角色应该是辅助，而不是主导。**

正确路径：
```
第一步：公司内部先做好三件事
    ├── 情况摸底（数据现状是什么）
    ├── 目标确定（数据治理要解决什么问题）
    └── 责权明确（谁负责、谁推动、谁考核）

第二步：成立数据组织
    └── 建立公司一级的数据治理委员会或专项小组

第三步：制定公司一级数据管理制度
    └── 明确数据标准、数据质量要求、数据安全规范

第四步：有了人和权之后
    └── 再请第三方咨询进来，配合实施
```

### 常见错误顺序

1. 先请咨询公司出方案
2. 方案做完才发现没有组织保障
3. 没有数据委员会，没有数据管理制度
4. 咨询公司走了，系统推不动

**结果：** 花了钱，没有效果。

### 关键原则

> 咨询公司是来帮你做技术方案和实施支持的，不是来帮你做组织保障的。
> 组织保障必须是自己公司的事情，必须先于咨询介入。

**先有人、有权、有制度 → 后有咨询、有系统、有工具**

核心原则：**先组织后技术，先治理后系统。**

## 日记2：数据治理重要的是管理体系而不是工具

**标签**：[[数据治理]] [[方法论]] [[工具误区]]

### 核心观点

就算没有数据治理平台，通过单纯数据库系统的各类功能也可以做治理。

### 常见误区

很多企业做数据治理，第一件事就是买平台。
**结果：** 平台上了没人用，制度没有，系统推不动。把工具当成解药。

### 没有平台也能做治理

| 治理动作 | 工具方法 |
|---------|---------|
| 数据标准定义 | 数据库字段命名规范 + CHECK约束 |
| 数据质量检查 | SQL定期查询 + 自动化脚本 |
| 数据安全 | 数据库用户权限管理 + 审计日志 |
| 主数据管理 | 数据库分区 + 唯一索引约束 |
| 数据血缘 | ER图 + 文档记录 |
| 数据资产盘点 | 数据库字典 + 定期巡检 |

**本质：制度和流程到位了，工具只是锦上添花。**

### 正确优先级

```
第一步：建立数据管理制度（人）
第二步：明确数据Owner职责（权）
第三步：制定数据标准规范（法）
第四步：选型数据治理工具（器）
```

**器最后。**

### 金句

> 好的数据治理不需要平台，需要的是对的人、对的制度、对的方法。

## 老周实战洞察：主数据治理的二级分类模型（重要创新）

**日期**：2026-10-15
**标签**：#数据治理 #主数据 #创新模型 #实战方法论

---

### 传统主数据治理的问题

传统的思路是：先把所有主数据列出来，然后统一治理。

**但实际问题是：**
- 主数据种类太多，边界模糊
- 不同主数据的业务价值完全不同
- 用同一套方法治理所有主数据，成本高、效率低

### 老周提出的二级主数据分类

```
主数据
├── 一级主数据（强管控）
│   └── 核心稳定、跨系统共享、变更不频繁
│   └── 例：组织架构、人员、银行账号、税号
│   └── 治理方式：委员会治理 + 平台管控
│
└── 二级主数据（嵌入式）
    └── 与业务系统深度绑定、随业务变化
    └── 例：产品分类、销售区域、客户分类
    └── 治理方式：嵌入业务系统功能，随系统一起管理
```

### 两级的核心区别

| 维度 | 一级主数据 | 二级主数据 |
|------|-----------|-----------|
| 稳定性 | 核心稳定，变更极少 | 随业务变化，变更频繁 |
| 共享范围 | 全集团跨系统共享 | 本业务系统内部使用 |
| 治理主体 | 数据治理委员会统一管控 | 业务部门自行管理 |
| 平台依赖 | 必须有主数据管理平台 | 不需要，可随业务系统管理 |
| 典型示例 | 组织架构、人员、税号、银行账号 | 产品分类、销售区域、客户细分 |
| 管理难度 | 低（系统化管理即可）| 高（需要嵌入业务流程）|

### 关键洞察

**二级主数据的真正价值不是"治理"，而是"嵌入业务系统功能设计"。**

传统思路：先建主数据平台，再谈应用

老周思路：
- 一级主数据 → 平台统一管理（标准动作）
- 二级主数据 → 在业务系统设计时就把数据架构考虑进去

### 实操建议

**一级主数据治理（传统做法）：**
```
1. 建立主数据管理委员会
2. 制定数据标准
3. 上主数据管理平台
4. 统一分发
```

**二级主数据治理（新思路）：**
```
1. 在业务系统设计阶段就做数据建模
2. 数据标准嵌入系统功能
3. 随业务系统一起维护
4. 不单独建平台，不单独治理
```

### 核心金句

> **一级主数据靠平台，二级主数据靠嵌入。**
> **二级主数据治理的最高境界，是让业务系统"忘记"主数据的概念，觉得数据就是功能的一部分。**

### 价值

这个模型的价值在于：
- 降低了主数据治理的复杂度
- 明确了不同主数据用不同的治理方法
- 节省了大量建平台的钱
- 更符合实际业务场景

## 老周实战洞察：主数据治理的混合制模式——源端治理优先

**日期**：2026-10-15
**标签**：#数据治理 #主数据 #混合制 #源端治理 #集中式vs联邦制

---

### 传统主数据治理的两种模式

```
传统模式
├── 集中制
│   └── 所有主数据统一到主数据平台管理
│   └── 优点：标准统一、管控到位
│   └── 缺点：业务响应慢，平台审批链路长，容易阻塞业务
│
└── 联邦制
    └── 各业务系统各自管理，主数据平台只做共享协调
    └── 优点：业务响应快
    └── 缺点：标准难统一，数据质量参差不齐
```

### 现代企业的现实情况

在现代企业中，几乎所有主数据都有系统在管理了：

| 主数据类型 | 已有系统 |
|-----------|---------|
| 人员主数据 | HR系统 |
| 客户主数据 | CRM系统 |
| 供应商主数据 | ERP系统 |
| 物料主数据 | ERP系统 |
| 财务主数据 | 财务系统 |

**结论：在现代企业中，几乎没有"没有系统管理的主数据"了。**

### 老周提出的混合制模式

```
混合制 = 源端治理 + 平台兜底

针对已有系统管理的主数据
└── 源端治理（首选方式）
    ├── 在数据源头进行治理
    ├── 业务系统负责维护和标准化
    ├── 主数据平台只做"分发"和"共享"
    └── 好处：快速响应业务变化，快速发现异常

针对没有系统管理的主数据
└── 才放到主数据平台进行统一管理
    └── 因为没有系统管，所以才需要平台管
```

### 核心洞察：为什么源端治理更好？

**集中制的问题：**
```
业务系统需要主数据
    ↓
向主数据平台申请
    ↓
平台审批确认
    ↓
数据标准化
    ↓
返回业务系统
    ↓
业务等待...（阻塞！）
```

**源端治理的好处：**
```
业务系统在数据产生时就完成治理
    ↓
数据变更实时生效
    ↓
异常快速发现
    ↓
平台只做分发，不做审批
    ↓
业务响应快，不阻塞
```

### 源端治理的具体做法

**源端治理四步法：**

```
1. 定标准
   └── 在源头系统定义数据标准
   └── 标准要嵌入业务流程，不是单独的审批流程

2. 强执行
   └── 源端系统强制执行数据校验
   └── 不符合标准的数据进不去

3. 快响应
   └── 数据变更在源端实时生效
   └── 不用等平台审批

4. 平台只分发
   └── 主数据平台负责数据分发和共享
   └── 不是数据的"审批关卡"
```

### 两个模型的关联

老周的两个模型是互补的：

| 模型 | 分类维度 | 治理方式 |
|------|---------|---------|
| **二级分类模型** | 主数据的重要程度 | 一级靠平台，二级靠嵌入 |
| **混合制模型** | 是否有源系统 | 有系统→源端治理，无系统→平台管理 |

**两个模型的核心逻辑一致：**
> **能通过业务系统管理的，就不要搬到主数据平台。主数据平台应该是"分发通道"，不是"审批关卡"。**

### 核心金句

> **源端治理的本质是"让数据在产生的地方就被管好"，而不是"把所有数据集中到平台再管"。**

> **主数据平台的最佳定位是"高速公路"（分发），而不是"收费站"（审批）。**

## 老周实战洞察：主数据平台的两大核心定位——"核查"与"分发"

**日期**：2026-10-15
**标签**：#数据治理 #主数据平台 #平台定位 #核心职责

---

### 主数据平台的两大核心定位

```
主数据平台
├── ① 标准的核查
│   └── 数据质量把关
│   └── 标准是否符合规范
│   └── 不是审批数据的"生死簿"
│   └── 是数据进场的"质检关"
│
└── ② 数据的分发
    └── 把高质量数据快速送达各业务系统
    └── 是数据的"高速公路"
    └── 不是数据的"收费站"
```

### 核查 vs 分发

| 职责 | 核查（质检） | 分发（通道） |
|------|------------|-------------|
| 定位 | 数据质量的守门人 | 数据流通的通道 |
| 动作 | 检查标准合规性 | 快速传递数据 |
| 速度 | 可以稍慢（质检需要时间）| 必须快（通道不能堵） |
| 视角 | 事后/事中检查 | 实时同步 |
| 关键 | 查出问题要能快速反馈源头修正 | 通路畅、延迟低、不丢失 |

### 常见误区

```
❌ 误区1：主数据平台是"数据仓库"
   └── 平台不是存储所有主数据的地方

❌ 误区2：主数据平台是"审批关卡"
   └── 所有数据都要平台审批才能用
   └── → 导致业务阻塞

❌ 误区3：主数据平台要"治理"所有数据
   └── 平台只管分发和质检
   └── 真正的治理在源端
```

### 正确理解

```
主数据平台 = 质检站 + 高速公路

质检站（核查）
└── 进来的数据是否符合标准
└── 符合 → 放行进入分发
└── 不符合 → 打回源端修正
└── 不是卡死，是反馈修正

高速公路（分发）
└── 数据从源端到各业务系统的快速通道
└── 平台只做传递，不做存储
└── 速度快、延迟低、不丢包
```

### 核心金句

> **主数据平台 = 质检站 + 高速公路**
>
> **质检站负责"核查"（数据质量把关），高速公路负责"分发"（数据快速送达）。**
>
> **平台不做数据的主人，只做数据的快递员。**

## 老周实战洞察：数据治理的顺序——先治理HR主数据

**日期**：2026-10-15
**标签**：#数据治理 #数据治理顺序 #HR主数据 #人员组织 #实战方法论

---

### 传统企业的通病：从产品/客户/供应商开始

很多企业做数据治理的习惯顺序：
```
① 先治产品主数据
② 再治客户主数据
③ 最后治供应商主数据
```

**结果：治了半天，数据还是乱。因为忽略了最核心的东西。**

### 核心洞察：所有业务都落实到人和组织

```
产品 → 谁生产？谁销售？
客户 → 谁负责？谁维护？
供应商 → 谁采购？谁对接？
订单 → 谁审批？谁执行？
```

**产品、客户、供应商，最终都是"什么人、什么组织、什么岗位"在负责。**

### 数据治理的正确顺序：先HR主数据

```
数据治理的正确顺序
│
├── ① HR主数据（人员和组织）【最优先！】
│   └── 人员：员工编号、姓名、部门、岗位、汇报线
│   └── 组织：组织架构、分子公司、部门层级
│   └── 原因：所有业务都落实到人和组织
│
├── ② 产品主数据
│   └── 谁生产、谁销售、谁负责
│
├── ③ 客户主数据
│   └── 谁负责、谁维护、谁跟进
│
└── ④ 供应商主数据
    └── 谁采购、谁对接、谁审核
```

### 为什么HR主数据最难治理？

**HR部门的特点：**
```
1. 相对独立
   └── HR系统往往是独立的，不受IT管辖

2. 权力较大
   └── HR是核心部门，谁都得罪不起

3. 数据敏感
   └── 人员信息涉及隐私，不敢动

4. 系统封闭
   └── 很多用的是SAP SuccessFactors、Workday等国外系统
   └── 接口开放难

5. 业务惯性
   └── HR有自己的工作方式和节奏
   └── 不想被IT牵着走
```

### HR主数据治理的核心价值

**为什么一定要撬动HR主数据？**

```
没有HR主数据：
├── 销售数据无法归属到具体负责人
├── 产品无法归属到具体组织和岗位
├── 供应商无法归属到具体采购人员
├── 所有分析都是"糊涂账"
└── 责任人找不到，数据治了也白治

有了HR主数据：
├── 每个客户都能找到负责人
├── 每个产品都能找到负责组织
├── 每笔订单都能找到审批人
├── 数据可以追溯到具体的人
└── 业务分析和绩效考核才有基础
```

### 关键洞察

> **数据治理的本质不是"治数据"，是"治责任"。**
>
> **治数据的终极目的是：让每一笔数据都能找到责任人。**
>
> **而责任人的基础，就是HR主数据。**

### 核心金句

> **产品、客户、供应商，最终都会落实到人和组织上。**
>
> **没有HR主数据，其他所有数据治理都是"治标不治本"。**
>
> **人员主数据是一切数据治理的"锚点"。**

## 老周实战洞察：数据治理组织架构与确权路径——先有制度，再建组织

**日期**：2026-10-15
**标签**：#数据治理 #治理组织 #确权 #数据管理办法 #数据管理办公室

---

### 核心思路：先确权，后建组织

```
数据治理的第一步，不是技术，是"确权"

确权 = 确立数据管理部门对全公司数据管理的职责和权限

路径：
① 先出《数据管理办法》（一级概要性制度）
   └── 不用很细，是一级概要性制度
   └── 核心：确立数据管理部门的责权
   
② 再通过这个制度去组建治理组织
   └── 用制度作为"尚方宝剑"
   └── IT/数据管理部门才能名正言顺地推进
```

### 《数据管理办法》核心内容

```
《数据管理办法》（一级制度）
├── 第一条：目的和依据
├── 第二条：适用范围
├── 第三条：数据管理的定义和原则
├── 第四条：数据管理部门的职责和权限  ← 核心！
│   └── 数据管理部门对全公司数据管理负责
│   └── 有权制定数据标准
│   └── 有权监督各业务域数据质量
│   └── 有权协调跨部门数据问题
│   └── 有权考核各业务域数据治理成果
├── 第五条：各业务领域的职责
├── 第六条：数据治理组织架构
└── 附则：实施时间和解释权
```

### 数据治理的两层组织架构

```
数据治理组织架构

├── 第一层：领导小组（决策层）
│   └── 组成：公司高层高管
│   └── 包括：董事会/党委会/总经理办公会
│   └── 职责：重大事项决策、资源协调、重大问题裁决
│
├── 第二层：数据管理办公室（执行层）
│   └── 性质：可以是虚拟组织，也可以是实体组织
│   └── 定位：公司数据管理的核心部门
│   └── 职责：
│       ├── 技术标准制定
│       ├── 质量标准制定
│       ├── 组织协调（跨部门数据问题）
│       ├── 跟踪监督（各业务域执行情况）
│       └── 评价考核（各业务域数据治理成果）
│
└── 业务领域（执行层）
    └── HR领域
    └── 产品领域
    └── 质量领域
    └── 营销领域
    └── 财务领域
    └── 供应链领域
    └── ...（根据企业实际灵活调整）
```

### 三层关系

```
领导小组（高层决策）
    ↓ 决策
数据管理办公室（核心执行）
    ↓ 指导+监督
业务领域（具体执行）
    └── HR主数据治理
    └── 产品主数据治理
    └── 客户主数据治理
    └── ...
```

### 关键洞察

**为什么先确权？**

```
没有确权的问题：
├── IT/数据管理部门推进数据治理"名不正言不顺"
├── 各业务部门不配合，说"你凭什么管我"
├── 数据治理推不动，责任不清，互相推诿

确权后的效果：
├── 数据管理部门有"尚方宝剑"
├── 各业务部门知道"谁"来管、管的边界在哪里
├── 后续组建HR治理小组等才能名正言顺
```

**为什么是"虚拟组织"？**

```
虚拟组织 vs 实体组织
├── 虚拟组织：不占编制，灵活
│   └── 适合：中小企业或转型期
│   └── 优点：快速组建，成本低
│   └── 缺点：权威性相对弱
│
└── 实体组织：正式编制，权威
    └── 适合：大型企业或数据治理成熟期
    └── 优点：权威性强，资源有保障
    └── 缺点：组建周期长，成本高
```

### 撬动HR主数据治理的具体路径

```
第一步：确权
└── 出台《数据管理办法》
└── 确立数据管理部门的责权

第二步：建组织
└── 组建数据管理领导小组（高层）
└── 组建数据管理办公室（执行层）
└── 组建HR业务领域数据治理小组

第三步：定标准
└── HR主数据标准（人员编号、岗位、组织架构）
└── 数据质量标准
└── 数据质量考核标准

第四步：推执行
└── HR部门配合执行
└── 数据管理办公室跟踪监督
└── 领导小组评价考核
```

### 核心金句

> **数据治理的第一步不是技术，是"确权"。**
>
> **没有确权，数据治理就是IT部门一个人在唱独角戏。**
>
> **确权之后，制度是"尚方宝剑"，组织是"执行抓手"。**
>
> **数据管理办公室是公司数据管理的"中枢神经"，连接领导小组和业务领域。**

### 一、HR主数据治理的组织体系

```
HR领域数据治理组织架构

├── HR领域数据治理小组
│   ├── 负责人：HR部门负责人
│   ├── 数据Owner：HR数据管理员
│   └── 执行人员：各HR子系统管理员

├── DC（Data Coordinator，数据协同和协作人）
│   ├── 什么是DC？
│   │   └── 不是数据所有者，而是数据流转中的协调节点
│   │   └── 负责跨系统、跨部门的数据协同工作
│   │
│   ├── DC的二级分类（配合主数据二级分类模型）
│   │   ├── 一级DC
│   │   │   └── 负责一级主数据的协调（人员、组织架构等）
│   │   │   └── 跨系统、跨部门的高层协调
│   │   │
│   │   └── 二级DC
│   │       └── 负责二级主数据的协调（岗位分类、HR流程数据等）
│   │       └── 嵌入业务系统的日常协调
│   │
│   └── DC的核心职责
│       ├── 推动数据标准的落地
│       ├── 协调数据质量问题
│       ├── 沟通业务需求
│       └── 配合数据治理委员会工作
```

### 二、为什么入湖是前置工作？

```
传统做法：
❌ 先定义主数据标准
❌ 再建主数据平台
❌ 再分配治理责任
结果：标准定了一大堆，落不了地，因为不知道现状是什么

正确做法：
✅ 先入湖
   └── 把HR相关的所有系统数据都接入数据湖
   └── SAP HR、招聘系统、考勤系统、薪酬系统...

✅ 入湖后分析
   └── 哪些数据是跨系统共享的 → 一级主数据
   └── 哪些数据是HR系统内部使用的 → 二级主数据

✅ 分清楚后再定义标准
   └── 一级主数据 → 统一标准，平台管理
   └── 二级主数据 → 嵌入HR系统功能，不单独建平台

好处：
├── 不会把本该二级的主数据强加给HR管
├── HR不会觉得数据治理是"被强加的任务"
├── 责权清晰，落地容易
```

### 三、协商式治理：不给HR"强压标准"

```
传统IT做法（❌）：
└── IT部门制定标准，强制HR执行
└── HR觉得是负担，不配合
└── 数据治理推不动

老周的实践（✅）：
└── 先入湖，看现状
└── 邀请HR一起分析：哪些该管、哪些不该管
└── HR说"这个我管不了"→ 从一级下沉为二级
└── HR说"这个我可以管"→ 确认为一级，HR负责

核心原则：
├── 共同协商，不强制
├── 尊重HR的业务逻辑
├── 让HR觉得数据治理是"帮我的"
└── 不是"管我的"
```
