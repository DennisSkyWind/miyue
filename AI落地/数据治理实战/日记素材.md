## 日记1：数据治理——先内后外，顺序不能颠倒

**标签**：[[数据治理]] [[方法论]] [[CIO]] [[企业数字化]]

### 核心观点

很多公司都有数字化部门，CIO 请咨询公司来做方案然后上系统实施。
这个思路是对的，但也不完全正确。

### 为什么这样说？

**第三方咨询的角色应该是辅助，而不是主导。**

正确路径：
```
第一步：公司内部先做好三件事
    ├── 情况摸底（数据现状是什么）
    ├── 目标确定（数据治理要解决什么问题）
    └── 责权明确（谁负责、谁推动、谁考核）

第二步：成立数据组织
    └── 建立公司一级的数据治理委员会或专项小组

第三步：制定公司一级数据管理制度
    └── 明确数据标准、数据质量要求、数据安全规范

第四步：有了人和权之后
    └── 再请第三方咨询进来，配合实施
```

### 常见错误顺序

1. 先请咨询公司出方案
2. 方案做完才发现没有组织保障
3. 没有数据委员会，没有数据管理制度
4. 咨询公司走了，系统推不动

**结果：** 花了钱，没有效果。

### 关键原则

> 咨询公司是来帮你做技术方案和实施支持的，不是来帮你做组织保障的。
> 组织保障必须是自己公司的事情，必须先于咨询介入。

**先有人、有权、有制度 → 后有咨询、有系统、有工具**

核心原则：**先组织后技术，先治理后系统。**

## 日记2：数据治理重要的是管理体系而不是工具

**标签**：[[数据治理]] [[方法论]] [[工具误区]]

### 核心观点

就算没有数据治理平台，通过单纯数据库系统的各类功能也可以做治理。

### 常见误区

很多企业做数据治理，第一件事就是买平台。
**结果：** 平台上了没人用，制度没有，系统推不动。把工具当成解药。

### 没有平台也能做治理

| 治理动作 | 工具方法 |
|---------|---------|
| 数据标准定义 | 数据库字段命名规范 + CHECK约束 |
| 数据质量检查 | SQL定期查询 + 自动化脚本 |
| 数据安全 | 数据库用户权限管理 + 审计日志 |
| 主数据管理 | 数据库分区 + 唯一索引约束 |
| 数据血缘 | ER图 + 文档记录 |
| 数据资产盘点 | 数据库字典 + 定期巡检 |

**本质：制度和流程到位了，工具只是锦上添花。**

### 正确优先级

```
第一步：建立数据管理制度（人）
第二步：明确数据Owner职责（权）
第三步：制定数据标准规范（法）
第四步：选型数据治理工具（器）
```

**器最后。**

### 金句

> 好的数据治理不需要平台，需要的是对的人、对的制度、对的方法。

## 老周实战洞察：主数据治理的二级分类模型（重要创新）

**日期**：2026-10-15
**标签**：#数据治理 #主数据 #创新模型 #实战方法论

---

### 传统主数据治理的问题

传统的思路是：先把所有主数据列出来，然后统一治理。

**但实际问题是：**
- 主数据种类太多，边界模糊
- 不同主数据的业务价值完全不同
- 用同一套方法治理所有主数据，成本高、效率低

### 老周提出的二级主数据分类

```
主数据
├── 一级主数据（强管控）
│   └── 核心稳定、跨系统共享、变更不频繁
│   └── 例：组织架构、人员、银行账号、税号
│   └── 治理方式：委员会治理 + 平台管控
│
└── 二级主数据（嵌入式）
    └── 与业务系统深度绑定、随业务变化
    └── 例：产品分类、销售区域、客户分类
    └── 治理方式：嵌入业务系统功能，随系统一起管理
```

### 两级的核心区别

| 维度 | 一级主数据 | 二级主数据 |
|------|-----------|-----------|
| 稳定性 | 核心稳定，变更极少 | 随业务变化，变更频繁 |
| 共享范围 | 全集团跨系统共享 | 本业务系统内部使用 |
| 治理主体 | 数据治理委员会统一管控 | 业务部门自行管理 |
| 平台依赖 | 必须有主数据管理平台 | 不需要，可随业务系统管理 |
| 典型示例 | 组织架构、人员、税号、银行账号 | 产品分类、销售区域、客户细分 |
| 管理难度 | 低（系统化管理即可）| 高（需要嵌入业务流程）|

### 关键洞察

**二级主数据的真正价值不是"治理"，而是"嵌入业务系统功能设计"。**

传统思路：先建主数据平台，再谈应用

老周思路：
- 一级主数据 → 平台统一管理（标准动作）
- 二级主数据 → 在业务系统设计时就把数据架构考虑进去

### 实操建议

**一级主数据治理（传统做法）：**
```
1. 建立主数据管理委员会
2. 制定数据标准
3. 上主数据管理平台
4. 统一分发
```

**二级主数据治理（新思路）：**
```
1. 在业务系统设计阶段就做数据建模
2. 数据标准嵌入系统功能
3. 随业务系统一起维护
4. 不单独建平台，不单独治理
```

### 核心金句

> **一级主数据靠平台，二级主数据靠嵌入。**
> **二级主数据治理的最高境界，是让业务系统"忘记"主数据的概念，觉得数据就是功能的一部分。**

### 价值

这个模型的价值在于：
- 降低了主数据治理的复杂度
- 明确了不同主数据用不同的治理方法
- 节省了大量建平台的钱
- 更符合实际业务场景

## 老周实战洞察：主数据治理的混合制模式——源端治理优先

**日期**：2026-10-15
**标签**：#数据治理 #主数据 #混合制 #源端治理 #集中式vs联邦制

---

### 传统主数据治理的两种模式

```
传统模式
├── 集中制
│   └── 所有主数据统一到主数据平台管理
│   └── 优点：标准统一、管控到位
│   └── 缺点：业务响应慢，平台审批链路长，容易阻塞业务
│
└── 联邦制
    └── 各业务系统各自管理，主数据平台只做共享协调
    └── 优点：业务响应快
    └── 缺点：标准难统一，数据质量参差不齐
```

### 现代企业的现实情况

在现代企业中，几乎所有主数据都有系统在管理了：

| 主数据类型 | 已有系统 |
|-----------|---------|
| 人员主数据 | HR系统 |
| 客户主数据 | CRM系统 |
| 供应商主数据 | ERP系统 |
| 物料主数据 | ERP系统 |
| 财务主数据 | 财务系统 |

**结论：在现代企业中，几乎没有"没有系统管理的主数据"了。**

### 老周提出的混合制模式

```
混合制 = 源端治理 + 平台兜底

针对已有系统管理的主数据
└── 源端治理（首选方式）
    ├── 在数据源头进行治理
    ├── 业务系统负责维护和标准化
    ├── 主数据平台只做"分发"和"共享"
    └── 好处：快速响应业务变化，快速发现异常

针对没有系统管理的主数据
└── 才放到主数据平台进行统一管理
    └── 因为没有系统管，所以才需要平台管
```

### 核心洞察：为什么源端治理更好？

**集中制的问题：**
```
业务系统需要主数据
    ↓
向主数据平台申请
    ↓
平台审批确认
    ↓
数据标准化
    ↓
返回业务系统
    ↓
业务等待...（阻塞！）
```

**源端治理的好处：**
```
业务系统在数据产生时就完成治理
    ↓
数据变更实时生效
    ↓
异常快速发现
    ↓
平台只做分发，不做审批
    ↓
业务响应快，不阻塞
```

### 源端治理的具体做法

**源端治理四步法：**

```
1. 定标准
   └── 在源头系统定义数据标准
   └── 标准要嵌入业务流程，不是单独的审批流程

2. 强执行
   └── 源端系统强制执行数据校验
   └── 不符合标准的数据进不去

3. 快响应
   └── 数据变更在源端实时生效
   └── 不用等平台审批

4. 平台只分发
   └── 主数据平台负责数据分发和共享
   └── 不是数据的"审批关卡"
```

### 两个模型的关联

老周的两个模型是互补的：

| 模型 | 分类维度 | 治理方式 |
|------|---------|---------|
| **二级分类模型** | 主数据的重要程度 | 一级靠平台，二级靠嵌入 |
| **混合制模型** | 是否有源系统 | 有系统→源端治理，无系统→平台管理 |

**两个模型的核心逻辑一致：**
> **能通过业务系统管理的，就不要搬到主数据平台。主数据平台应该是"分发通道"，不是"审批关卡"。**

### 核心金句

> **源端治理的本质是"让数据在产生的地方就被管好"，而不是"把所有数据集中到平台再管"。**

> **主数据平台的最佳定位是"高速公路"（分发），而不是"收费站"（审批）。**
