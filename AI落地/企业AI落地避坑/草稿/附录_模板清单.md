## ① 附录 H　场景筛选表

**这张表和附录 A 的区别**：

```
附录 A（场景评估表）  →  ★ 已经决定要做了，★ 那怎么排序、怎么收敛
附录 H（场景筛选表）  →  ★ 还没决定要不要做，★ ★★ 先用这一页筛掉不该做的
        ↓
★★ ★★ 顺序很重要：★★ 先筛，再排
★★ ★★ 拿一张 46 个场景的表去做优先级排序，★ ★★ 是本末倒置——
★★ ★★ 因为那张表里，★ ★★ 一半的场景本来就不该做
```

**用法**：拿一个候选场景，对着下面 12 个问题打"是/否"。**不用写任何方案**，5 分钟能答完。

### H.1 十二问筛选表（可复制）

| # | 问题 | 是 / 否 |
|---|---|---|
| **1** | **这件事现在有人做吗？**（做不了 AI，也要有人在做） | |
| **2** | **如果 AI 做好了，收益能被说成"省了多少时间"或"多赚了多少"吗？** | |
| **3** | **出错一次，代价有人承担吗？**（能追到具体的人/岗位） | |
| **4** | **做这件事需要的文档/数据，今天就拿得到吗？** | |
| **5** | **这些数据的口径，是唯一的吗？**（没有第二套算法在打架） | |
| **6** | **★ 现在查这件事，老路是什么？** | |
| **7** | **★ 老路哪一项比新方案强？** | |
| **8** | **使用者今天愿意多打开一个入口吗？** | |
| **9** | **这个场景做完，**哪个环节**因此变短了？**（不是"覆盖了几个流程"） | |
| **10** | **有没有一个具体的人，会在第一个月里每天用它？** | |
| **11** | **试点失败了，我们能说清"为什么"吗？** | |
| **12** | **预算从哪出？**（说不出归口部门，就先别立项） | |

### H.2 怎么读这张表

```
★★ ★★ 第 6、7 两问是这张表的核心，★★ 也是最容易被跳过的一问

   第 6 问：现在这件事，大家是怎么做的？
        ↓
   ★★ 如果答案是"有邮件 / 有 Excel / 有个群"——★★ 那就先问第 7 问
   ★★ 因为老路一定在某一项上强，★★ 不然它早该被换掉了
        ↓
   ★★ 第 7 问：老路哪一项比新方案强？
        ↓
   ★★ ★★ 常见答案（★ ★★ 这三条是"先别做"的信号）：
   · ★★ 自己能挑要哪部分（AI 替用户做了选择）
   · ★★ 能转给同事、抄送主管（AI 默认单线程）
   · ★★ 零学习成本（AI 要求先学会怎么问）
        ↓
   ★★ ★★ 而如果新方案只赢"移动端能查"这一项，★★ ★★ 通常不值得单独立项
   ★★ ★★ 除非——★ 它是那个不可替代的一项（比如一线在外场，没电脑）
```

### H.3 三条"直接不做"的信号

```
★★ ★★ 出现下面任何一条，★ ★★ 不用再往下评估了：

   ❶ ★★ 答不出第 2 问（★ 说不出收益形态）
      → ★★ 这不是技术问题，★ 是这个场景的价值本身没被想清楚

   ❷ ★★ 答不出第 5 问（★ 口径不唯一）
      → ★★ 这是第三章讲的"翻译"没做，★ ★★ 做 AI 之前先把口径对齐

   ❸ ★★ 第 7 问的答案是"老路在三项上强，我们只赢一项"
      → ★★ ★★ 老路不是落后，★ ★★ 它是当前的最优解
      → ★★ 这种情况应该做的是：★ ★★ 先去做 5.2 的数据准备与 5.3 的流程再造，
         ★ ★★ 而不是先做一个 AI 入口
```

### H.4 筛完之后

```
★★ 过了筛 → ★★ 进附录 A 的评分表，★ ★★ 排队、收敛、选 1–2 个进试点
★★ 没过筛 → ★★ ★★ 写进清单，★ ★★ 半年后重评（★ 别删，★ ★★ 下次复盘要用）
```

> **★ 金句**
>
> **「先筛，再排。拿一张 46 个场景的表去做优先级排序，是本末倒置——因为那张表里，一半的场景本来就不该做。」**
>
> **「老路不是落后，它是当前的最优解。」**

> **★ 一条使用提醒**
>
> **这张表最有价值的一行是第 7 问。**
> **如果一个场景永远答不出"老路哪一项比新方案强"，那多半是你还没把老路弄清楚，而不是新方案特别强。**

## ② 附录 A　场景评估表

**来源**：作者的实践做法是——把所有候选场景列成清单，逐条按"值不值得做"打分，而不是凭印象挑几个。素材中记录的规模是**七十余条候选需求逐条打分**【待核实：具体条数以作者最终确认为准】。

### A.1 评分表（可复制）

```
┌────┬────────────────┬──────────┬──────────┬──────────┬────────┐
│ #  │ 场景            │ 业务价值  │ 可行性    │ 优先级    │ 结论   │
│    │                │ (1-5)    │ (1-5)    │ =价值×可行性│        │
├────┼────────────────┼──────────┼──────────┼──────────┼────────┤
│ 1  │                │          │          │          │ 做/缓  │
├────┼────────────────┼──────────┼──────────┼──────────┼────────┤
│ 2  │                │          │          │          │ 做/缓  │
├────┼────────────────┼──────────┼──────────┼──────────┼────────┤
│ …  │                │          │          │          │        │
└────┴────────────────┴──────────┴──────────┴──────────┴────────┘
```

### A.2 价值怎么打分（5 分定义）

| 分 | 判据（业务价值） |
|---|---|
| 5 | 直接影响收入、成本或合规风险，且**有明确的责任人**（做错了谁赔） |
| 4 | 明显减少重复劳动，替代人力明确 |
| 3 | 效率提升，但受益人分散、价值难量化 |
| 2 | 锦上添花，做不做都能活 |
| 1 | 说不清收益 |

### A.3 可行性怎么打分（5 分定义）

| 分 | 判据（可行性） |
|---|---|
| 5 | 数据现成、口径唯一、流程已有负责人 |
| 4 | 数据现成，但口径需对齐一次 |
| 3 | 数据在两个系统内可取，需开发 |
| 2 | 数据需跨系统整合或需外部采购 |
| 1 | 数据不存在或口径混乱 |

### A.4 收敛规则（★ 这一步才是重点）

```
优先级 = 价值 × 可行性

≥ 15  → 进入候选池（第一批做 1–2 个）
9–14  → 备选（第一批跑通后接着做）
< 9   → 暂不做（写进清单，半年后重评）

★ 但最终只选 1–2 个进入试点，其余全部留在清单里
```

**"选完不删表"很重要**：被搁置的场景留在清单上，下次复盘时重评，而不是每次重新想一遍。

### A.5 一条使用提醒

> **这张表最重要的一列不是分数，是"结论"列里的"为什么不做"。**
>
> 如果 20 个场景里有 18 个写的是"暂不做"却没写原因，那么三个月后你会重新讨论这 18 个场景。

## ④ 附录 C　AI 模型与工具台账模板

**说明**：本附录采用通用工程模板，不依赖任何内部制度原件。✅ **2026-11-02 作者确认：就用本通用模板代替，不再追原件。**
以下模板按通用工程实践编写，可直接使用。

### C.1 台账字段

```
┌────┬──────────┬────────┬────────┬────────┬────────┬────────┐
│ #  │ 名称/用途  │ 类型    │ 版本   │ 责任人 │ 上线日  │ 状态   │
├────┼──────────┼────────┼────────┼────────┼────────┼────────┤
│ 1  │          │        │        │        │        │在用/退役│
└────┴──────────┴────────┴────────┴────────┴────────┴────────┘
```

### C.2 每个条目要补的六项

| 项 | 内容 | 为什么必须有 |
|---|---|---|
| **数据边界** | 哪些数据会进它、哪些不出厂 | 出事时第一句话就是问这个 |
| **权限与可见范围** | 谁能用、谁能看它处理过什么 | 权限继承的落点 |
| **日志留存** | 输入/输出/调用人/时间存多久、谁能查 | 审计与追溯 |
| **降级方案** | 它挂了怎么办，谁接手 | 兜底不是可选项 |
| **复核机制** | 谁定期看它的输出、抽查多少 | 防止它悄悄变差 |
| **退役条件** | 什么情况下下线、下线后数据怎么办 | 防止僵尸工具累积 |

### C.3 退役条件（建议写法）

```
出现下列任一情况 → 启动复核 → 决定整改或退役：
  ① 连续 N 个月价值类指标低于初始目标的 50%
  ② 人工介入次数持续上升（说明模型在退化或场景在漂移）
  ③ 依赖的上游系统已下线
  ④ 出现合规问题且无法通过整改闭环
  ⑤ 场景的业务流程已不存在
```

> 【待核实】退役条件中的 N 值与"人工介入次数上升"的判定口径，需按作者所在企业的管理制度确定。
