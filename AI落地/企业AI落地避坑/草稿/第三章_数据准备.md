## 3.0 本章要回答什么

第一章的坑三说了一句话：**数据没准备好就想上 AI**。第二章把场景选完了，第三章就要面对那件最不性感的事——

```
场景选对了，方案也定了。
然后 IT 部门问了一句：
      "数据从哪来？"
```

这一问，会让项目停两个月。

而这两个月里发生的所有事，几乎都源于一个误会：

> **很多人以为"数据准备"是数据部门的事。**
>
> **实际上，"数据准备"是把企业的业务口径，翻译成 AI 能听懂的形式——这是一次翻译工作，不是一次搬运工作。**

搬运会失败，因为 AI 不接受原始数据：它需要**口径统一、边界清晰、权限可控、来源可溯**的信息。

翻译不会失败，因为翻译的对象是**口径**——而口径是业务部门定的，不是数据部门定的。

**这就是本章的立场：数据准备的第一责任人不是 IT，是业务。**

## 3.1 先复习：AI 落地的四大基石

第二章选场景时用的那四个判据，这里再挂一次，因为**数据准备的每一步都能挂到其中一条上**：

```
基石一  场景要成立          —— 场景不对，数据再准也没用
基石二  数据要能算          —— 口径不清，AI 算的是"第三个数"
基石三  流程要能承接        —— AI 出了结论，没人接，等于没出
基石四  组织要能管住        —— 权责不清，出了事无人认领
```

**数据准备主要压在基石二上，但它的成败却常常由基石一和基石四决定。**

这句话很反直觉，但很重要：

```
数据准备的失败，九成不是"数据脏"，
是"这个场景本就不该做" 或 "做完了没人认领"。
```

一个不该做的场景，你为它治理数据，等于**为一个错误结论修路**。
一个没人认领的场景，你为它治理数据，等于**修了一条没人走的路**。

**所以在动手整理数据之前，先回头看第二章那三问：这件事做错了谁赔？现在人工怎么做？**

## 3.2 三张清单

数据准备不需要一个庞大的治理体系，需要三张**能在一周内填完**的清单。

三张清单的分工是：

```
┌─ 数据可用性清单 ─ 机器要吃的：口径 / 时效 / 完整性 / 权限
│   → 回答：这份数据能不能用？
├─ 文档治理清单 ─── 人要查的：所有者 / 版本 / 生效期 / 密级
│   → 回答：这份文件现在算不算数？
└─ 反馈闭环清单 ─── 用起来之后：报错 / 纠错 / 回流
    → 回答：用错了怎么办、多久能改好？
```

**为什么是三张而不是一张**：因为它们回答的是三个不同的问题，而且**只有第一张是数据部门的事**。

### 3.2.1 数据可用性清单：机器要吃的那一口

这张清单的字段，可以直接抄：

| 字段 | 要写清什么 | 不写清会怎样 |
|---|---|---|
| **口径** | 这个数字怎么算出来的，唯一算法是什么 | 模型学进去两套口径，给你第三套 |
| **来源** | 在哪个系统，哪张表，谁是权威源 | 同一指标从三个地方取，各取各的 |
| **时效** | 数据更新到什么时候，延迟多少 | 拿上周的库存做今天的预测 |
| **完整性** | 覆盖多少业务、多少时间、多少维度 | 训练集只覆盖了三成场景 |
| **权限** | 谁能看到、谁能改、能不能出模型 | 越权访问，事故从数据泄露开始 |

**用一张真实的盘点表来看这张清单长什么样。**

某大型药企在做销售预测场景时，做过一份"场景所需数据盘点表"，它的表头列是：

```
数据描述 | 数据来源 | 数据周期 | 核心字段 | 数据量 | 数据质量
```

而这张表填出来的内容长这样（脱敏后）：

```
┌──────────────┬────────┬──────────────┬──────────┬───────┐
│ 内部发货明细  │ BIS    │ 2023–2025     │ 规格/数量/日期 │ 百万行级 │
├──────────────┼────────┼──────────────┼──────────┼───────┤
│ 终端纯销数据  │ BI     │ 2024–2025     │ 终端/销量/日期 │ 千万行级 │
├──────────────┼────────┼──────────────┼──────────┼───────┤
│ 经销商进销存  │ BIS    │ 2024–2025     │ 经销商/进货/出货 │ 百万行级 │
├──────────────┼────────┼──────────────┼──────────┼───────┤
│ 外部医疗场景数据│ 外部    │ 待落实       │ 待定      │ 待定   │
└──────────────┴────────┴──────────────┴──────────┴───────┘
```

**这张表就是"数据准备"的实物形态：**

```
一个场景
  ├─ 三个内部系统（不是同一个）
  ├─ 两套数据周期（2 年 vs 3 年）
  ├─ 一块还得去外面谈的外部数据
  └─ 每个系统各有各的字段口径
```

**三个洞察，比表本身更值钱：**

**洞察一：这张表最有价值的列是"数据周期"，不是"数据量"。**

> 因为数据量决定跑不跑得动，**数据周期决定结论靠不靠谱**。
> 一个场景需要 3 年趋势，而其中一块数据只有 1.5 年——**这才是要提前拍板的事**。

**洞察二：表里最刺眼的是"外部数据待落实"。**

一个内部场景，依赖一块**还没谈下来的外部数据**，那么项目排期里就一定藏着一个风险：外部一延，整个项目延。

> **凡是要外部数据才能成立的场景，都必须写进立项文件的风险栏，而不是藏在附件里。**

**洞察三：这张表本身就是一个"要不要做这个场景"的判断器。**

如果填完这张表，发现三块内部数据里有两块口径不明、一块要靠外部采购才能拿到——**那这个场景现在不该做**，先做别的。

**省下的是整个项目，不是几个月。**

### 3.2.2 文档治理清单：人要查的那一份

第二张清单管的是**非结构化材料**：制度、规程、合同范本、会议纪要、检验标准、SOP。

这类东西的特点是：**AI 要读它们，但它们自己会过期。**

```
一份三个月前的制度文件
  ├─ 内容没错
  ├─ 但已被新版取代
  └─ AI 照样把它当现行有效引用 → 结论错，且无法追溯
```

所以文档治理清单的字段是：

| 字段 | 含义 | 为什么必须有 |
|---|---|---|
| **所有者** | 这份东西归谁维护 | 没主人的文件会一直"有效"下去 |
| **版本** | 当前是第几版 | 没有版本号的文档无法判断新旧 |
| **生效期** | 什么时候开始有效、什么时候失效 | **这是 AI 出错的高发点** |
| **密级** | 内部 / 受控 / 秘密 | 决定它能不能被谁检索到 |

**这张清单背后有一个致命细节：生效期。**

> 制度、规程、标准类文件，**绝大多数不是"写错了"，而是"过期了还被引用"**。
>
> 人判断一份文件是否有效，靠的是"我记得这版后来改过"。
> **AI 判断不了这件事——除非你把生效期喂给它。**

这就是为什么文档治理的第一件事不是上传，而是**打标签**。

**这张清单的第二个致命细节：所有者。**

一份没有所有者的文件，在 AI 场景下会变成：
- 没有人能回答"这份东西对不对"
- 没有人能修它
- 出错时没有人能负责

**而这正是第一章 1.4 讲过的那个机制在文档场景的重演：责任无处落地，抵触与敷衍就有土壤。**

### 3.2.3 反馈闭环清单：用起来之后的那三件事

第三张清单最容易被忽略，也最能决定一个 AI 场景的**实际寿命**。

```
场景上线
   ↓
用户用它 → 发现错了
   ↓
???
   ↓
（如果这里没有清单，90% 的场景就停在这一步）
```

反馈闭环清单要写清三件事：

| 事项 | 具体要定 | 常见的坑 |
|---|---|---|
| **错误上报** | 谁在什么入口报错、报什么（场景/输入/错误输出） | 只留了个邮箱，没人看 |
| **纠错责任** | 谁来判断"这是错的"、多久内给结论 | 反馈回来没人认领，闭环断在第二跳 |
| **回流路径** | 纠错的结论怎么回到知识库/规则/数据，让下次不再错 | 改了单次记录，没改源头，**同一个错犯三次** |

**第三条最关键，也最常被漏。**

一个只记录、不回流的反馈系统，本质上是**一个抱怨箱**：

```
用户报错 → 运营记录 → 用户收到"已收到" → 下次继续错
```

而回流机制要做的是：

```
用户报错 → 定位到具体是哪一段知识/哪一条规则/哪一个数据口径
         → 改源头（不是改这一次的答案）
         → 记录一条"这类错误"的通用规则
         → 下次同类问题不再犯
```

**这就是"纠错"和"改进"的区别：前者修一次，后者修一类。**

**能不能做对，取决于反馈闭环有没有回流这一步。**这也是本书后面讲"运营"时会再出现的一个机制。

### 3.2.4 三张清单怎么填：一周工作法

不要做全景盘点。**只填第一个场景要用的那一份。**

```
第 1-2 天  拿一张表跑通
           挑第一个场景，按"数据可用性清单"把这张场景要用的数据逐项列出来
           （照着 38 号那张盘点表的列抄）

第 3 天    补文档清单
           这个场景会引用哪些制度/规程/标准？
           逐份确认：所有者、版本、生效期、密级

第 4 天    定反馈闭环
           这个场景最可能出哪三类错？谁报？谁判断？改完回到哪里？

第 5 天    开会，做三件事
           ① 清单里标"待落实/待确认"的，当场定责人和时限
           ② 清单里标"拿不到"的，判断这个场景还做不做
           ③ 确认哪些字段需要 IT 侧提供，哪些需要业务侧补口径
```

**第 5 天的第②件事才是重点：清单填完不是为了开始做，是为了允许你决定不做。**

## 3.3 RAG 与数据治理的真实接口

这一节要讲一件很多人没意识到的事：

> **RAG（检索增强生成）不是绕过数据治理的捷径，它只是把数据治理的问题从"全量"缩小到"检索得准不准"。**

### 3.3.1 为什么 RAG 看起来像"不用治理也能用"

因为 RAG 的直觉 appealing：

```
把文档丢进向量库 → 用户提问 → 检索出几段 → 塞给模型 → 生成答案
```

看起来，脏数据、过期文档、口径混乱，全都被"检索"这一步吸收了。

**但事实是：检索只能在你已经治理好的东西上做筛选，做不了治理本身。**

具体地说，RAG 会把数据治理的四类问题原封不动地搬到检索环节：

| 治理问题 | 在 RAG 里的表现形式 |
|---|---|
| 口径不统一 | 检索出两段互相矛盾的内容，模型"综合"出一个第三种说法 |
| 版本过期 | 检索出旧版制度，答案看起来完全正确 |
| 权限不清 | 检索出用户本不该看到的机密段落 |
| 溯源缺失 | 答案对了，但说不出来自哪份文件——**在受监管场景里等于没答** |

### 3.3.2 四个真实接口

**接口一：切片（chunking）——治理问题被放大三倍**

```
一份 80 页的规程，切成 100 个片段
   ↓
每个片段脱离上下文：
  "本条适用于……"   ← 指代谁？在别的片段里
  "例外情况见附录B" ← 附录 B 不在这 100 片里
  "（本条自2025年起废止）" ← 废止信息在第 3 页，在第 47 片里
   ↓
检索召回的是第 47 片
   ↓
模型拿着一段没有生效期、没有例外说明的条文回答问题
```

**这就是为什么"文档治理清单"直接决定 RAG 的质量上限**：你标没标生效期，切片里就没有。

**切片切得再聪明，也救不了没打过标签的文档。**

**接口二：混合检索——为什么纯向量检索在制度类文档上会翻车**

制度、规程、标准这类文本有个特点：**关键词比语义更可靠**。

```
问："偏差调查的处理时限是多少个工作日？"
文档："偏差调查应在 5 个工作日内完成（见 3.2.1）"

纯向量检索：靠语义相似度找 → 找到一堆提到"调查""时限"的段落
关键词检索：命中"5 个工作日" → 精确
```

**混合检索（关键词 + 语义 + 结构化过滤）是制度类场景的必需项，不是可选项。**

> 【待核实】作者所在项目的实际检索策略（是否用混合检索、是否接图谱）——素材中未见具体记载，本节为通用工程实践，需按实情修订。

**接口三：权限继承——RAG 最大的合规缺口**

这是本节最要紧的一条。

```
传统系统：权限在数据源那一层
   → 你查报表，SQL 带权限条件，返回的就是你能看的

RAG 系统：权限最容易"掉"在检索这一层
   → 全员共用一个向量库 → 检索按语义命中 → 命中了就能看到
```

**如果不把权限继承到检索层，RAG 就会变成"全员都能看到所有文件"的知识库。**

正确的做法是把权限作为**检索的前置过滤条件**，而不是生成后的兜底：

```
✅ 权限过滤在检索前（按用户身份过滤候选片段）
⚠️ 权限过滤在生成后（先检索再判断）—— 已经泄露了
❌ 不做权限（默认全员可见）
```

**这不是技术偏好问题，是第七章要讲的红线问题。**在这里先记住一句：**"检索到"就等于"看到了"，所以权限必须落在检索之前。**

**接口四：引用溯源——在受监管场景里，答案不带出处等于没答**

```
模型答："偏差调查应在 5 个工作日内完成。"
                ↑
        错一个数字，整条答案作废
        而且没人知道它从哪来
```

所以 RAG 的输出必须带引用：

```
✅ 每句结论后面挂来源（文件名 + 版本 + 条款号 + 生效期）
✅ 检索不到 → 明确回答"没有依据"，而不是编一个
✅ 引用了旧版 → 治理清单里的生效期字段在这一刻兑现价值
```

**"没有依据就说不知道"这条规则，是把幻觉从技术问题变成工程问题的唯一办法。**

### 3.3.3 一句话结论

> **RAG 把数据治理的难度从"全公司"缩小到"一个场景"，但没有把难度消掉。**
>
> **它把治理的粒度，从"数据表"变成了"可检索的片段"。**

而"可检索的片段"能不能被正确检索，取决于：口径清不清、版本标注没标注、生效期写没写、权限挂没挂。

**这四件事，全在上一节那三张清单里。**

## 3.4 数据分级：能不能进模型

RAG 之外，AI 还要面对一个更直接的问题：**哪些数据能进模型。**

这里最容易出事的地方，是把"能不能给 AI 看"当成一个是非题。其实它是三档：

```
┌─────────────────────────────────────────────────────┐
│ 第一档  可进                                            │
│   · 已公开的资料、公开的行业数据                        │
│   · 内部通用文档：制度、规程、模板、流程说明            │
│   · 脱敏后的业务数据（去标识化、无个人标识）            │
│   条件：可追溯来源、可标注密级                          │
├─────────────────────────────────────────────────────┤
│ 第二档  需脱敏后方进                                    │
│   · 含个人信息的记录（患者、客户、员工、供应商联系人）   │
│   · 含商业敏感的数据（价格、销量、毛利、渠道策略）       │
│   做法：去标识化 / 聚合化 / 只给摘要不给原始             │
│   ★ 例：子女端只看健康摘要，不看原始心率数据            │
├─────────────────────────────────────────────────────┤
│ 第三档  绝对不进                                        │
│   · 受控文件与商业秘密原文                              │
│   · 依法不得外传的数据                                  │
│   · 客户/患者个人身份信息原文                           │
│   做法：不进模型；必要时在企业内私有部署、且只做检索      │
└─────────────────────────────────────────────────────┘
```

### 3.4.1 分级的判断标准：不是"重要不重要"，是"出去之后能不能收回"

很多企业的分级做不下去，是因为用错了标准——按"重要性"分，结果一二三档都有人争。

**用另一个标准会清楚得多：**

```
这份数据一旦出了厂，我还能不能把它要回来？

  能 → 第一档或第二档（脱敏后）
  不能 → 第三档（受控数据 / 个人信息原文）
```

**这个标准的好处是它不靠主观判断，靠后果判断。**

### 3.4.2 第二档的三个常见脱敏手法

| 手法 | 做什么 | 适用 |
|---|---|---|
| **去标识化** | 去掉姓名、证件号、手机号等直接标识，保留分析价值 | 人员、客户、供应商数据 |
| **聚合化** | 明细变成区间/汇总（"某区域某品类销量区间"） | 商业敏感数据 |
| **分层给摘要** | 不给原始，只给结论性摘要 | 面向不同角色的场景 |

**分层给摘要是最容易被忽略、也最有效的一种。**

> 同一个数据，不同角色该看到的东西不一样。
>
> 一个面向患者的健康陪伴场景，和一个面向内部运营的报表场景，**需要的是同一份数据的不同颗粒度**。
>
> 而"只给摘要不给原始"这个设计，**同时解决了数据最小化问题和权限边界问题**——它在技术上要求你先把数据分层，而这正是治理想推动的方向。

### 3.4.3 分级不是一次做完的，是逐场景做的

```
正确做法：
  场景 A → 只做 A 涉及的那几类数据的分级（通常 3–5 类）
  场景 B → 复用已有分级，只补新增的

错误做法：
  先做全公司的数据分级体系 → 一年后还没做完 → 场景全部停摆
```

**这和第一章 1.5 第三层（只治理第一口）是同一个原则在数据侧的应用。**

## 3.5 最小起步：只治理第一口

大纲给这一节的标题很直白——**不要一上来全量治理，先治理第一个场景要用到的那 10%**。

这一节要把它讲透，因为它是本章最容易被忽略、也最省钱的做法。

### 3.5.1 为什么"全量治理"必然做不完

```
全量治理的诉求：
  全公司的数据，全部口径，三年以上历史，全部权限梳理
        ↓
它的规模由公司决定，不由你决定
        ↓
而它交付的时间点，由 AI 项目的排期决定
        ↓
结果：AI 项目等它 → 等不到 → 妥协 → 带着脏数据硬上
        ↓
然后所有人得出结论："数据治理做不了，AI 做不了"
```

**注意最后那一句——这是最坏的结果：治理的漫长被误读成"治理没用"。**

实际上它只是**顺序错了**。

### 3.5.2 最小起步的四条做法

**做法一：以场景为圆心，而不是以部门为圆心。**

```
以部门为圆心：
  先治理财务部 → 再治理销售部 → 再治理生产部
  → AI 项目在第三年才开始受益

以场景为圆心：
  先治理"销售预测"这一个场景用到的数据（约 10%）
  → 这个季度就能跑通一个闭环
  → 闭环跑通之后，治理的方法本身也被验证了
```

**做法二：先治"被问得最多的那几个指标"。**

> 前提是**至少针对高层关心的指标进行了完整治理**——而不是全部数据。
>
> 高层关心的指标通常只有十几个。**把它们治透，比把三千张表治一半有用得多。**

**做法三：把"数据不具备"写成可决策的结论。**

```
写法一（错的）：
  "本项目需完成数据治理"

写法二（对的）：
  "本项目需要 3 个口径指标：
     ① 纯销口径 —— 现存 3 套算法，需统一，责任人：销售运营部，4 周
     ② 经销商进货 —— 数据仅到 2024 年，不足以支撑 3 年趋势，需外部数据
     ③ 终端动销 —— BI 与业务系统两处不一致，需确认权威源
   若 ①②③ 在 X 月 X 日前未达成，本项目降级为原型验证，不承诺业务结论。"
```

**写法二把"数据不具备"从一句抱怨，变成了一张有责任人、有时限、有降级方案的计划。**

**做法四：把第一口的治理成果做成"可复制的模板"，而不是一次性成果。**

```
好的第一口：
  三张清单填出来了 → 清单模板也定下来了 → 下一个场景直接套用
  → 第二个场景的治理成本是第一口的 1/4

坏的第一口：
  第一个场景靠某个能人手工整理了一堆 Excel → 下次还要重来
```

### 3.5.3 一个可以立刻用的判断表

在决定"这个场景现在做不做"时，用这张表：

| 问题 | 答"是" | 答"否" |
|---|---|---|
| 这个场景最核心的 1-3 个指标，**有唯一算法**吗？ | 继续 | **先治理口径，或换场景** |
| 需要的数据**能在 2 个系统内拿到**吗？ | 继续 | **先做取数，或换场景** |
| 关键数据的历史**够长**吗（趋势类场景 ≥ 3 年）？ | 继续 | **降级为当期判断类场景** |
| 数据**权限清晰**、知道谁能看吗？ | 继续 | **先做权限梳理** |
| 有明确的**文档来源**（制度/标准/规程）可引用吗？ | 继续 | **没有引用源的场景，RAG 无解** |
| 出错**有人认领**吗？ | 继续 | **先定责任边界（回第一章 1.4）** |

**六个"是"才启动。一个"否"，就先解决那一个"否"，或者换场景。**

### 3.5.4 最小起步的真实风险

必须说清楚它省不了什么：

```
最小起步 ≠ 降低标准
最小起步 = 把标准用在必要的地方，先形成闭环

它省掉的是：给用不上的数据做治理
它不省掉的是：第一个场景该做的治理，一样都不能少
```

**最容易出现的翻车是：拿"最小起步"当借口，把第一个场景的数据治理也省了。**

那不叫最小起步，那叫没做治理，只是没被人发现。

## 3.6 本章小结

数据准备这件事，可以压成四句话：

**第一句：数据准备是翻译，不是搬运。**

搬运的是数据文件，翻译的是业务口径——**而口径是业务部门定的**。

**第二句：三张清单，够用一整年。**

数据可用性（机器吃的）、文档治理（人查的）、反馈闭环（用错之后）。**三张表都只要一周填完，但只填第一个场景要用的那一份。**

**第三句：RAG 不是绕过治理的捷径，它是把治理的粒度从"数据表"缩小到"可检索的片段"。**

切片、混合检索、权限继承、引用溯源——**四个接口，四个治理断点。**
其中最危险的一条是权限：**"检索到"就等于"看到了"，所以权限必须落在检索之前。**

**第四句：数据分级不看重要性，看"出去之后能不能收回"。**

可进 / 需脱敏 / 绝对不进——**能收回的可以谈，收不回的别碰。**

而这一切的起点，是第一章那句话：

> **不要为 AI 治理全公司的数据，只治理 AI 马上要吃的那一口。**

## 3.7 金句墙

> **数据准备不是数据部门的事——口径是业务部门定的。**

> **搬运不会失败，翻译才会失败。而翻译的对象是口径。**

> **数据准备的失败，九成不是"数据脏"，是场景本就不该做，或做完了没人认领。**

> **一份 80 页规程切成 100 片之后，每一片都失去了它的上下文——包括"本条自 2025 年起废止"那一行。**

> **RAG 不是绕过数据治理的捷径，它只是把治理的问题从"全量"缩小到"检索得准不准"。**

> **"检索到"就等于"看到了"，所以权限必须落在检索之前。**

> **答案不带出处，在受监管的场景里等于没答。**

> **数据分级不看重要性，看"这份数据出去之后，我还能不能把它要回来"。**

> **不要为 AI 治理全公司的数据，只治理 AI 马上要吃的那一口。**

> **全量治理让企业得出"治理做不了，AI 做不了"的结论——那不是治理没用，那是顺序错了。**

> **反馈闭环没有"回流"，就只是一个抱怨箱。**
