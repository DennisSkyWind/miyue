## 9.0 一个必须先说清的问题：为什么这些东西叫"数字员工"

在讲怎么建之前，得先回答一个看起来像常识、其实很少有人认真回答的问题：

> **为什么企业里那些 AI 小应用、Agent、机器人——包括"阿飞"这一类——都被叫做"数字员工"？它们和以前建的 ERP、CRM、OA 这些数字化系统，到底有什么区别？**

这个问题的答案，**是本书全部方法论的起点**。

因为如果搞混了这两件事，后面所有的做法都会走偏：

- 搞混了 → 你会**给每个数字员工建一套系统**，然后被 IT 成本和运维拖死（这是 8.2 那张表里"46 个计划做"排不下去的深层原因之一）；
- 搞混了 → 你会用**评估系统的方式**去评估数字员工（看它有多少功能、覆盖多少模块），而应该用**评估岗位的方式**去评估它。

### 9.0.1 先看传统数字化系统长什么样

ERP、CRM、OA、SRM……这些系统的形态，经历过这轮数字化的人都很熟悉，它们有非常一致的骨架：

```
        ┌─────────────────────────────────────┐
        │        一套完整、独立的系统            │
        │                                     │
输入 ──►│  业务数据录入                          │
审批 ──►│  多级审批流转                          │
  业务 ──►│  规则校验 / 状态机 / 权限控制            │
  输出 ──►│  报表 / 台账 / 归档                    │
        │                                     │
        └─────────────────────────────────────┘
                    │
              统一登录
                    │
              同一个界面
              同一个入口
```

**三个特征极其鲜明：**

1. **它是一套完整闭环。** 一件事从输入到审批到归档，全在这套系统里做完，**它自己带走了整个业务环节**。
2. **它是独立王国。** 有自己的用户体系、自己的菜单树、自己的权限模型、自己的登录页。**员工要进入它，必须先登录它。**
3. **它是单一场景的产物。** 一个系统解决一个或几个明确的管理闭环——采购的闭环在 SRM 里，销售的闭环在 CRM 里，**每个闭环各自成系统**。

> **一句话概括传统数字化系统：它是按"业务闭环"切出来的垂直烟囱。**

### 9.0.2 再看数字员工长什么样

现在换一个视角。

一个数字员工——比如负责合同审核的那个，负责智能问数的那个，负责物料检测异常分析的那个——它在企业里实际的样子是这样的：

```
   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
   │   OA     │   │   CRM    │   │  FSSC    │   │   SAP    │
   └────┬─────┘   └────┬─────┘   └────┬─────┘   └────┬─────┘
        │              │              │              │
        └──────────────┴──────┬───────┴──────────────┘
                             │
                    ┌────────┴────────┐
                    │   数字员工        │
                    │                 │
                    │  · 取数          │
                    │  · 比对          │
                    │  · 判断          │
                    │  · 起草          │
                    │  · 留痕          │
                    └────────┬────────┘
                             │
              穿插在业务节点上，做岗位该做的事
```

**三个特征同样极其鲜明，而且正好是上一段的镜像：**

1. **它不带走业务环节，只干活。** 合同还在 OA 里走，付款还在 SAP 里跑。**数字员工插在环节之间，做的是"某个岗位该做的那部分工作"**，而不是自己成为一个新的业务闭环。
2. **它没有界面。** 员工不需要登录它、不需要从菜单里点进它。它**出现在原本就有的界面里**——OA 的审批页、SAP 的订单页、CRM 的客户页。它甚至没有入口，因为**它的入口就是别人的入口**。
3. **它按岗位切，不按业务闭环切。** 一个数字员工对应**一个岗位的一段工作**，而不是一个模块。

> **一句话概括数字员工：它是按"岗位"切出来的横向能力，穿插在多个系统的业务节点之间。**

### 9.0.3 五个关键差别

把两边的差别摊开，一共五条，每一条都很致命：

| # | 维度 | 传统数字化系统（ERP/CRM/OA） | 数字员工 |
|---|---|---|---|
| **1** | **建设逻辑** | 按**业务闭环**垂直切分，一个闭环一套系统 | 按**岗位工作**横向切分，一个岗位一个数字员工 |
| **2** | **与业务的关系** | **自己带走一个完整环节**（输入→审批→归档全在里面） | **穿插在别人的环节之间**，自己不形成闭环 |
| **3** | **用户入口** | 有独立登录页、统一菜单、独立界面 | **没有入口**——它的入口是 OA/SAP/CRM 里原有的那个按钮 |
| **4** | **系统边界** | 垂直烟囱，系统之间靠接口对接、边界清晰 | **跨系统、跨环境、跨交互**，天然横跨多个系统 |
| **5** | **评估方式** | 看功能覆盖、模块数、流程闭环完整度 | 看**它替的那个岗位省了多少、担了多少责** |

**第 4 条是数字员工最独特的地方，也是最容易被低估的地方。**

传统系统之间的边界是**清晰的**——ERP 到 CRM 要走接口，接口挂了就是挂了，出问题好定位。

数字员工的边界是**模糊的**——它同时在 OA、CRM、FSSC、SAP 里取数、比对、写入。**它的价值恰恰来自这种模糊；它的风险也恰恰来自这种模糊。**

> **传统系统出问题，锅在系统。数字员工出问题，锅在岗位。**

这就是为什么第九章后面要花大力气讲"它替代的到底是哪个岗位"。

### 9.0.4 为什么这个区别决定了做法完全不同

上面五条差别，往下推，会推出**完全相反的两套做法**。这是本章存在的理由：

| 如果你把它当**系统**建 | 如果你把它当**员工**建 |
|---|---|
| 先做需求调研 → 出功能清单 → 设计界面 → 写代码 → 联调 → 上线 | 先定**岗位** → 说清它替的是谁、担什么责 → 划数据边界 → 定它在哪几个节点上干活 → 再谈技术 |
| 评估用"功能覆盖率、模块完成度" | 评估用"**这个岗位原来要几个人几天，现在多少**" |
| 推广靠"这个系统上线了，请大家登录试用" | 推广靠"**你原来那件活，现在交给它了**" |
| 需求方是 IT 部门 | **需求方是那个岗位的负责人** |
| 失败信号：功能没做完 | 失败信号：**功能都做完了，但没人用它** |

**左边那一列，几乎所有企业都在走。**

所以才有了那个刺眼的现状：系统一个接一个上线，业务部门用得都不深，每个系统都有点用但没有一个真正离不开——**因为它们是被"建"出来的，不是从岗位上"长"出来的。**

### 9.0.5 怎么识别自己在坑里

三道题，答错就说明你还在按系统思维看数字员工：

1. **如果你要给数字员工做一整套系统架构图，那大概率方向就错了。** 数字员工的价值恰恰在于它**不需要**一套独立系统。
2. **如果你的数字员工有自己的登录页和主菜单，那它已经变成系统了。** 它的入口应该是 OA 审批页上的那个按钮。
3. **最关键的一题**：**你说得清"这个数字员工替代的是哪个岗位的哪一段工作"吗？** 说不清 —— 那你做的不是数字员工，是一个没有主人的机器人。

第三题是全章的判卷标准。**说不清岗位的数字员工，没有资格进入管理体系。**

### 9.0.6 正确做法：先写岗位说明书

**在讨论任何技术方案之前，每个数字员工必须先有一张"岗位说明书"。** 这是本章所有制度的地基：

| 项 | 内容 | 示例（脱敏） |
|---|---|---|
| **岗位名称** | 它替的是哪个岗位 | 合同审核初审岗 |
| **原岗位工作** | 这个岗位原来具体做什么 | 法务逐字审合同、核对条款、比对 OA 表单金额 |
| **数字员工做什么** | 承接其中哪几段 | 一级初审（合法性/金额合理性/敏感词识别）+ 表单字段自动比对 |
| **数字员工不做什么** | 明确不承接的 | 不做最终审批、不签字、不出具法律意见 |
| **在哪些节点** | 穿插在哪些系统的哪些环节 | OA 合同审批流的"一级审核"节点 |
| **人机分工** | 什么由人担责、什么由它担责 | 它出意见+留痕，人做二级审核并签字 |
| **岗位价值** | 这个岗位的成本、工时、差错率 | 效率提升幅度、年省金额、漏检率变化【待核实：缺基数】 |

**这张表有三个好处：**

1. **它把"AI 项目"翻译成了"岗位改造"**——后者是业务负责人的语言，前者不是；
2. **它天然带出边界**——"不做什么"和"在哪些节点"两栏，就是后面 9.4 的权限设计输入；
3. **它天然带出验收标准**——"岗位价值"那栏，就是这个数字员工的成功判据。

> **金句**
>
> **「数字员工不是一套新系统，是一个新岗位；先写岗位说明书，再谈技术方案。」**

### 9.0.7 一个具体例子：从"上系统"到"配岗位"

用素材库里那个效果最完整的案例（AI 合同智审）走一遍：

**如果按系统思维做：**
> 调研合同审核流程 → 提炼功能清单（合同解析、风险识别、字段比对、印章核验、报告生成）→ 设计界面 → 开发 → 与 OA 做接口对接 → 上线 → 培训 → 推广

**如果按岗位思维做：**
> ① 这个岗位原来是什么？——法务/审核岗，逐字审合同，一级人工识别风险 + 二级人工与 OA 表单逐条比对。
> ② 它承接哪几段？——一级初审 + 表单字段比对。**二级审核和签字不接。**
> ③ 插在哪个节点？——OA 合同审批流的"一级审核"节点，不另开入口。
> ④ 边界？——不出具法律意见、不做审批决策；所有意见留痕可追回原文依据。
> ⑤ 岗位价值？——效率提升 50%~96%、年度效益可核算（金额按作者要求不出书）、漏检风险降 30% 以上【待核实：三个数均缺基数】
> ⑥ 人机分工？——它出意见，人签字。**签字的人对结果负责。**

**同一件事，两种路径的差别在于：**

- 第一种，需求方是 IT，验收标准是"功能是否可用"，失败信号是"接口没调通"；
- 第二种，需求方是**审核岗负责人**，验收标准是"这个岗位的工时和差错率变了没有"，失败信号是"做完了但没人敢用"。

**而真正让这个案例落地的，恰恰是第二种路径里的一句设计：**
> 一级审核由 LLM 以法律专家身份做条款合法性、金额合理性、敏感词风险识别，**生成审核意见嵌入 OA 表单**。

**"嵌入 OA 表单"——这五个字就是"数字员工不是系统"的全部含义。**

## 9.1 为什么数字员工要单独立一章

前面八章反复出现同一个词：**数字员工**。

但到目前为止，它在书里一直是个"技术名词"——一个 RPA 机器人、一个 Agent、一个智能体。

而当你真的把它**当人一样建起来**——给它名字、给它形象、给它边界、给它职责、给它制度、给它宣传——你会发现一件反直觉的事：

> **这一步不是包装，是落地的前置条件。**

理由很硬：

- 一个**没有名字**的工具，员工不会记住它，也不会有归属感，用完就忘；
- 一个**没有形象**的工具，跨部门传播时无法被指认（"让那个审合同的看看"比"让数字员工A-合同看看"传播成本低十倍）；
- 一个**没有权限边界**的工具，不敢接核心业务，因为它随时可能被当成数据泄露源；
- 一个**没有制度**的工具，无法被推广，因为没人敢为它签字；
- 一个**没有宣传**的工具，永远只有技术团队知道它存在。

**这五件事（IP、VI、匿名/边界、范围与场景、管理体系与制度、宣传）合起来，就是"把 AI 变得更人性化"的全部内容。**

而人性化的目的只有一个：**让更多员工和领导理解，未来的工作方式是"人 + 数字员工"的协同，而不是"人对抗 AI"。**

这一章讲的，就是怎么把这件事落地。

## 9.2 IP 设置：先回答"它是谁"

### 现象

很多企业做数字员工，第一件事是取名。然后就卡住了。

因为"取名字"这个动作背后其实藏着四个必须回答的问题，而 90% 的企业只回答了第一个。

### 为什么会这样

我们来看一份**真实的、已经跑起来的**数字员工管理规范。这套规范出自某大型药企的《数字员工管理指南 V1.0》，它对命名的规定是这样的：

> **命名规范**：采用「企业品牌简称 + 功能定位关键词」组合命名，**禁止部门自行添加后缀**（如 "- 财务版""小某某"）。
>
> **示例**：数字员工A（企业简称 + "智能知识管理"定位）；数字员工B（某文化业务品牌 + "智能创作"定位）。
>
> **版本管理**：迭代版本需在命名后用数字标注（如 "数字员工A 2.0"），重大功能升级需经数字化中心审批。

这四条规则，每一条都在回答一个 IP 层面的问题：

| 规则 | 回答的问题 | 不这么做的后果 |
|---|---|---|
| 品牌简称 + 功能定位 | **它是谁** | 名字不统一，集团层面认不出这是"我们的"数字员工 |
| 禁止部门自行加后缀 | **它归谁** | 各部门各叫各的，最后产生"机器人重名/撞名"，管理层完全失控 |
| 品牌 vs 功能二段式 | **它对外代表什么、对内干什么** | 面向外部客户的名字必须过品牌审核，面向内部的必须能说明职责 |
| 版本号 + 升级审批 | **它现在长什么样** | 改了功能不换号，业务方手里的文档、口头称呼、界面入口全部对不上 |

**这条规范最狠的一句是"禁止部门自行添加后缀"。**

它背后的判断是：**数字员工的 IP 是集团资产，不是部门私产。** 一旦允许部门自己加后缀，三个月后你会有"数字员工A-财务版""数字员工A-财务部版""数字员工A财务"三个东西，IT 管不动，管理层也说不清。

而且这个规范有个非常漂亮的细节：**命名格式本身就编码了权限边界**。看一眼名字就知道它是什么——"数字员工A"是内部保密型，"数字员工B"是外部创作型。名字本身就是身份的第一次自证。

### 怎么识别自己在坑里

1. 你能列出**公司所有数字员工的完整清单**吗？有多少个是部门自己起的名？
2. 有没有出现**同一个名字被多个部门用**的情况？
3. 业务方在口口相传时，**用的是编号还是名字**？（用编号 = 传播失败）
4. 版本升级之后，**旧的文档和截图还对得上吗**？

### 正确做法

**一张 IP 定义表，每个数字员工必填五项：**

| 项 | 内容 | 举例（脱敏） |
|---|---|---|
| **名称** | 品牌简称 + 功能定位 | 数字员工A-财务报销 |
| **定位** | 一句话说清它是什么 | 财务共享报销单据初审助手 |
| **职责** | 3~5 条核心职责 | 单据完整性校验、重复报销识别、异常打回 |
| **禁区** | 明确不能做什么 | 不做最终审批、不出纳付款、不接触薪资数据 |
| **版本** | 迭代号 + 审批记录 | 1.2，重大升级经数字化中心审批 |

**同时立三条硬规矩：**

1. **命名权集中**：只有数字化中心能批名字，部门只能提申请
2. **台账化管理**：建立《数字员工命名台账》，记录所有名称、职责、使用部门，避免重复——**这一条常被忽略，但它是防止"数字员工重名"和"功能重复建设"的唯一手段**
3. **版本可追溯**：重大功能升级必须走审批，且版本号可见

> **金句**
>
> **「名字是数字员工的身份证，不是它的营销名。」**

## 9.3 VI 设置：形象不是包装，是识别成本

### 现象

有一家企业做过一次统计：**把公司里所有 RPA 数字员工的性别、年龄、姓名偏好全部统计出来做成报表**。

这件事看起来很小，很"虚"，但它是企业数字化史上少见的、真正从"人"的角度出发的设计动作。

它要回答的是：**我们的数字员工，长什么样？**

### 为什么会这样

一个数字员工的形象（IP 视觉形象）解决四个非常具体的问题：

| 问题 | 没有 VI 时 | 有 VI 时 |
|---|---|---|
| **识别** | 截图里一堆框框，跨部门分不清谁是谁 | 一个头像就是身份 |
| **信任** | 员工不知道这东西是谁，不敢用 | 有名字有形象有职责，愿意打开 |
| **传播** | 每次宣传都要截图、做图、凑素材 | 海报、头像、KT 物料现成 |
| **归属** | 工具，用完即弃 | "我们部门的同事"，有归属感 |

更实用的一点是**VI 是物料的复利**。

在办数字员工大赛这件事上，宣传物料被拆成了一张清晰的清单：

- 前期宣传：RPA 自动化概念宣传、大赛背景与流程利好、宣传语与渠道准备
- **大赛资料包：现成文案模板、海报模板、RPA 机器人元素图**
- 厂商资源包：厂商 logo 与 IP 形象（外发版）
- 启动会：产品与场景宣讲、企业内已落地应用场景分享、**高层领导讲话并给比赛定性**
- 赛后：比赛成果与优秀队伍宣传、按项目规模安排 IT 人员部署、品牌宣传支持（公众号等）、宣传海报和文案

注意那句"**RPA 机器人元素图**"——这正是 VI 的核心作用：**它让所有物料出自同一套视觉体系，而不是每次活动临时凑图。**

还有一句更值得注意：**"高层领导讲话并给比赛定性"**。这说明在设计体系里，宣传不只是海报和公众号——**最高层的一次公开定调，其效力远超一百张海报。**

### 怎么识别自己在坑里

1. 你能说出你们数字员工的**形象设定规则**吗（性别、年龄、配色、字体）？还是每次外包设计师随便画？
2. 你的数字员工在**企业微信/OA/系统里有没有头像**？还是灰色的通用图标？
3. 你做一次内部宣传，**需要多久凑齐物料**？超过两天 = 没有 VI 资产库
4. 上一次**高层公开为 AI 站台**是什么时候？

### 正确做法

**第一步：做一次形象统计（这是最容易起步的动作）。**

把现有数字员工的性别、年龄、姓名偏好统计出来，做成一张表。这张表的价值不在数据本身，在于它**把"我们的数字员工长什么样"从模糊感觉变成了可讨论的选项**。

统计完再定三件事：

- **形象基调**：统一还是分族群？（建议统一基调 + 按职能区分色系/配饰，便于区分"内部型"和"外部型"）
- **命名偏好**：从既有名字里反推员工对数字员工的想象，避免新起一套名字风格
- **族群规划**：哪些族群是"内部保密型"、哪些是"对外服务型"、哪些是"陪伴型"——**不同族群必须视觉可区分**，因为它们的权限完全不同

**第二步：建 VI 资产库。**

固定一套：头像（多尺寸）、半身像、表情包、元素图（机器人元素/图标/线条）、海报模板、PPT 模板、KT 物料模板、名片/工牌样式。

**做到这一步的标志是：办一次活动，物料不外包也能出齐。**

**第三步：把 VI 和权限绑在一起。**

视觉区分必须对应权限区分。内部保密型和外部服务型数字员工，**头像就该不一样**——这样员工在系统列表里一眼就能看出"这个能问、那个不能问"，减少误用。

> **金句**
>
> **「形象不是给人看的，是给权限看的——员工看到头像就该知道能不能碰。」**

## 9.4 匿名与边界：数字员工的权限底座

### 现象

同样出自那份《数字员工管理指南 V1.0》，还有一组规定，这一组比命名规范更硬：

> **数字员工A（内部知识管理型）**
> - 定位：企业级保密数据管家，专注内部知识闭环管理
> - 核心职责：管理研发数据、生产工艺等保密信息，提供加密查询与分析；负责内部培训资料、合规文档的智能归类与问答
> - **禁止访问互联网，数据交互仅限企业内网系统**
>
> **数字员工B（外部创作服务型）**
> - 定位：开放式内容创作引擎，连接外部资源与业务场景
> - 核心职责：基于互联网数据生成市场宣传文案、科普内容等非涉密材料；支持产品手册图文创作、短视频脚本生成等营销场景
> - **可访问公开网络资源，但需过滤敏感信息**（如竞争对手数据）

对应的权限矩阵：

| 维度 | 数字员工A（内部型） | 数字员工B（外部型） |
|---|---|---|
| 数据访问 | 企业信息系统、数据库、质控文档 | 公开行业报告、新闻资讯、创意平台 |
| 交互范围 | 内部员工、合规审计系统 | 外部客户、营销渠道、公开平台 |
| 敏感操作 | **需双人授权**（数字化中心 + 业务部门） | **内容发布前需经品牌部审核** |

### 为什么会这样

这一节对应老周说的"**匿名设置**"——即**数字员工对外呈现时以什么身份出现、能看到什么、代表谁说话**。

但这份规范给出的答案比"匿名"两个字丰富得多，它实际上是一张**三层的边界设计**：

**第一层：网络边界。** 能不能出网。内部型**物理上禁止访问互联网**；外部型可以，但只能碰公开资源。这不是配置项的区别，这是**架构上的隔离**。

**第二层：数据边界。** 能碰哪些数据。研发数据、生产工艺、质控文档——这些是药企最敏感的东西，只能给最受限的那个数字员工。

**第三层：操作边界。** 关键动作需要谁点头。内部型的敏感操作**双人授权**（数字化中心 + 业务部门）；外部型的内容**发布前经品牌部审核**。

> **这一层是最容易被忽略、也最要命的。**
>
> 一个数字员工如果能自己访问互联网 + 接触内部数据 + 直接对外发布内容，那它就是一个**自主的数据泄露通道**，而且这个通道看起来还"很智能"。

**匿名设置的本质是回答一个问题：它做的动作，算谁做的？**

外部型数字员工生成的市场文案，最终是对外发布的。谁签的字？规范给的答案是：**品牌部审核**。也就是说——**数字员工产出，经人签字，等于员工产出。** 这条链路一旦定下来，责任归属就清楚了。

### 怎么识别自己在坑里

1. 你的数字员工，**能不能访问互联网**？这个答案是"是"还是"否"，还是"没想过"？
2. 有没有一份**权限矩阵**（谁能用、能碰什么数据、敏感操作谁批）？
3. 数字员工**对外发布的内容**，有没有一道人工审核？如果直接发出去，等于你的品牌部在替 AI 背书。
4. 出现数据泄露时，**你能说清是谁的责任**吗？

### 正确做法

**每个数字员工上线前，必须填完这张边界表：**

| 项 | 内容 |
|---|---|
| 网络访问 | 内网 / 公网 / 公网+白名单（默认内网） |
| 数据范围 | 可访问的系统、数据集、字段（默认最小集） |
| 交互对象 | 内部员工 / 外部客户 / 公开渠道 / 无 |
| 敏感操作 | 列举 + 每项的审批人（默认双人授权） |
| 对外呈现 | 实名（挂企业品牌）/ 匿名（仅显示功能）/ 半匿名（显示品牌+编号） |
| 内容审核 | 对外发布是否需人工签字（默认需要） |
| 留痕 | 谁在何时调了什么、返回了什么 |

**再加三条制度：**

1. **《数字员工命名申请表》**：新增数字员工必须提交，明确功能定位 + 命名建议 + 使用部门
2. **《数字员工命名台账》**：数字化中心统一维护，记录所有名称、职责、使用部门，**防止重复建设**
3. **违规处理有明文**：擅自命名或修改数字员工身份——**首次警告并整改，再次违规暂停相关账号权限**

第三条最值得学。很多企业的制度只有"应该怎么做"，没有"违反了怎么办"，结果就是**违规成本为零，制度自然失效**。而"首次警告、再次停权限"这个梯度设计很聪明：第一次给面子改正，第二次才真的疼，而且**不封死**——它留了一条"改正后恢复"的路。

> **金句**
>
> **「数字员工的匿名，不是让它没有身份，是让它不能替人背锅。」**

## 9.5 范围与场景：1.0 试点、2.0 覆盖、3.0 生态

### 现象

数字员工建好一个、两个之后，绝大多数企业会做同一件事：**开一个更大的会，规划"全场景数字员工"。**

然后就没有然后了。

因为"全场景"从来不是规划，是许愿。

### 为什么会这样

有一份数字人建设规划，把这件事拆成了三段，比"全场景"这种说法有用得多：

| 阶段 | 定位 | 技术 | 目标 | 场景 |
|---|---|---|---|---|
| **1.0** | **3 个基础场景试点** | NLP（自然语言理解与生成） | 通过数字人结合 NLP 模型在成熟场景下实现初步效果 | 展厅数字人、营销数字人、陪伴数字人 |
| **2.0** | **结合 IT 系统进行场景覆盖** | 多模态 + 数据治理 | 通过大模型 + 企业内部数据，**形成可胜任岗位职责的数字员工** | 营销辅助、财务辅助、差旅助手、陪伴助手、物流管理助手等 |
| **3.0** | **联合生态扩展与创新** | 多模态 + 数据治理 + IoT | 联合上下游生态伙伴推广合作方向 | 慢病管理与监测、医药看护陪伴、用户健康管家 |

这个三段法里有三个判断值得学：

**第一，1.0 阶段的目标是"在成熟场景下实现初步效果"，不是"覆盖业务"。** 展厅、营销、陪伴——都是**流程短、数据熟、风险低**的场景。

**第二，2.0 阶段的目标才升级为"形成可胜任岗位职责的数字员工"。** 注意这个措辞：**从"能对话"到"能胜任岗位"，中间隔着的不是模型，是数据治理和多模态。**

**第三，3.0 走出企业边界。** 这一步需要生态合作，技术上反而不是最难的，最难的是**你凭什么让别人愿意接你的数字员工**——所以它只能放在最后。

底座部分也同样有层次：**硬底座**（算力调度、算力切分、算子加速、全链路运维、安全防护、云边协同）+ **软底座**（知识库中台：产品手册、企业历史知识沉淀、行业知识库、企业文档；基础大模型；向量检索与重排模型）+ 数据中台与 IT 平台。

> **一个值得注意的排序**：安全防护和全链路运维在硬底座里，与算力调度并列。**不是最后补的。**

### 怎么识别自己在坑里

1. 你的数字员工规划里，**1.0 阶段有几个场景**？超过 5 个 = 不是试点
2. 你能说清 2.0 阶段**新增的技术依赖**是什么吗？说不清 = 2.0 只是 1.0 的加量
3. 每个阶段的**成功标准**是什么？如果答案是"上线了"而不是"达成了什么" → 没有阶段划分
4. 底座清单里，**安全和运维**排在算力后面还是前面？

### 正确做法

**按三段法走，每段有明确的"过门条件"：**

```
1.0（试点）  → 过门条件：场景跑通、有人每天用、数据可回流
   ↓
2.0（覆盖）  → 过门条件：数据治理过关、知识库可信、能承接岗位职责
   ↓
3.0（生态）  → 过门条件：产品化、可交付给外部伙伴
```

**并且，1.0 阶段必须严格限制场景数量。**

有一个现成的筛选思路可以借用：大赛的赛道划分本身就是一种筛选——

- **赛道一「实施落地」**：场景复杂度适中，**通过培训后参赛团队能在赛程内完成开发**。要求是"详细阐述改造前后的流程对比、设计方案、预期实现效果及其对集团运营产生的经济和社会效益分析"。
- **赛道二「创意提案」**：场景复杂、需要更强技能、**参赛团队无法在赛程内完成开发**。只提交方案，不要求开发。

这个划分很聪明：**它把"能力不够"从失败重新定义为赛道分类。** 做不出来的场景不是失败，是"创意提案"。这对保护创新热情非常有效——**一个组织最怕的是员工提了idea然后发现做不出来就不敢再提了。**

### 场景选择的一个反向标尺

大赛的评审标准里，有一条是很多企业场景评审表都缺的：

> **可复制性（10 分）：可在公司（甚至行业）同类型业务中进行复用。**

很多企业的场景评估只看"这个场景价值多大"，不看"这个场景能不能复制"。结果就是：**每个部门都做了一个高度定制、无法推广的项目，第二个部门要用只能从头再来。**

**在场景清单上直接加一列"可复制性"，比事后做推广便宜得多。**

> **金句**
>
> **「1.0 阶段做三个场景，比规划三十个场景更有价值——因为三个会逼你真的跑通。」**

## 9.6 管理体系与制度：让数字员工可以被推广

### 现象

制度写完、形象画好、场景跑通，然后呢？

然后你会遇到这个场面：你想把这个数字员工推给另一个部门，对方问三个问题——

1. 它叫什么？→ 答得上（有台账）
2. 它能干什么、不能干什么？→ 答得上（有制度）
3. **出了事谁负责？** → 答不上来

第 3 个问题答不上来，推广就到此为止。

### 为什么会这样

因为**制度的作用不是约束，是授权**。

一份《数字员工管理指南》，真正解决的是"**谁有权批准一个新的数字员工存在**"这个问题。它包含五块内容，正好是一个完整闭环：

```
① 命名规范          → 它叫什么（IP层）
② 身份与职责定义     → 它是谁、能干什么（岗位层）
③ 权限与数据边界     → 它能碰什么（安全层）
④ 新增审批机制       → 谁能让它存在（治理层）
⑤ 违规处理          → 违反了怎么办（纪律层）
```

第 ④ 条的流程是：

> 各部门如需新增数字员工，需提交《数字员工命名申请表》，明确：
> - **功能定位**（如"生产数据预测""供应链调度"）
> - **命名建议**（需符合「品牌简称 + 场景关键词」规则）
>
> **统一备案管理**：数字化中心建立《数字员工命名台账》，记录所有名称、职责及使用部门，避免重复。

第 ⑤ 条是：

> 部门擅自命名或修改数字员工身份，**首次警告并整改，再次违规将暂停相关账号权限**。

**这个"两级处理"的设计值得单独说。**

大多数企业的制度写着"严禁擅自命名"，但没有后果——**违规成本为零，制度自然失效**。而"首次警告、再次停权限"这个梯度设计很聪明：第一次给面子改正，第二次才真的疼，而且**不封死**——它留了一条"改正后恢复"的路。

### 怎么识别自己在坑里

1. 别的部门要上线数字员工时，**走的是你的审批流，还是他们自己上线了你事后才知道**？
2. 你有没有一份**台账**，能一眼看出全公司有多少个数字员工、谁在用、干什么？
3. 你的制度里，**有没有"违规怎么办"**？
4. 数字员工出问题时，**谁是你的第一联系人**？这个问题必须在制度里写死。

### 正确做法

**制度四件套（可直接进附录）：**

| 文件 | 作用 | 关键内容 |
|---|---|---|
| **《数字员工管理制度》** | 主文件 | 命名规范、身份职责、权限边界、审批、违规处理 |
| **《数字员工命名申请表》** | 入口 | 功能定位 + 命名建议 + 使用部门 + 业务负责人 |
| **《数字员工命名台账》** | 底账 | 名称、职责、数据边界、使用部门、版本、启用日期、责任人 |
| **《数字员工权限矩阵》** | 安全 | 网络 / 数据 / 交互对象 / 敏感操作审批人 / 留痕要求 |

**再加两条治理规则（很多企业没有）：**

1. **新增数字员工必须有业务侧责任人**，不能只挂在技术部门——**没有业务责任人的数字员工，半年后一定变成没人维护的僵尸**
2. **台账每季度复核一次**：把"已启用但 90 天零调用"的数字员工标记出来，要么优化要么下线

第二条尤其重要。数字员工会**只增不减**——因为下线在心理上和政治上比上线难。一年下来台账里可能有几十个僵尸。而**僵尸数字员工是安全风险，也是维护负担**。

### 宣传与推广：制度之外的另一半

制度解决"能不能用"，宣传解决"**愿不愿用**"。

现成的一条完整宣传线（来自数字员工大赛的实践）：

| 阶段 | 动作 | 关键动作 |
|---|---|---|
| 前期（1-7 天） | 概念与氛围 | RPA 自动化概念宣传、大赛背景/流程/利好宣传、宣传语与渠道准备、**报名通道准备** |
| 筹备 | 物料就位 | 文案模板、海报模板、**RPA 机器人元素图**、厂商 logo 与 IP（外发版）、大赛日程（可外发） |
| 启动会（1 天） | 造势与定性 | 产品与场景宣讲、**已落地应用场景分享**、**高层领导讲话并给比赛定性**、会议场地与参会引导 |
| 赛中 | 参与 | 各部门组队、赛程推进、评审 |
| 赛后 | 转化与扩散 | 优秀场景选题成果转化实际应用落地、**IT 人员按项目规模部署**、比赛成果与优秀队伍宣传、品牌宣传支持（公众号）、宣传海报与文案 |
| 长期 | 沉淀 | 优秀场景持续推广、复制到同类业务 |

**三个最值得注意的点：**

**① 启动会讲"已落地的应用场景"，而不是讲技术。** 老员工能立刻看懂"这个已经有人在用了"——这是最强的说服力。

**② 高层领导讲话并给比赛定性。** 这一步是把"部门活动"变成"公司级信号"。**没有这一步，宣传做得再好也只是自娱自乐。**

**③ 赛后要跟"IT 人员部署"。** 宣传和交付之间必须有承接，否则大赛结束就断档——**赛后就没人用的数字员工，是最伤的失败。**

还有一个数据值得记：某大型药企**首届**数字员工大赛，**集团六大一级部门全员参与，36 支队伍报名、33 支投入实战**，其中生产/质量/EHS 一级部门以 14 支参赛队伍成为"主力军"。

这个分布很说明问题：**报名最多的是离制造最近的部门**（提质、降本、增效的诉求最迫切），而不是技术部门。这正是第一章讲的"别从全员培训开始"的另一面印证——**真正会报名的是那些最痛的人。**

> **金句**
>
> **「制度给数字员工发户口本，宣传给它办入职仪式——两个都缺，它就是个没人认领的账号。」**

## 9.7 让 AI 变得更人性化：这一章真正想说的话

### 现象

我们把 IP、VI、边界、场景、制度、宣传六件事讲完了。但它们各自看都很"细碎"——为什么值得单独立一章？

因为它们合起来指向同一个结论，而这个结论是全书前八章都没说过的：

**数字化协同的工作模式，不是"员工被 AI 替代"，而是"每个员工带着自己的数字员工工作"。**

### 为什么会这样

把老周的原话拆开：

> 数字化包含自动化和 AI，即数字员工；它可通过交互获取数据并自动执行任务，**让员工提炼自身技能**，以此方式建立。

这句话里有两个关键词，是整本书的落点之一：

**第一个是"交互获取数据"。** 数字员工不是后台批处理，是**有来有回**的。它先问你要什么、你要给它什么、它的边界在哪。**这个"交互"过程本身，就是一次岗位建模。**

**第二个是"让员工提炼自身技能"。**

这句话很重。它意味着：员工在跟数字员工磨合的过程中，会被迫想清楚——**我这件事到底是怎么做的？我凭什么比它做得好？**

而这恰恰是**第六章「算账」和第八章「效率悖论」要回答的问题的入口**：

- 如果员工想清楚了"我的技能是什么"，那"AI 替代我"这个说法就不成立了——**AI 拿走了任务，留下了判断**
- 如果员工提炼出了技能，那"效率红利"就有了落点——**不是空出来的时间，是更强的岗位能力**
- 如果每个员工都带着自己的数字员工，那 8.2 里那张"46 个计划做、23 个已实现"的场景清单，**就不该由一个部门去建，而该由每个岗位去建**

> **换句话说：数字员工是人机协同的载体，不是自动化工具的升级版。**

而这也回答了第一章那个最尖锐的问题——**"几百个 Agent 零价值"为什么会出现？**

因为把 Agent 当**工具**建（做完就完），价值必然是零；
把数字员工当**岗位**建（有名字、有边界、有制度、有责任人、有技能沉淀），价值才有落点。

### 怎么识别自己在坑里

1. 你能说出**你们公司哪个数字员工，是某个员工自己"带"出来的**吗？不是 IT 给的，是这个员工自己磨合出来的。
2. 你的员工用数字员工时，**是在"用工具"，还是在"带下属"**？这听起来矫情，但体感差别很大。
3. 你有没有统计过：**某个员工在跟数字员工协作后，他自己的岗位能力发生了什么变化**？如果从来没有被观测过，那"提炼技能"就只是口号。

### 正确做法

**把数字员工的运营目标，从"上线数量"改成"岗位能力增量"。**

具体三个动作：

**① 每个数字员工配一个"带它的人"。** 不是管理员，是**使用它的岗位上的那个人**。他的工作是：提需求、喂数据、纠错、然后**把自己的方法论沉淀进去**。这才是"提炼自身技能"的具体机制。

**② 建"人机分工表"，而不是只建"场景清单"。**

| 环节 | 人做什么 | 数字员工做什么 |
|---|---|---|
| 数据获取 | 定义口径、判断数据可不可信 | 交互式获取、对齐口径、标记缺失 |
| 规则判断 | 处理例外、担责签字 | 执行确定性规则、标记不确定项 |
| 方案生成 | 选择路径、评估取舍 | 生成候选、给出依据 |
| 执行落地 | 授权、沟通、异常处理 | 自动执行标准动作 |

这张表的价值：**它把"AI 会不会取代我"这个恐惧问题，变成了"我和它怎么分工"这个管理问题。**

**③ 宣传的对象，从"数字员工"转向"人和数字员工一起工作"。**

大赛、海报、公众号、内部宣讲——**主角应该是"某个员工和他的数字员工"，而不是"某公司上线了 N 个机器人"。**

前者有代入感，后者只有数字。

> **金句**
>
> **「数字员工的终点不是替人干活，是让人从干活的人变成会带数字员工的人。」**

## 9.8 本章小结

1. **数字员工不是系统，是岗位。** 传统系统按业务闭环垂直切、自己带走一整个环节、有独立入口；数字员工按岗位横向切、穿插在多个系统的节点之间、**没有自己的入口**。搞混了，就会给每个数字员工建一套系统，然后被成本拖死。
2. **先写岗位说明书，再谈技术。** 七个字段：岗位名称、原岗位工作、承接什么、不承接什么、在哪些节点、人机分工、岗位价值。**说不清岗位的数字员工，没资格进管理体系。**
3. **IP 与 VI 的本质是识别与授权。** 名字是身份证（要集中、要台账、要版本），形象是权限标识（要跟权限绑定），边界是安全底线（网络 / 数据 / 操作三层）。
4. **场景要三段走，1.0 只做三个。** 试点跑通 → 结合 IT 系统覆盖 → 生态扩展；2.0 的门槛是数据治理和多模态，不是模型。
5. **制度给户口本，宣传给仪式，两者缺一不可。** 制度要有"违规怎么办"，宣传要有"高层定调"和"赛后部署承接"。
6. **最终目标是让员工从"干活的人"变成"会带数字员工的人"。** 这才是数字化的协同工作模式，也是效率红利能兑现的落点。

> **本章整体金句**
>
> **「数字员工不是把 AI 做得更像人，是把人的工作重新定义一遍。」**
