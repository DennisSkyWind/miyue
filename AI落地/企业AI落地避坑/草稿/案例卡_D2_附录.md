# 附录　可脱敏案例卡（8 张）

> 用法：D3「案例库」直接取用。每张卡 = 场景 / 痛点 / 做法 / 结果 / 教训。
> 数字纪律：无一手出处的效果数字一律写「【待核实】」，宁可空着，不可推算。
> 脱敏：产品名 → 「某核心中成药」；系统名保留通用名（SAP/CRM/OA/FSSC/KDIP）；金额已模糊化。

## 案例卡 01　物料采购合同 AI 审核（**全库唯一效果三要素齐全的案例**）

| 项 | 内容 |
|---|---|
| **场景** | 物料采购合同审核（四大合同类型：服务类、框架类、物料类、资产类 + 非固定版本销售协议） |
| **痛点** | 合同审核高度依赖法务逐字人工；条款引用易出错、漏检无留痕；审核周期长，直接卡住采购与生产物料到位 |
| **做法** | 两阶段推进：**阶段一「法律智审」**——四大合同类型全部上线；**阶段二「关键字段智能核对」**——字段自动提取、差异项自动标注，正在推广至其他合同类型。同时配套印章完整性核验工具：Trae 平台 + Python + 计算机视觉，自动扫描 PDF/Word 每一页，识别公章、区分骑缝章、OCR 深度识别印章内容。治理上走「事前 AI 智审嵌入 → 事中 AI 批量巡检 → 事后 AI 批量跟进整改」闭环 |
| **结果** | 效率提升 **50%~96%**；年省约 **6~13 万元**；漏检风险降低 **30% 以上**（以上为本企业实测口径，32 号）。**注：三个数字的基数（原有工时/漏检率原值）未在素材中记录 →【待核实】** |
| **教训** | ① **AI 合同审核的价值不在"审得更严"，在"审得更快且能留痕"**——漏检风险的下降才是法务真正买单的理由；② 印章核验这类"最笨的活"（逐页翻看）反而是 AI 最稳的切入点，**先做确定性高、可量化的场景，再碰需要判断力的条款**；③ 阶段化推进（先法律智审、再字段核对、再扩类型）比一次性铺开更可控 |

> **书稿用法**：这是第八章「真实案例复盘」的**头号案例**，也是第六章「算账」的唯一完整样本。

## 案例卡 02　数字员工智能问数 + 客服

| 项 | 内容 |
|---|---|
| **场景** | 营销中台：业务人员用文字或语音直接问内部数据与制度 |
| **痛点** | 移动端数据查询受限，业务人员"用数不友好"；业务与制度问题无快速获取通道，只能人工问答，信息获取效率低。需求方原话：「提问前后**缺少逻辑关系**，不好回答」 |
| **做法** | 数字员工智能问数（问「某事业部某省 1 月纯销多少」「哪个产品销量/达成率/增长率最高」）+ 数字员工客服（汇总常见业务问题与制度资料，全公司问答式获取，如「如何合规地开通数据权限」）。底层是 1.0 起累积的 **90+ 业务知识学习模块**（问答对、药品管理法规、GMP 附录等），1.0 阶段确立的分工机制：外部问题由陪伴IP 多轮对话、内部知识由数字员工A 精准匹配文档 |
| **结果** | 该需求在台账中标注为 **价值高 / 紧急**（12 条高价值需求中占 2 条），已随 2.0 版本上线并嵌入 OA/KDIP/CRM/FSSC 四大系统。**调用量口径见 933 次【待核实：统计区间】** |
| **教训** | ① **问数类场景的成败不在模型，在口径**——"哪个产品增长率最高"这种问题，前提是纯销/发货/达成率三套口径已经对齐；口径没对齐，模型越强错得越离谱；② **问数 + 问制度必须分开建设**：问数依赖数据打通，问制度依赖知识治理，两者的瓶颈完全不同 |

## 案例卡 03　AI 销售预测与库存优化（预测试点）

| 项 | 内容 |
|---|---|
| **场景** | 单一品种 AI 销售预测试点（实施计划书已成文，39 号） |
| **痛点** | 三大病灶写得很实：**数据孤岛**（销售、库存、市场数据分散）、**数据滞后**（某降压药案例因数据滞后 48 小时导致旺季断货、淡季积压）、**流程低效**（人工经验调整占比 30%，月度预测周期 7 天，季度目标达成率波动 ±18%） |
| **做法** | 分阶段模型策略；目标单一品种 12 个月销售预测误差率 ≤10% |
| **结果** | 目标值与痛点基线已明确（误差率 ≤10%、预测周期 7 天 → 目标缩短、达成率波动 ±18% → 目标收敛），**实际达成数据尚无 →【待核实】** |
| **教训** | ① **这是全书"AI 不是万能药"最好的反例**：单个场景的预测误差率 10% 听着不高，但在 7 天预测周期、±18% 达成率波动的基线下，它只够**辅助**决策，替代不了人——AI 落地的诚实定位是"把 30% 的人工经验调整压下去"，不是"取代预测"；② **48 小时数据滞后比模型精度更致命**，这正是第三章「数据准备」要讲的：数据治理的投入产出比高于模型调优 |

## 案例卡 04　AI 物料检测数据异常分析

| 项 | 内容 |
|---|---|
| **场景** | QC 实验室：物料检测数据的关联分析与异常识别 |
| **痛点** | 检测数据分散，异常发现依赖人工逐项比对，效率低且易漏；异常根因定位难 |
| **做法** | 借助 AI 对相关物料检测数据进行关联，识别异常数据并找出原因 |
| **结果** | 台账标注 **价值高 / 紧急**（12 条高价值需求之一，QC 侧价值最高的一条）。**实际效果数字未记录 →【待核实】** |
| **教训** | ① **质量场景的 AI 价值不体现在"检得快"，体现在"漏得少"**——GxP 体系下漏检的代价远高于提效；② 但 AI 在质量域的输出**必须可追溯到原始检测记录**，否则不可用于放行决策——这是第七章合规章的入口 |

## 案例卡 05　财务共享 RPA 推广

| 项 | 内容 |
|---|---|
| **场景** | 财务共享领域 RPA 系统推广（一期） |
| **痛点** | 财务业务自动化诊断写得很直白：**高重复性手工操作占比财务工作量 60%+**、**流程断点多（人工干预率超 40%）**、**系统间数据孤岛（接口缺失率超 60%）** |
| **做法** | 三段路径：**短期（0-3 个月）** 优先落地银行对账、发票处理等确定性高的场景；**中期（3-12 个月）** 构建 RPA 卓越中心（CoE），开发 50+ 标准化流程；**长期（1-3 年）** 走向流程智能进化（数字员工自主优化工作流）。同期开展 RPA 训练营，学员初级工程师认证、带教需求完成实施 |
| **结果** | RPA 系统上线（一期）**已完成**，2025-09-30 计划与实际完成同日；RPA 训练营 **已完成**（培训 37 人次）；财务月结场景在数字员工大赛中已有参赛项目。**上述 60%+ / 40% / 60% 三个基线数字的统计口径未记录 →【待核实】** |
| **教训** | ① **RPA 不是落后方案，是"确定性场景的最优解"**——银行对账这种有明确规则的活，用 RPA 比用大模型便宜十倍且可审计；② **CoE（卓越中心）模式比"每个部门自己搞"更可持续**，因为 RPA 的真正成本不在开发，在维护；③ 三段路径里最该抄的是短期那段：**先做确定性高的，别一上来就谈"流程智能进化"** |

## 案例卡 06　采购价格预测（某核心中成药）

| 项 | 内容 |
|---|---|
| **场景** | 采购领域：某核心中成药价格预测模型 |
| **痛点** | 为实现科学决策支持，需构建重点产品（某核心中成药）的价格预测能力；系统需根据当前排产计划、仓储数据、销售数据综合判断 |
| **做法** | 完成价格影响因子数据收集 → 模型上线 → 持续优化（调优后预测偏差率需符合模型评估要求） |
| **结果** | 模型上线里程碑**已完成**；「模型持续优化」里程碑**进行中**，计划完成时间 2025-11-30，**当前实际状态 →【待核实】**。台账中该需求价值标低、紧急度标一般 |
| **教训** | ① **采购价格预测是"数据密集型"而非"模型密集型"**：难点在影响因子数据的收集与持续更新，不在算法；② 注意一个反常识的信号——**台账里它被标为"价值低/一般"**，但它却是已完成度最高的项目之一，这提示：**需求方自己填的价值和紧急度，未必反映真实优先级**，这正是第 2 节"伪紧急占 44%"的另一层注脚 |

## 案例卡 07　设备智能监控与运行情况分析

| 项 | 内容 |
|---|---|
| **场景** | 制造领域：设备智能监控及运行情况分析（含智慧灯检项目、能源数据采集分析） |
| **痛点** | 设备运行状态依赖人工巡检与经验判断，能耗与工艺问题事后归因难；视觉检测环节人工作业效率与一致性受限 |
| **做法** | 能源侧先做**底层数据采集仪表的更新与部署**（精益能源管理系统项目立项）；设备侧走**蓝图设计 → 系统测试（问题清单 + 整改清单 + 操作手册 + CSV 验证资料）→ 生产环境上线**的标准四步 |
| **结果** | 蓝图设计确认及汇报**已完成**（签字版蓝图）；系统测试与设备管理系统生产环境上线**进行中**（计划 2025-11-14）；智慧灯检项目处**商务阶段 / 设备调试与验证中**。**实际运行指标未记录 →【待核实】** |
| **教训** | ① **制造场景的 AI 前面一定站着一个 IoT**——能量数据的价值不在分析，在采集；采集没做，AI 就是无米之炊；② 设备类项目**必须走 CSV 验证**，否则在 GxP 环境下根本没法上线——这是第二章"合规不是刹车，是路线"的最佳例证 |

## 案例卡 08　印章完整性核验（**最朴素也最成功的一个 AI 工具**）

| 项 | 内容 |
|---|---|
| **场景** | 法务、合规、行政、档案审核场景：批量文档的印章完整性核验 |
| **痛点** | 印章是合同、协议与公文的效力核心凭证，但长期依赖人工逐页翻看——**效率低、易漏检、无留痕**（原文表述） |
| **做法** | 采用 Trae 平台 + Python + 计算机视觉：自动扫描 PDF / Word 文档每一页，精准识别公章、区分骑缝章（骑缝章是横跨多页、单个页面无法判断的关键难点），并用 OCR 深度识别印章内容 |
| **结果** | 工具已建成并在数字员工大赛中作为参赛项目落地。**准确率/漏检率数字未记录 →【待核实】** |
| **教训** | ① **最好的 AI 场景往往不是最"AI"的那个**——印章识别没有大模型、没有 Agent，纯 CV + OCR，却是最容易证明价值、最不容易出错、最快能上线的场景；② **"区分骑缝章"这一句，是全书讲技术选型时最该给读者看的一个细节**：业务里真正难的不是模型能不能识别，是**你知不知道业务上什么叫做对**；③ 这也是"AI 项目最容易的启动点"——**从最烦、最机械、最没人愿意干的活开始** |

## 案例卡使用纪律

1. **不得把设计目标写成已实现**：案例卡 03 的「误差率 ≤10%」、案例 01 的三个效果数字，前者需核实状态，后者需核实基数，核实前一律带 `【待核实】`。
2. **不得给案例补"失败教训"**：凡素材未记录的，一律留空。老周口述或真实复盘后才能补。
3. **同一案例不重复使用**：8 张卡分别对应数据、场景、算账、治理四个主题的落点，第二章场景全景时用卡 02/03/04/06/07/08，第六章算账用卡 01/05，第八章复盘用卡 01/03/05/08。
4. **案例卡是「骨架」，正文还要加"过程"**：痛点→做法之间缺的那段（怎么立项、谁拍板、踩了什么坑），**必须由老周口述补齐**，否则案例读起来像产品手册而不是复盘。这正是 D3 的核心任务。
