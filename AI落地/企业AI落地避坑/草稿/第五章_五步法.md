## 5.0 本章要回答什么

第二、三、四章分别解决了**选事**、**备料**、**选型**。但这三件事做完，项目通常还没开始被使用。

真正卡住项目的，是从"方案通过"到"真的有人每天用"之间的这段路。这段路上有一系列决定项目生死的事，而它们**很少出现在项目计划里**：

```
方案通过了 → 谁先用？用多久？拿什么算成功？
         → 什么时候该停？
         → 谁来维护它？
         → 谁授权它？
         → 高层自己用不用？
```

**这一章把这六个问题按顺序摆出来。**

顺序很重要，因为它对应一条真实的推进链：

```
步骤1 场景梳理   →  步骤2 数据准备评估  →  步骤3 技术方案选型
   ↓                                        ↓
（做对的事）                          （用对的技术）
                                            ↓
                              步骤4 试点验证 ←★ 全书写"避坑"的关键
                                            ↓
                              步骤5 规模化推广
                                            ↓
                        ★ 两个必须单独讲的专节
                     高管怎么接 AI ／ 助手的边界在哪
```

## 5.1 步骤一：场景梳理（承接第二章）

这一步的目标不是"选一个场景"，而是**把第二章那三个问过的问题，变成一张可以开工的清单**。

```
场景清单（第二章产出）
        ↓ 加三列
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ 场景          │ 做错了谁赔    │ 现在人工怎么做 │ 谁的工作方式会变│
├──────────────┼──────────────┼──────────────┼──────────────┤
│ ……           │ ……           │ ……           │ ……           │
└──────────────┴──────────────┴──────────────┴──────────────┘
        ↓ 收敛
     1–2 个场景
```

**为什么是 1–2 个，不是 5 个：**

```
同时推 5 个场景的结果：
  每个场景分到 1/5 的注意力
  每个场景都只做到"能演示"
  5 个都不能复制
        ↓
  一年后：5 个 POC，0 个能推广的东西
```

而推 1–2 个的结果：

```
一个场景做透 → 拿到可复制的路径 → 第二个场景成本减半
```

**这一节唯一需要强调的是"收敛"这个动作。**它看起来只是砍需求，实际上是本章第一道防线：

> **清单上的场景越多，越容易出现"每个都做一点、每个都没成"的结局。**
> **而这种结局最致命的不是失败，是它会让组织相信"AI 这条路走不通"。**

## 5.2 步骤二：数据准备评估（承接第三章）

这一步的目标是**判断"现在能不能做"**，不是"把数据治理完"。

第三章那张判断表在这里直接用：

| 问题 | 答"是" | 答"否" |
|---|---|---|
| 核心指标有唯一算法吗？ | 继续 | 先治理口径，或换场景 |
| 数据能在 2 个系统内拿到吗？ | 继续 | 先做取数 |
| 历史够长吗（趋势类 ≥ 3 年）？ | 继续 | 降级为当期判断类 |
| 权限清晰吗？ | 继续 | 先做权限梳理 |
| 有可引用的文档来源吗？ | 继续 | RAG 无解 |
| 出错有人认领吗？ | 继续 | 先定责任边界 |

**六个"是"才启动。**

这一步的产出是三样东西，缺一不可：

```
1. 数据可用性清单（这个场景要用的那一份，不是全公司的）
2. 文档治理清单（这个场景会引用的制度/规程，逐份确认所有者、版本、生效期、密级）
3. 风险与降级方案（拿不到的数据怎么办、结论降到什么程度）
```

**第 3 样最常被漏，也最关键。**它决定了当数据不到位时，项目是**降级**还是**卡死**。

> 【待核实】本章未引用具体场景的清单实例。若作者愿提供一份真实项目的清单样例（含脱敏），本章说服力会显著提升。

## 5.3 步骤三：技术方案选型（承接第四章）

这一步的产出不是"选了哪个模型"，而是**一份带约束的技术方案**：

```
┌─ 数据边界 ───────────────────────────────┐
│  哪些数据出廠？哪些不出？                  │  ← 第三章 3.4
│  权限在哪一层过滤（检索前 / 生成后）？        │  ← 第三章 3.3
├─ 形态 ──────────────────────────────────┤
│  内部 Copilot / 流程内嵌 / 对客服务          │  ← 第四章 4.4
├─ 能力 ──────────────────────────────────┤
│  RAG / 微调 / Agent 的组合与边界            │  ← 第四章 4.2
├─ 留痕 ──────────────────────────────────┤
│  每次调用的输入、输出、版本、责任人           │  ← 第七章 7.3
└─ 兜底 ──────────────────────────────────┘
   置信度不足怎么办？无来源怎么办？人怎么确认？
```

**注意最后两项。**技术选型最容易被写成"选了什么"，而真正决定项目能不能过合规评审的，是**留痕与兜底**。

**这一步最容易出的错，是把技术方案当成采购方案来做。**

```
采购视角：找功能最强的、最好演示的、最便宜的
方案视角：先定边界（数据/权限/留痕/兜底），再在边界内选能力
```

**第三章讲过的那句话在这里适用：先想"不做什么"，再想"用什么做"。**

## 5.4 步骤四：试点验证 ★

**这是全书写"避坑"的关键一节。**

因为前面三步都还在纸面上，而这一步是**第一次让真实的人、真实的业务、真实的错误来检验前面所有的推理**。

而大多数项目的试点是这样做的：

```
选一个部门 → 培训两小时 → 扔一个工具过去 → 三个月后问"用得怎么样"
        ↓
   "还行吧"
        ↓
   然后就推广了，然后就没有然后了
```

**这套做法有三个致命缺陷：没有范围、没有指标、没有止损。**

### 5.4.1 灰度范围：谁先用，决定了试点能证明什么

试点的范围不是"随便挑个部门"，而是要同时满足三个条件：

```
┌──────────────────────────────────────────────────────┐
│ ① 信任成本低：                                       │
│    这个部门的人，出了问题不会一纸状告到老板那里        │
│    （错得起，才试得起）                                │
├──────────────────────────────────────────────────────┤
│ ② 决策权高：                                          │
│    部门负责人自己说了算，不用来回请示                 │
│    （能拍板，试点结论才作数）                          │
├──────────────────────────────────────────────────────┤
│ ③ 业务痛感强：                                        │
│    这个部门自己就痛，不是被安排来试的                   │
│    （痛，才会用；不痛，只会配合）                       │
└──────────────────────────────────────────────────────┘
```

**这三条同时满足的部门，通常不会超过三个。**如果一个都挑不出来，说明前面场景选错了，或者这个组织的信任成本普遍过高。

> ★ 这三条来自作者对试点用人的判断。【待核实】——是否保留这组判据作为正式方法，需作者确认。

### 5.4.2 试点周期：短到能止损，长到能看出问题

```
太短（几天）→ 只看出"能不能跑通"，看不出"好不好用"
太长（半年）→ 组织热情耗尽，问题被时间磨平，止损已经来不及
```

一个可用的经验区间：

```
   4–8 周  ← 建议区间
   ├─ 前 2 周：上手期（记录卡在哪儿）
   ├─ 中间 3–4 周：真实使用期（★ 关键：必须用真实业务，不能用演示数据）
   └─ 最后 1–2 周：验收与结论期
```

**中间那段"必须用真实业务"，是试点最容易作弊的地方。**

```
真实使用期最常见的两种假象：

  假象一：用"干净"的演示数据跑 → 避开了所有真实场景的脏乱
            → 结论：可行 → 推广 → 推广后集体翻车

  假象二：由项目组代做 → 用户只要"看结果"
            → 结论：可行 → 推广 → 推广后没人会用
```

**试点必须由业务的人、在真实的业务上、用他们自己的数据做。**这条违反了，试点结论就没有意义。

### 5.4.3 验收指标：怎么设一个不会被业务"做样子"的指标

这是试点设计里最难的一件事。

**先看一种常见的失败设计：**

```
验收指标：使用人数 ≥ 10 人
        ↓
业务怎么应付：让 10 个人注册账号，打开一次
        ↓
指标达成 ✓  实际价值 ✗
```

**因为这个指标只考核"行为发生"，不考核"价值产生"，所以它必然可以作秀。**

设计验收指标的三条原则：

**原则一：指标要落在"业务结果"上，不是"使用行为"上。**

| 不合格（可作秀） | 合格（难作秀） |
|---|---|
| 使用人数 | 这个场景原来每月人工 X 小时，现在降到多少 |
| 生成条数 | 生成的结论被采纳的比例 |
| 登录次数 | 原来要 3 天的汇总，现在当天出结果且被用于一次决策 |
| 满意度打分 | 原来漏掉的差错，现在漏了几起 |

**原则二：至少留一个"反向指标"，防止为了达标而作弊。**

```
正向指标：结论被采纳率 ↑        ← 会被"只挑好说的"操纵
反向指标：人工复核发现的错误率 ↑  ← 错误被发现了，说明真的在用
```

> 一个只涨正向指标的试点，基本可以判定为"没真用"。

**原则三：指标在试点开始前就写下来，且由业务方签字确认。**

```
事后再定指标 → 指标一定会被调整成"能达到"的样子
```

### 5.4.4 止损条件：★ 什么时候该停

**这是试点最容易被跳过、也最值钱的部分。**

因为项目组天然有"再试一个月"的冲动——**而组织的时间与热情是最贵的成本。**

止损条件必须在试点开始前写好，并且是**可判定的**：

```
┌────────────────────────┬──────────────────────────────┐
│ 止损条件（示例）         │ 判定方式                       │
├────────────────────────┼──────────────────────────────┤
│ 4 周后主动使用率 < 30%  │ 从日志直接统计，无需访谈        │
│ 关键指标口径仍不统一     │ 数据可用性清单的"口径"项未关闭   │
│ 出错无责任人             │ 错误上报无人响应超过 N 次       │
│ 每次输出需人工全量重做   │ 抽样 20 条，重做比例 > 50%       │
│ 业务方要求停用           │ 一位决策者提出即可启动复核       │
└────────────────────────┴──────────────────────────────┘
```

**止损不等于失败。**这句话要写进项目制度里：

> **止损是"承认这个场景现在不成立"，不是"承认这帮人不行"。**
>
> **一个能在第 6 周止损的项目，比一个拖到第 30 周才承认失败的项目，节省的是整个组织的信任。**

**而止损之后还有一件必须做的事**：把这个场景的失败原因写进下一轮的场景清单。**止损也要产生知识。**

### 5.4.5 试点要双验

一个试点成功了，只能证明一件事：**这件事在这个部门能成。**

```
双验：
  可行性 —— 这个场景技术上做得成吗？
  可复制性 —— 这个做法能搬到别的部门吗？
        ↓
  只验可行性，不验可复制性
        ↓
  推广时才发现：它成立是因为这个部门有个能人
        ↓
  推给其他部门 → 全部失败 → 结论："AI 不行"
```

**"这个部门有个能人"是最常见的不可复制原因。**所以试点时要额外问一句：

> **这个做法里，有多少是靠这个部门的特殊条件？**
> 特殊条件包括：某个人特别厉害、某份数据特别全、某个流程本来就很规范。

**只要答案里有一句"靠某个人"，推广方案就必须先解决"这个人不在场时怎么办"。**

### 5.4.6 ★ 一个真实的试点案例：营销 AI 助手（做砸了的那一次）

> **本节与第八章 8.5 节是同一个项目的两个视角**：第八章讲"它为什么失败"，这一节讲"**试点本来应该在哪一步止损**"。
> ★ 这是作者亲历项目，素材来源 61 号（口述）。

### 案例的试点设定

```
试点对象：某大型药企营销条线的一线销售人员 + 其管理层
试点内容：两块
          ① 知识库：制度政策解读、销售政策与销售方案解读、产品信息
          ② 数据：一线随时查自己的销售数据，管理层可查下属与整体
研发方式：营销部门 + IT 部门联合研发
试点结果：★ 功能做出来了，场景没有跑起来
```

### 这个试点，四个"应该"分别落在哪

| 试点四要件 | 这个项目上的实际表现 | 差距 |
|---|---|---|
| **范围**（谁先用） | 营销一线 + 管理层 | 范围本身不算错，但**没有按"信任成本低 × 决策权高 × 业务痛感强"筛过**——一线是"被要求试"，不是"自己想试" |
| **周期** | 未见明确的试点周期设定 | 没有周期，就没有"到点看结论"的时点 |
| **验收指标** | 功能层面达成（能查、能问） | ★ **指标设在了"功能有没有"上，而不是"用户满不满意、数对不对"上** |
| **止损条件** | 未见止损线 | ★ **没有止损线，于是项目不是失败，而是慢慢死掉** |

**★ 从试点设计的角度看，这个案例暴露的不是执行问题，是四个要件里有三个没设或设错了。**

### 如果当时按第五章的方法做，三个具体动作

**动作一：验收指标要落在满足率上，不是功能上。**

```
❌ 当时的指标形态：功能做出来了，能查能问 → 通过
✅ 应该的指标形态：
   · 一线每周主动使用率 ≥ 30%
   · 数据类请求的"满足率" ≥ 50%
     （抽 20 个高频问题，系统给出的数是否就是他要的那个数）
   · 知识库类问题的一次解决率 ≥ 70%
```

**★ 这里最值得记的是"满足率"这个指标形式——它把"数对不对"变成了可抽检、可统计的东西。**而"能查"是无论如何都会达成的。

**动作二：4–8 周就要看一次结论，而不是等"系统建好"。**

```
★ 这个案例的结构性缺陷：
   知识库那半边能用 → 让人以为项目在推进
   数据那半边不对 → 让人以为是"数据没到位，再等等"
        ↓
   于是永远有理由继续做
        ↓
★ 而 6 周一次的口径对齐会，本来能在一周内暴露"口径根本对不齐"这个事实
```

**动作三：止损线要写在项目启动文档里，并且由业务方签字。**

```
止损条件（本项目当时缺失）：
   试点 6 周时若
     · 主动使用率 < 30%
     · 数据类请求满足率 < 50%
   → 暂停功能开发，先治口径与入口
        ↓
★ 止损的意义不是承认失败，是把钱从"加功能"转到"治数据"
   —— 因为加功能会掩盖数据问题，而不是解决它
```

### ★ 这个案例对"试点"这一节的反直觉补充

> **试点跑成功了，能证明的东西有限；试点跑失败了，能证明的东西很多。**
>
> 这个案例证明了三件事：
>
> ```
> ① 数据口径不统一时，功能做得再好也没用
> ② 入口不在工作流里时，合规正确的路径一定输
> ③ 验收指标设在功能层时，项目一定会被误判为成功
> ```
>
> **而这三条，成功案例都证明不了——因为成功案例里，这些坑都恰好被绕过了。**

**所以本书的第八章特意安排了一个失败项目；而这一节要补一句：失败项目的复盘价值，恰恰在于它把成功案例绕过去的坑，全部摊开给人看。**

## 5.5 步骤五：规模化推广

推广阶段要解决三件事：**组织与授权、运营机制、持续改进**。

### 5.5.1 组织与授权：谁批准、谁运维、谁担责

推广时最容易出现的混乱是：**用的人多了，但没人负责。**

```
推广前必须明确的三件事：

  ① 授权：谁有权让这个工具在哪个范围内被调用
     （谁批准新用户接入？谁能扩权限？谁能下线它？）

  ② 运维：出问题时谁处理、多久内处理
     （尤其：业务方自己建的工具坏了找谁？）

  ③ 担责：它参与的业务环节里，出错谁签字
```

**第三条最容易被推着走。**推广期的典型场景是：

```
某场景在试点时由资深专家复核 → 推广后由轮岗的新人使用
   ↓
新人不具备判断 AI 对错的能力
   ↓
但流程上，他现在是"签字人"
   ↓
出错了，流程合规，人却冤
```

**推广不是把人换掉，是把复核能力也复制出去。**这一条要写进推广方案。

### 5.5.2 运营机制：谁来维护它

**推广期最常见的三种死法，就在这里。**

```
死法一：试点完就散
   试点团队解散 → 工具无人维护 → 半年后模型过期、知识不更新
   ↓
   现象：项目总结写得很好，然后没有然后

死法二：无人运营
   上线了，但没人看反馈、没人更新知识、没人盯指标
   ↓
   现象：用户逐渐流失，理由是"不好用"
   ↓
   ★ 而"不好用"通常不是模型问题，是三个月没人管

死法三：运维成本吞掉收益
   推广得越广，维护量越大
   ↓
   现象：算账时发现，省下来的人时全花在了维护上
```

**这三种死法有一个共同点：它们都不是技术问题，都是"没人负责"的问题。**

所以推广方案里必须有一行：

```
┌─────────────────────────────────────────────────┐
│ 这个工具上线后的长期负责人：____（名字，不是岗位）  │
│ 每周投入：____ 小时                              │
│ 反馈闭环由谁接：____                             │
└─────────────────────────────────────────────────┘
```

**"名字，不是岗位"是重点**：写岗位意味着没人真的负责。

> 运营机制的具体形态可参考第四章提到的 MCP 与权限代理思路：**把"谁在什么范围调了什么"变成系统自动记录的事，而不是靠人记得。**

### 5.5.3 持续改进：让它一年比一年好

```
持续改进的循环：

  使用 → 发现问题 → 定位到源头（知识/规则/数据口径）
       → 改源头 → 记录一条通用规则
       → 回到使用
```

**这正是第三章 3.2.3 讲的反馈闭环**——在推广阶段，它从"一个清单"变成"一个机制"。

**判断一个 AI 场景是否健康的三个信号：**

| 信号 | 健康 | 不健康 |
|---|---|---|
| 用户提问的重复率 | 下降（同类问题越来越少） | 不变（说明每次都在重复劳动） |
| 人工复核的错误发现率 | 下降（模型在变好） | 持平（模型没变好，只是没人查） |
| 新场景从提出到上线的周期 | 缩短（能力在复用） | 不变（每个场景都是一次性项目） |

## 5.6 专节：高管怎么接 AI —— 不是培训，是助理

**这一节是本书最具原创性的一节，也是全书最反直觉的主张。**

### 5.6.1 两个真障碍，培训解决不了

```
高管用不起来，通常归因为"积极性不够""学习意愿不强"
   ↓
于是方案是：培训、专题会、训练营、大赛
   ↓
但真实的障碍是另外两件事：

  障碍一：不熟悉快速迭代的 AI
         → 有门槛、达不到预期 → 于是判定"没用"

  障碍二：顾虑数据安全
         → 不敢用 → 于是判定"不安全"
```

**认知提升解决不了这两个障碍。**它只能让人"知道 AI 是什么"，而这两个障碍需要的是**"给我一个敢用、好用、还不涉密的工具"**。

于是有了一个反直觉的主张：

> ### **对高层，不要先教 AI，要先配助理。**
>
> **员工要的是培训，高层要的是助理。**
>
> **给高管讲一百次大模型，不如给他一个真的能用的助手。**

### 5.6.2 助理的四类定制需求

给一位高管配 AI 助手，先问四个问题——**这不是设想，是工作量清单**：

| # | 高管要的 | 助理要做的 | 典型形态 | 安全级别 |
|---|---|---|---|---|
| ① | **他需要的数据** | 把他平时要的数据汇总好 | 每日经营与业务简报、异常提示 | 高（业绩、利润、人力） |
| ② | **他脑子里的规则** | 把判断标准显性化并据此判断 | 按规则判断、出初稿、提示例外 | 中（规则本身常涉密） |
| ③ | **他每天要批的流程** | AI 预处理，他只做确认 | 审批预填、汇报初稿、差异比对 | 中高 |
| ④ | **他关心的信息** | 监控 + 摘要 + 提示 | 政策、竞品、舆情、项目进展 | 低（可外部化） |

**"量身定制"这四个字听起来很贵，但它是可以估算的**：四类需求 → 四类工作 → 可分工、可排期。

**而它贵得值，因为高层的使用是杠杆最高的。**

```
高层不用 AI  → 下面的人不会用 → 整个组织停在 L1
高层用了 AI  → 下面的人看到有用 → 才有第五章 5.5 说的那种扩散
```

### 5.6.3 三个设计决定

**决定一：出处可追溯。**

每条结论指向原始来源（文件、数据、制度条款）。

> **让高管能自己核，而不是被迫"选择信或不信"。**

**决定二：置信度阈值。**

```
置信度 ≥ 阈值 → 直接给结论
置信度 < 阈值 → 不给结论，改为列出"需要你判断的分歧点"
```

**这一步把 AI 从"决策者"降为"提示者"，同时把风险显性化。**高管看到的是"有分歧的地方"，这恰恰是最值得他花时间的地方。

**决定三：草拟制。**

> **助理起草，高管拍板。**
>
> **高管的 AI 助手不是替他决策，是替他省掉一半的读和写。**

### 5.6.4 ★ 最大的心理障碍可能不是"不会用"，而是"被记录"

这一条值得单独讲，因为很多方案会在这里翻车。

助理天然携带两项能力：**会议/沟通留痕 + 决策记录**。而对很多高管（尤其合规敏感岗位），"被记录"意味着：

```
自己的判断被留档 → 成为日后被追溯的证据
沟通被当成"可被审阅的内容" → 说话变谨慎、变慢、不说真话
```

**这会同时毁掉两件事：助理的价值，和组织的坦诚。**

（这里和第一章 1.4 的悖论是同一个：员工效率提升了，但如果没有相应减少事务、兑现收益，抵触就是理性选择。**助理如果只增加记录、不减少事务，就是纯负担。**）

设计对策：

```
① 提供"仅对我可见 / 不入正式记录"的模式，让高管先建立信任
② 明确留痕的用途边界（服务本人 / 不作绩效素材），并让高管看得见留了什么
```

### 5.6.5 试点选人：三维度 + 双验

高管助手的试点选人，和 5.4.1 的三条件是同一套逻辑：

```
信任成本低 × 决策权高 × 业务痛感强
```

**但高管助手还要多做一次双验：**

```
可行性   —— 这个助理对他真的有用吗？
可复制性 —— 这个配置能复制给另一位高管吗？
```

**复制的难点在"量身定制"本身**：一个人的规则、关注点、阅读习惯都是独有的。

> 所以高管助手规模化推广的方式，**不是把同一个助手发给所有高管，而是把"定制流程"标准化**——把"提炼四类需求 → 配置 → 草拟制校验 → 阈值设定"变成一条可复制的流水线。

## 5.7 专节：AI 助手能做到哪一步 —— 组织透明度是天花板

上一节讲"高管怎么用起来"，这一节讲"**最多能用到什么程度**"。两者必须一起讲，因为只讲前者会让人产生不切实际的期待。

### 5.7.1 两种能力层级

| 层级 | 能力范围 | 数据来源 | 前置条件 | 可实现性 |
|---|---|---|---|---|
| **L1 · 系统内智能感知** | 汇总已有系统的数据、给异常提示、辅助判断 | ERP/OA/CRM/项目管理系统等**已有系统** | 无 | **当前绝大多数企业能做到** |
| **L2 · 全盘管理** | 全面掌握信息与数据，感知会议决议与个人行为，支撑"全面管理" | 组织的**全部真实过程** | ★ **组织文化达到"完全透明化管理"** | **绝大多数企业做不到** |

**关键区分：**

```
L1 是对结构化数据的读取与加工
L2 是对组织过程的感知 —— 会议决议、谁说了什么、决策怎么来的、行为轨迹
```

**L2 需要的数据压根不在系统里，在人和会议里。**

### 5.7.2 为什么 L2 卡在文化上

```
想让高管助手"全面管理所有信息和数据"
        ↓
需要感知：会议决议 · 个人行为 · 决策过程
        ↓
这些信息在哪里？
        ↓
不在系统里 —— 在会议桌上、在沟通中、在人的行为里
        ↓
要让 AI 感知到，必须先把它"变成数据"
        ↓
而"变成数据"的前提是组织愿意被记录、被看见
        ↓
★ 这不是技术问题，是组织文化问题
        ↓
组织文化未达"完全透明化管理"
        ↓
✗ L2 不成立 → 只能退回 L1
```

> **AI 感知的是系统，组织运行在人的行为里。要感知后者，先要组织愿意被看见。**
>
> **技术能穿透系统，不能穿透文化。**

### 5.7.3 分寸声明（这一条不能省）

```
透明化是为了让决策看得见全貌，
不是让管理者看得见每个人的一举一动。
```

**这句话不是免责声明，是方案能否被组织接受的分水岭。**

一旦"高管 AI 助手"被理解为"监控工具"，它会遇到两股力量同时反对：

```
管理层：担心被盯着
员工：担心被盯着
        ↓
助理成了"记录工具"，而不是"省事工具"
        ↓
没人配合真实数据 → L1 都做不好
```

**所以在启动高管助手之前，必须先把用途边界写清楚并公开：**

```
✅ 做什么：帮高管省掉读与写、把分散信息汇总、把他的规则显性化
✅ 做什么：让决策看得见全貌（有依据、有出处）
❌ 不做什么：不做个人行为的持续监控
❌ 不做什么：不作为绩效素材
```

### 5.7.4 给作者的一句提醒

这一节在书里的作用是**设限**，所以它必须诚实：

> **做不到全盘管理不是 AI 不行，是组织还没准备好被看见。**

而反过来也一样：

> **一个把 L1 做到极致的组织（L1 才是绝大多数企业现在能拿到的），价值已经足够大。**

**不要用 L2 的想象去卖 L1 的产品**——那是一切失望的来源。

## 5.8 本章小结

五步法，六个要点：

```
① 场景收敛到 1–2 个          —— 铺得越宽，越像"AI 走不通"
② 数据先评估再治理          —— 六个"是"才启动，不是治理完再做
③ 技术方案先定边界再选能力   —— 数据/权限/留痕/兜底，四项必须先写
④ 试点必须四件齐全          —— 范围、周期、指标、止损，缺一不可
⑤ 推广先定人再谈机制         —— 谁授权、谁运维、谁担责，三件事写名字
⑥ 高层要助理不是培训        —— 且要知道天花板在组织透明度
```

**这五步里，最容易被跳过的分别是：**

| 步骤 | 最常被跳过的 | 跳过的后果 |
|---|---|---|
| 场景梳理 | 收敛 | 5 个 POC，0 个能推广 |
| 数据准备 | 评估（直接开干） | 卡两个月，或者带着脏数据硬上 |
| 技术选型 | 边界与兜底 | 过不了合规评审，返工 |
| **试点验证** | **止损条件** | **拖到第 30 周才承认失败** |
| 规模化推广 | 长期负责人 | 试点完就散，半年后没人维护 |

**而这一章真正的落点只有一句：**

> **从决定做，到真的被用起来，中间隔着的不是技术，是六张必须有人签字的纸。**

## 5.9 金句墙

> **清单上的场景越多，越容易出现"每个都做一点、每个都没成"的结局。**

> **试点必须由业务的人、在真实的业务上、用他们自己的数据做——违反了，试点结论就没有意义。**

> **验收指标要落在业务结果上，不是使用行为上；使用行为是可以作秀的。**

> **止损是"承认这个场景现在不成立"，不是"承认这帮人不行"。**

> **一个能在第 6 周止损的项目，比拖到第 30 周才承认失败的项目，节省的是整个组织的信任。**

> **AI 感知的是系统，组织运行在人的行为里。要感知后者，先要组织愿意被看见。**
