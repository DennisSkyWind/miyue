## 6.0 本章要回答什么

老板问的从来不是"AI 好不好"，而是三个问题：

```
① 这笔钱要花多少？
② 能换回来什么？
③ 为什么别人买平台你不买？
```

大部分企业的答法是第一种：报一张预算表。

**而这张预算表往往漏掉最贵的那一项。**

更要命的是第三个问题——在 AI 这行，"该不该花这笔钱"远不如"**这笔钱买的东西会不会明年就作废**"要紧。

所以本章把算账做成两件事：

```
6.1–6.2  把账算全：成本五项、收益三类（传统算账）
6.3–6.4  把账算对：采购决策方法、云与本地的真问题（战略算账）
6.5–6.7  落到纸上：ROI 表、KPI 设计、不同规模企业的差异
```

> **一句话主张：采购是结果，不是起点。**
>
> 第二章选场景 → 第三章看数据 → 第四章定形态 → **第六章据场景倒推采购清单** → 第五章按预算定试点范围。
> 这就是本书"治决策"的价值主张——**把"要不要投 AI"这个假问题，换成"这几个场景值不值得投"这个真问题。**

### ★★ 本章的核心框架：AI 项目的账，要算三笔

**★ 这一节是全章的骨架，后面每一节都在往这三笔账里填东西。**

```
┌──────────────────────────────────────────────────────────┐
│ ★ 第一笔：钱                                              │
│   授权费 / 咨询费 / 硬件 / 实施费  ↔  人力 / 时间          │
│   → 这是所有人都会算的那一笔                                │
├──────────────────────────────────────────────────────────┤
│ ★★ 第二笔：能力                                           │
│   判断力（选型、配置、维护）  ↔  兜底（有人替你负责）      │
│   → 这笔账很少有人主动算                                    │
├──────────────────────────────────────────────────────────┤
│ ★★★ 第三笔：投入风险 ★★★                                 │
│   ★ 路线变化时，谁买单？                                    │
│   → 这笔账几乎没有人算，而这恰恰是 AI 行业最要命的一笔      │
└──────────────────────────────────────────────────────────┘
        ↓
★★ ★★ 而这一章最想说的话就在第三笔里：
   ★★★ 在一个高速变化的领域里，
   ★★★ 付费买的是"别人的路线"，
   ★★★ 而企业真正要的是"★ 保留换路线的权利"
```

**★ 为什么第三笔最重要？因为它是唯一一笔"事后才知道贵不贵"的账。**

```
第一笔账：签字那天就能算出来
第二笔账：签完半年后才知道贵不贵
★★★ 第三笔账：★ 要等下一代范式出来，才知道贵不贵
        ↓
★★ ★★ 而在 AI 这个领域，★ 下一代范式来得比多数企业的采购周期还快
        ↓
★★★ 所以这一章有一个很硬的推论：
   ★★★ 你无法靠"算得更细"来规避第三笔风险——
   ★★★ 你只能靠"★ 把风险结构换掉"来管理它
   ★★★ 这就是 6.3.2 那条主张的真正来由
```

## 6.1 成本侧：五项，其中一项从不出现在预算表里

AI 项目的成本不是一项，是五项。而预算表上通常只写了两项。

### 6.1.1 五项成本

```
┌────────────────────────────────────────────────────────────┐
│ ① 算力与部署                                             │
│    自建硬件：机房、服务器、网络、运维                        │
│    云端：调用量、并发、预留实例                              │
│    量级参考：中型企业整体投入常在百万量级                    │
├────────────────────────────────────────────────────────────┤
│ ② 模型与工程                                             │
│    模型调用、微调、知识库与检索工程、集成开发                │
│    量级参考：应用实施通常几十万到一百多万                    │
├────────────────────────────────────────────────────────────┤
│ ③ ★ 数据治理前置投入（本节重点）                          │
│    口径统一、清单梳理、权限梳理、标签与文档治理              │
│    ★ 这一项最常被漏算，也最容易把项目拖死                    │
├────────────────────────────────────────────────────────────┤
│ ④ 人员与培训                                             │
│    项目团队、试点部门的培训、变革沟通、关键岗位的机会成本      │
├────────────────────────────────────────────────────────────┤
│ ⑤ ★ 错误处理与兜底人工                                    │
│    人工复核、异常处理、幻觉拦截、争议裁决                    │
│    ★ 这一项在项目初期最大，在成熟后下降——但永远不为零          │
└────────────────────────────────────────────────────────────┘
```

**而行业里被讨论最多的投入，通常发生在前面：**

| 支出项 | 泛化量级（不指向具体企业） |
|---|---|
| 外部咨询 | 一百多万到两百万 |
| 设备购买 / 硬件算力 | 几百万 |
| 应用实施 | 几十万到一百多万 |

> **写法提醒（给作者）**：不写"我们花了 X"，写"**在这个行业里，一个中等体量的企业把 AI 这件事做起来，咨询、算力、实施三项加起来通常是百万量级**"。
> 用意是让读者产生"这确实不是小数目"的实感，从而接受后面"最小化投入"的主张。

### 6.1.2 ★ 第三项：数据治理前置投入

这一项之所以最常被漏算，是因为它**不发生在技术团队里**。

```
预算表上写的：  买模型 + 搭系统 + 做集成
实际发生的：
   ① 三个口径对不上 → 要业务部门开会定 → 要 IT 改数仓 → 要重跑历史数据
   ② 文档没有生效期 → 要逐份找所有者确认 → 要建标签
   ③ 权限不清 → 要梳理岗位与授权 → 要改接口
   ④ 历史数据不够 → 要么改目标，要么外部采购
        ↓
   以上每一项都不是"技术采购"，而是"业务与治理的工作量"
        ↓
   它不进任何一张技术采购单
```

**这一项的三个特征决定了它必然被漏：**

```
① 不在采购合同里     → 采购流程看不见它
② 不由技术团队完成   → 预算归口的技术负责人报不出来
③ 发生在项目启动后   → 立项时的估算里没有它
```

**所以算账必须在立项时就把它写进去。**第三章 3.5 讲的"最小起步"能压低这一项，但压不掉——**第一个场景要用的数据，一样得治。**

**★ 而这一项漏算的代价，往往在一年后才显形，而且显形的方式很隐蔽。**

```
★ 一个真实的方向性失败（详见 8.5.2）：
   想对 C 端做数字员工（穿戴设备/智能屏/虚拟数字人），
   规划时与国内头部大厂合作
        ↓
★ 停下来，三条原因之一是：
   ★★ "企业内部数据沉淀和管理模式不成熟，无法适应新模式"
        ↓
★ ★ 注意这一条的形态：
   它不出现在任何一张采购单上，
   它不出现在任何一份技术方案里，
   ★ 而它恰恰是让整个方向站不住的那一条
        ↓
★ 所以算账时，除了"数据治理前置投入"这项成本，
★ ★ 还要加一条更前置的判断：
   ★ "这个新模式要用的数据，现在在我们公司里以什么形式存在？"
   ★ 存在系统里且结构化 → 可以往下走
   ★ 还在纸单、微信、口头里 → ★ 这不是 AI 项目，
     是流程数字化项目，且该由流程负责人牵头
```


### 6.1.3 ★ 一份真实披露过的成本结构（★ 已按作者要求去除全部金额）

> **脱敏说明**：本节所有金额已按作者要求删除，只保留**结构与相对量级**。金额本身不可比（不同企业规模差一个数量级），而**结构不可比才最值得看**——它揭示的是"钱花在了哪一类事情上"。

```
┌─ 一期 AI 创研项目的公开投入结构（不含金额）──────────┐
│  人力                                             │
│    业务 AI 领域负责人 二十余人 / IT AI 领域负责人 二十余人 │
│    项目参与人数 七十余人 / AI 创研参与总人数 两百余人      │
│    ★ 专职从事 AI 相关工作的人力：不足两人            │
│                                                      │
│  投入构成（按类别，不含金额）                        │
│    外部咨询费（若走这条路）                          │
│    培训                                           │
│    平台开发费                                      │
│    20+ 个数字员工开发费                             │
│    移动端应用开发                                   │
│                                                      │
│  另一本账（集团/上级层面）                          │
│    AI 战略分解项目投入                              │
│    后期原有算力投入                                 │
│    上级单位可能投入的算力资源                       │
└──────────────────────────────────────────────────────┘
```

**★ 这份结构里藏着三条对全书都极其重要的信息：**

**第一条：自主推进真正省下的，是"咨询"这一块，而不是"开发"这一块。**

```
平台开发 + 20+ 数字员工开发 + 移动端应用
        ↓
而咨询是"一次性的方案"
自主开发是"自己的能力"
        ↓
★ 这就是第六章 6.3.2"尽量不预先采购产品化平台"最硬的一条证据：
   钱省下来了，而且省下的方式不是"少做"，是"自己做"
        ↓
★ 而"自己做"的成本不在预算表上：
   它是那些本来要投给咨询的时间，转投到了自己的团队身上
```

**第二条：★ 最贵的那一项成本，在这份账里根本不是钱。**

```
★ 专职从事 AI 相关工作的人力：不足两人
        ↓
而这个项目要推进：
   · 上百项需求的梳理与分类
   · 5 个共性解决方案 + 9 个领域解决方案
   · 近 600 人次培训的组织
   · 三十余支队伍、一百五十余人的大赛运营
   · 二期五大成果的落地
   · 本地算力平台（开源推理架构 + 容器化部署）
        ↓
★ 算一下：不足两人的专职人力，
   要同时承担上面全部七件事
        ↓
★ 所以所有"投入很可控"的叙事，都漏掉了最贵的一项——
   ★ 那两个人一整年的人力，以及他们被拖住的机会成本
```

**第三条：还有一本更大的账，在集团层面，而且它自己承认了一个问题。**

```
本企业自主推进（一期口径）
        ↓
上级单位的战略分解项目 + 算力投入 + 可能投入的算力资源
        ↓
★ 而汇报材料自己承认：
   市场部、数转办、数字化中心、各板块部门各自做规划和预算，
   上级单位也有自己的规划
        ↓
★ 结果：实施投入缺少统一策划
```

> **★ 这条正好接上 8.5 节那个失败案例的病根——**
> **营销助手失败于"口径和入口的解法不在项目组手里"；而这一条说的是"连钱和规划都不在同一张表上"。**
> **两者是同一个病的两种表现：责任分散在多个主体手里，而没有一个主体握有全局。**

> 【待核实】"专职 AI 人力不足两人"这一表述是否对外可披露；以及各级投入的**相对**比例（哪一块最重），可用于本章"钱花在哪"的一段。金额一律不出书。


### 6.1.4 ★ 第五项：兜底人工

这一项最容易被认为是"暂时的"，但它有一个长期特征：

```
一个 AI 场景要达到可信可用，通常需要：
   模型能力够 + 资料够好 + 兜底流程够稳
        ↓
   三者中最后一项最容易被砍（因为它不出现在系统里，只出现在排班表里）
        ↓
   兜底一砍：复核变抽查 → 漏检 → 出事 → 信任崩塌 → 场景停用
```

**兜底人工是场景的"信誉税"。**它不产生功能，但它决定用户还信不信这个工具。

## 6.2 收益侧：三类，不要只算第一类

### 6.2.1 提效类（最容易算，也最容易被做样）

```
提效 = 人时节省
     = (原来做这件事的耗时 − 现在做这件事的耗时) × 人数 × 频率
```

**这个公式有一个经典的注水空间：只算"一次任务的时间差"，不算"从零到一的改造"。**

```
只算场景内的耗时：
  原来人工做一份汇总：4 小时
  现在 AI 出初稿：0.5 小时，人复核 1 小时
  → 每份省 2.5 小时 ✅

但完整链路是：
  原来 4 小时 → 现在 1.5 小时（省的 2.5）
  ＋ 数据准备（一次投入，多场景摊销）
  ＋ 流程改造（审批环节新增、权限申请、系统对接）
  ＋ 兜底复核的额外工时
  → 净节省远小于 2.5 小时
```

### 6.2.2 决策类（最值钱，最难算）

```
决策类收益 = 决策提速 + 风险降低
```

**它的特点是：省下的不是工时，是"错误决策的概率×单次错误的代价"。**

```
一个价格审批场景：
  原来 3 天出结论 → 现在 1 天
  → 这不是省了 2 天工时，这是省了 2 天的市场窗口
```

> 【待核实】具体决策类收益的量化方式需按场景单独设计，本章不给通用数字。

### 6.2.3 质量类（最容易归零，最容易长期化）

```
质量类收益 = 差错减少 + 合规事件减少 + 一致性提升
```

**质量类收益的特点是"不出现在当月报表里"。**

```
原流程：10 个销售各自判断 → 判断标准 7 套
新流程：AI 按统一口径初筛 → 判断标准 1 套 + 人工例外处理
        ↓
收益不是"这个月多卖了 X"
收益是"明年稽核时，这块不再是最常出问题的地方"
```

**而在受监管行业里，这一类收益的价值可能被低估了。**

### 6.2.4 ★ 一个必须提前承认的问题

**收益侧有一个结构性的诚实问题：**

```
提效类收益，会被"人没减"这件事完全抵消。

  原来 10 个人做这件事 → 现在 2 个人做这件事
  ↓
  省下的 8 个人并没有消失
  ↓
  他们去做别的事？还是被要求做更多的事？
  ↓
  如果没有重新配置，这 8 个人的时间会被新的工作填满
  ↓
  → 效率提升在组织层面不体现为产出增加
```

**这不是 AI 的问题，是"效率红利如何兑现"的管理问题**——但它必须在立项时就想清楚：

```
立项时就要写明：这笔收益兑现到哪里去？
   ① 释放人手去做更高价值的事 → 写明是哪几件事
   ② 直接减少编制/外包支出 → 写明是哪一个岗位
   ③ 支撑业务增长（同样的人做更多的业务） → 写明业务量目标
```

**三者都不写，那这笔收益在账上永远只是"理论收益"。**

## 6.3 采购决策方法：你要落哪些场景，就采购哪些

这一节是本章真正的骨肉。

### 6.3.1 唯一原则：从场景倒推采购清单

```
原则：我们要落实哪些应用场景，就采购哪些。
```

**它的正确用法是倒推，不是正推：**

```
❌ 正推（大多数企业这么做）：
   听说要做 AI → 咨询公司来调研 → 出方案 → 报预算 → 采购
   → 买回来发现：有一半功能对应的场景，你的组织根本没准备做

✅ 倒推（本书主张）：
   场景清单（第二章，已收敛到 1–2 个）
        ↓
   每个场景要什么形态（第四章：Copilot / 流程内嵌 / 对客）
        ↓
   每个场景要什么数据（第三章的三张清单）
        ↓
   每个场景要什么算力与调用量
        ↓
   采购清单 + 金额区间
```

**倒推的好处是：采购清单天然和场景一一对应，删掉一个场景就删掉一笔钱。**

**而正推的采购清单，删不掉——因为它买的是"平台能力"，不是"场景能力"。**

### 6.3.2 ★ 尽量不要预先采购产品化的平台（以及它的边界条件）

这是本章最有争议、也最有价值的判断。

**理由：**

```
AI 发展速度太快。从 2023 年到现在，每年年底年初都会出现大的新应用模式。
        ↓
假如企业刚投入，花 3 个月到半年上线一套 AI 平台，花了大价钱，
结果还没用起来就要被淘汰，然后又要赶快等着大平台升级
        ↓
牵动的东西很多
```

**注意这个论证的结构：它不是说"平台不好"，而是说"平台的保质期短于项目的周期"。**

**所以判断标准不是"平台 vs 不平台"，而是：**

```
你的项目周期 是多少？
平台的技术代际 是多少？
        ↓
平台代际 < 项目周期 → 这个平台大概率会在你上线前就换代
        ↓
而升级的代价，通常远高于初次采购的差价
```

**★ 而这个判断之所以成立，是因为第三笔账——投入风险。下面把它的完整算法写出来。**

```
★★ ★★ 风险不是"平台 vs 自建"的道德问题，是一笔可以算的账：

   ┌──────────────────────────────────────────────┐
   │ 外采路线：你为一整套"会过时的东西"长期付费     │
   │      ★★ 平台换代 → 你的用法过时，授权还在      │
   │      ★★ 风险形态：★ 押在别人的路线上           │
   ├──────────────────────────────────────────────┤
   │ 自部署路线：你用人力换掉了"押错路线"的风险     │
   │      ★★ 框架换代 → 你的代码跟着换              │
   │      ★★ 风险形态：★ 跟不上的风险               │
   │      ★★ ★★ 两种风险，不存在没有风险的那条      │
   └──────────────────────────────────────────────┘
        ↓
★★ ★★ 拆开看，AI 这件事的风险恰好分成两层：
   · 算力层：★ 变化还不算太大
     → 所以算力买还是租、按什么规格买，不用太纠结
   · ★★ 应用层与开发层：★★ 变化非常大
     → ★★ 而这恰恰是平台卖的东西，也是你买的东西
        ↓
★★★ ★★★ 于是第三笔账的算法出来了：
   ★★★ "★ 这笔钱买的东西，会不会在项目周期内换代？"
   ★★★   会 → ★ 风险由你承担（人力换自由度）
   ★★★   不会 → ★ 风险由供应商承担（钱买确定性）
```

**★ 所以这里给出全章唯一一条真正的决策判据：**

> **★★★ "你的组织撑不撑得住'路线一直变'这件事？"**
>
> **撑得住 → 自部署（用人力换自由度）**
> **撑不住 → 外采（用钱买确定性）**
>
> **★★★ 这道题没有普遍正确的答案，只有算得清的账。**
> **★★★ 而这道题的关键不是"你会什么技术"，是"★ 你这个组织能持续几年投入在维护上"。**

**★ ★★ 而这条判据的延伸，正好是 6.7 节要讲的那个真实反例：**

```
★ 大型企业买了大厂平台 → 半年后新形态爆发 → 平台基本报废
★ 而中型企业用开源自建 → 虽然累，但资产是自己的
        ↓
★★ ★★ 请注意这个反差的方向：
   ★★ 买平台的那家，★ 花的是"确定性"的钱
   ★★ 自建的那家，★ 承担的是"变化"的风险
        ↓
★★★ ★★★ 而两家最后谁更划算，取决于一件很具体的事：
   ★★★ ★★★ 那家买了平台的，★ 有没有为"平台作废"预留过退出成本？
```

### 6.3.3 这条主张的边界条件（必须写出来，否则会误导读者）

**不预先采购平台，不等于不能买平台。**以下三种情况，买平台是合理的：

```
① 已有明确需求且平台能力正好匹配
   → 买的是"能立刻用的东西"，不是"未来的可能性"

② 平台提供的是通用基础设施（模型网关、检索服务、权限代理、审计）
   → 这类东西不会因为模型换代而作废，且自建成本高于采购

③ 你的团队规模不足以自建
   → 公开研究口径：自建失败率约为采购的两倍【待核实——具体研究出处需作者核实】
```

**而下面这些情况，应当坚决不预先采购：**

```
① 平台的核心卖点是"把最新的模型能力打包"   → 这个卖点明年就贬值
② 平台的核心卖点是"支持你未来想做的所有场景" → 你还不知道未来场景是什么
③ 平台需要"先买后规划"才能体现价值           → 采购额随规模膨胀，且无法按场景核减
```

> 【待核实】"自建失败率约为采购两倍"这一口径的**具体出处与统计口径**，需作者在 57 号材料中确认后引用；本章暂按"公开研究口径"表述并标注。

### 6.3.5 ★ 平台型能力与单点型能力，是两本完全不同的账

**★ 这是本章最容易被算错的地方，也是很多企业算完账得出错误结论的根源。**

```
单点型能力（一个工具解决一个问题）
   例：合同审核助手、印章识别工具
        ↓
   账很清晰：
     投入 = 一次性开发 + 少量运维
     收益 = 省下的工时 × 单价（当场可算）
     周期 = 几个月
     风险 = 场景本身不成立就停下，损失有限
        ↓
   ★ 这类项目算 ROI 时，几乎总是划算的
     —— 因为它的收益是"确定的工时节省"

平台型能力（给一个部门建一套共用的底座）
   例：部门级 Agent 平台（一套智能体+一套知识库+一套技能库，全员共用）
        ↓
   账完全不同：
     投入 = ★ 主力是人力（长期）+ 算力 + 安全与运维的持续投入
     收益 = ★ 很难单独归因（每个人都"觉得有用"，但说不清省了多少）
     周期 = 以年计（要养、要迭代、要让人信）
     风险 = ★ 一次投入，可能同时服务几十个人
        ↓
   ★ 这类项目用单点那套算法算，必然算成"亏"
     —— 因为它的收益是"分散的、不可拆分的"
```

**★ 真实的自建 vs 外采账（本案例一手材料口径，金额已泛化）：**

```
★ 路线一：开源自行部署（用开源项目自搭平台）
   · 授权费：0（★ 8.2.6 的真实做法：QwenPaw 与 Octop
     ★★ 都是开源系统自行部署，不是买来的商业平台）
   · 咨询费：省掉（原本 50~100 万区间）
   · 平台开发费：小额
   · 数字员工/应用开发费：按需
   · ★ 但真正的大头不在预算表上：★ 专职人力
     （本书算过的最贵的一项——专职 AI 人力不足两人，
       却要同时扛需求梳理、方案提炼、培训组织、赛事运营、
       本地算力平台、二期五大成果落地）
        ↓
★ 所以这条路线的真实代价是：不是"少花了钱"，
   而是"把钱换成了自己人的时间"
        ↓
★★ ★★ 而 ★★ 这条路线真正的理由，★ 还不止是省钱：
   ★★ 那是 ★ 投入风险 —— 见下方"第三笔账"

★ 路线二：商业平台外采（买 WorkBuddy 这类）
   · 咨询/许可/定制费用：要花
   · ★ 换来的是三样东西：
     ① 更快上线（不用自己踩坑）
     ② 不用长期养一套平台
     ③ ★ 有人对"平台能跑"负责
        ↓
★ 于是判断依据只有一条：
   这套底座是不是要长期演进？
     是 → 自部署（因为你要改它，而且要改很多次）
     否 → 外采（因为你要的是尽快用起来）
```

**★★★ 而在 AI 这个领域，这道判断题前面还得再加一句——第三笔账：投入风险**

```
★★★ ★★★ 前面比的是"钱"，但真正的分野在这张表之外：

   · ★ 算力层：★ 变化还不算太大
   · ★★ 应用层与开发层：★★ 变化非常大
        ↓
★★ ★★ 于是两条路线的风险长这样：

   ┌──────────────────────────────────────────────┐
   │ 外采：你为一整套"会过时的东西"长期付费         │
   │      ★★ 平台换代 → 你的用法过时，授权还在      │
   │      ★★ 风险形态：★ 押在别人的路线上           │
   ├──────────────────────────────────────────────┤
   │ 自部署：你用人力换掉了"押错路线"的风险          │
   │      ★★ 框架换代 → 你的代码跟着换             │
   │      ★★ 风险形态：★ 跟不上的风险               │
   │      ★★ ★★ 两种风险，不存在没有风险的那条       │
   └──────────────────────────────────────────────┘
        ↓
★★★ ★★★ 所以这两笔账必须一起看：
   · 第一笔：钱（授权费 vs 人力）
   · 第二笔：★ 能力（判断力 vs 兜底）
   · ★★★ 第三笔：★ 投入风险（★ 路线变化时谁买单）
        ↓
★★★ ★★★ 而第三笔账给出了一条只有在这个领域才成立的判据：
   ★★★ ★★★ "★ 你的组织撑不撑得住'路线一直变'这件事？"
   ★★★   撑得住 → 自部署（用人力换自由度）
   ★★★   撑不住 → 外采（用钱买确定性）
   ★★★ ★★★ ★★ 没有普遍正确的答案，只有算得清的账
```

> **★ 落到一句可署名的话：**
>
> **★ 在一个高速变化的领域里，付费买的是"别人的路线"，**
> **★ 而企业真正要的是"★ 保留换路线的权利"。**
>
> **★ 所以这条路的代价不是"省钱"，是"★ 用人力承担路线变化的风险"。**
> **★ 而这笔人力，恰恰沉淀在组织里，谁也拿不走。**

**★ 但无论自建还是外采，平台型能力都必须回答同一个问题：**

```
★ 第二个部门接进来时，改动大不大？
        ↓
   改动小 → 它真的是底座，账会在第二年、第三年摊薄
   改动大 → 它只是第一个部门的工具，
            ★ 那么它就该用单点型的算法去算账，
              也就该按单点型的标准去砍
```

> **金句**
>
> **「单点型能力算工时，平台型能力算时间。用错算法，好项目也会被砍掉。」**
>
> **「自建不是省钱，是把钱换成了自己人的时间——而时间是最贵的那一项。」**

### 6.3.4 最小化投入：把预算换成能力

```
最小化投入 ≠ 少花钱
最小化投入 = 少买"可能用得上"的东西

省下来的钱，投到两处：
  ① 场景本身（数据、流程、验收）
  ② 人（让员工、让技术部门的人在这个过程中认识到最新的应用模式）
```

**第二条常被忽略，但它其实是这笔投入最保值的部分。**

```
场景会过时（AI 变了，场景的解法也变了）
平台会过时
模型会过时
        ↓
但"这个团队现在知道 AI 能干什么、怎么干"不会过时
```

**所以一笔 AI 预算里，有一部分严格来说不是买项目，是买组织的 AI 肌肉。**

## 6.4 云端 vs 本地：这是个假二选一

第四章给了"私有化 vs API"的决策树。这一节补上采购视角下最容易被忽略的一层。

### 6.4.1 两个朴素方案，两个明显问题

```
方案 A：全上云
   → 问题：数据出厂的安全性

方案 B：全放本地
   → 问题：模型能获取到的只是局部或部分信息，能力受限
```

### 6.4.2 真问题：数据的外发边界

```
真正的设计对象不是"云 or 本地"，是"哪些数据、以什么形态、出厂到哪"。
```

```
┌─ 绝对不出厂 ──────────────────────────────┐
│  受控文件、商业秘密原文、个人信息原文        │
│  → 不给模型；必要时企业内私有部署且只做检索   │
├─ 脱敏后出厂 ──────────────────────────────┤
│  去标识化、聚合化、只给摘要                 │
├─ 可分片出厂 ──────────────────────────────┤
│  按板块/按任务把信息切给不同模型             │
└─ 无限制出厂 ──────────────────────────────┤
   已公开资料、通用知识                       │
```

### 6.4.3 路由模型的价值不是省钱

```
切换多模型（用路由层按任务分发）：

  一个模型看全部  →  合规结论：数据全量外发
  一个模型只看一段 →  合规结论：数据外发范围可论证
```

**★ 关键判断：路由模型的价值不是"省成本"，是"把数据外发的范围切到最小"。**

> 一个模型看全部、一个模型只看一段，是两种完全不同的合规结论。
> 这也是第四章决策树里"数据能不能出厂"这个因子的真正含义——**它问的不是"能不能用云"，是"出得了厂的那部分数据有多小"。**

### 6.4.4 云端算力的三个非安全理由

采购视角下，还有三个常被忽略的判断：

```
① 波动性：试点期的调用量无法预测，按峰值买硬件必然闲置
② 迭代速度：本地部署的硬件对新模型能力的兼容要等下一轮采购
③ 兜底路径：本地部署失败时，有没有云上的降级方案
```

> 【待核实】路由层/模型网关的具体组件是否点名，需作者拍板（与坑二"是否点名模型名"是同一类问题）。

## 6.6 KPI 设计：设一个不会被业务"做样子"的指标

KPI 是本书反复出现的主题（第五章 5.4.3 讲试点验收指标，这里讲长期 KPI）。**两者的原则一致，但对象不同。**

```
试点验收指标  →  判断"这个场景成不成"
长期运营 KPI  →  判断"这件事值不值得继续投"
```

### 6.6.1 三类 KPI

| 类别 | 指标示例 | 作用 |
|---|---|---|
| **使用类** | 活跃使用人数、场景渗透率 | 早期信号，但**极易作秀** |
| **价值类** | 单位场景节省人时、结论采纳率 | 真实收益，需人工核对 |
| **健康类** | 复核发现的错误率、人工介入次数、用户主动反馈数 | 判断它是否在被真正使用 |

### 6.6.2 KPI 设计的三条原则

**原则一：每个 KPI 必须配一个"反向 KPI"。**

```
只看"使用人数"   → 会涨
只看"采纳率"     → 会被挑着算
只看"满意度"     → 会虚高

配反向：
  使用人数 ↑  ⇄  主动报错率 ↑
  采纳率 ↑    ⇄  复核否决率 ↑
  满意度 ↑    ⇄  深度使用（连续 4 周）占比
```

**只有正向指标的 KPI 看板，等于给"做样子"发奖金。**

**原则二：KPI 的统计口径必须写下来，并与第三章的"口径唯一"要求一致。**

```
"活跃使用"  = 7 日内使用 ≥ 1 次？
            = 还是 7 日内使用 ≥ 3 次？
            = 还是产生过一次被采纳的输出？
        ↓
三个定义会得出三张完全不同的看板
```

**这是第一章坑二在 KPI 上的翻版：同一个词，两套算法，第三次沟通就是吵架。**

**原则三：KPI 要有一个"归零"的机制。**

```
如果一个场景连续 N 个月：
  · 价值类 KPI 达不到初始目标的 50%
  · 且健康类 KPI 显示人工介入次数上升
        ↓
那么它应该被降级或下线，而不是继续"优化"
```

**为什么要有这个机制？因为 sunk cost（沉没成本）是 AI 项目最常见的死法。**

## 6.7 不同规模企业的算账差异

**这一节原本是全章素材最薄弱的地方**（素材库无不同规模企业的对比数据），2026-11-02 补入了一个**真实的对照案例**（6.7.4）后，这一节反而成了本章最有说服力的部分。

★ **本节的写作纪律**：不填任何具体金额与合同数字；案例按"某大型制造企业"脱敏呈现；方法论部分标 `【待核实】`。

### 6.7.1 小企业（几十人量级）

```
特征：没有 IT 团队、没有数据部门、没有预算做平台
        ↓
最优解：几乎全部采购，不自建
        ↓
算账方式：按"人天订阅 × 人数"算，不算资产
        ↓
★ 最大的坑：为了"显得有技术能力"而买硬件
         → 一台闲置的服务器，比不买的成本高得多
```

### 6.7.2 大型企业（几千人量级）

```
特征：IT 部门存在但往往不做 AI；有大量存量系统；有数据治理历史包袱
        ↓
最优解：混合——通用能力采购，场景自建
        ↓
算账方式：
  ① 一次性投入（数据治理 + 集成）与人天收益分开算
  ② 收益兑现必须写明去向（尤其"释放人力"要指定承接部门）
  ③ 平台采购要按"代际 vs 周期"判断（6.3.2）
```

### 6.7.3 中型企业的中间路线

```
特征：有 IT 但没有 AI 团队；有预算但不够自建平台；场景多而杂
        ↓
最优解：先做 1–2 个场景，用最小化投入验证路径
        ↓
算账方式：把这一次的投入当作"组织能力建设投资"来算
        → 一部分算项目 ROI，一部分算能力沉淀（6.3.4）
```

### 6.7.4 ★★ 一个已经发生的反例：大手笔买了平台，却在半年后成了废品

**★ 这是本章唯一一个有真实前因后果的对照案例（★ 作者 2026-11-02 补充）。**

**先看这件事怎么发生的：**

```
★★ 某大型企业（★ 脱敏：某大型制造企业）
        ↓
★ 2025 年底：★ 直接购买了大厂平台
   —— 买的是"确定性"：快、成熟、有人兜底
        ↓
★★ 2026 年：★ 开源生态连续爆发
   · ★★ 先是 OpenClaw 一类开源形态起来
   · ★★ 随后是 WorkBuddy 一类形态起来
        ↓
★★★ ★★★ 结果：★ 那套刚买的平台，★ 基本报废
        ↓
★ 而这家企业当初买平台时，★ 并没有做错任何一步：
   · 场景是真的
   · 需求是真的
   · 采购流程合规、供应商也是大牌
   · ★★ 甚至连"平台会过时"这件事，★ 在行业里也不是秘密
```

**★★ 而这件事真正的价值，不在于"买错了"，在于它把第三笔账变成了一次真实发生的事：**

```
★ 前一节讲的是判据：会不会换代
★★ 这一节发生的是：★ 还没等换代完成，★ 它就已经被绕过去了

   2025 年底  买平台（当时它是最好的选择）
   2026 年初  开源形态出现
   2026 年中  又一个形态出现
   ★ ★ ★ 此时平台上刚开发完的功能，★ 已经有人在别处免费用着了
```

> **★★ 写到这里必须停一下，把这个案例的"教训"写准——**
>
> **★ 它不是"买平台买错了"。**
> **★ 因为在 2025 年底那个时点上，买平台大概率仍然是对的。**
>
> **★★★ 真正值得记下来的是这句话：**
>
> **★★★ "★ 就算你买对了，两年后它也可能变成废品"——**
> **★★★ **所以一笔采购决策的真正问题不是"买不买"，而是"★ 这笔钱里，有多少是可以被下一代形态继承的"。**
>
> **★★★ 而这个比例，几乎无法在采购那一刻算出来。**
> **★★★ ★★★ 这就是第三笔账最残酷的地方：★ 它只能事后结算。**

### 6.7.5 ★★ 那笔账该怎么算？——"退出成本"这个被漏掉的东西

**★ 案例讲完，得给出算法。否则它只是一个 anecdote。**

```
★★ ★★ 反例真正的落点在这里：
   买平台的那家，★ 花的是"确定性"的钱
   自建的那家，★ 承担的是"变化"的风险
        ↓
★★ 那到底谁更划算？★ 取决于一件很具体的事：
   ★★ 那家买了平台的，★★ 有没有为"平台作废"预留过退出成本？
        ↓
★★★ ★★★ 答案是：★ 大多数企业没有预留
```

**★★ 所以这里给出本章第三条判据（★ 与 6.3.2 的"撑不撑得住"并列）：**

```
★★★ ★★★ 判据三：★ 你的这笔投入，有多少能在下一代形态到来时活下来？

   算式（不用精确，用比例感就行）：
   ┌────────────────────────────────────────────────┐
   │  可继承的部分                                       │
   │    = 数据（你自己的数据永远是你的）                │
   │    + 知识资产（沉淀下来的文档、结构、口径）          │
   │    + 团队能力（人学会的东西换平台也带得走）          │
   ├────────────────────────────────────────────────┤
   │  不可继承的部分                                       │
   │    = 平台功能（换代即作废）                        │
   │    = 授权（继续付，但换不回来）                    │
   │    = 定制工作量（改在别人家身上的）                │
   └────────────────────────────────────────────────┘
        ↓
★★★ ★★★ 于是采购决策多了一个以前没有的问题：
   ★★★ "★ 这笔投入里，可继承的部分占多少？"
        ↓
   ★ ★ 平台买得越多、功能定制得越深 → 可继承比例越低
   ★ ★ 而 ★★★ 场景、数据、团队能力 ★★★ 投得越多 → 可继承比例越高
```

> **★★ 于是这一节给出一个很反直觉、但我认为很正确的结论：**
>
> **★★ 在一个高速变化的领域里，★ 越是在"平台"上花钱，越是在为一次必然的作废付钱。**
> **★★ 而越是把钱投在"★ 数据、知识、人"这三样上，越是在为下一代形态存本钱。**
>
> **★★ 这也解释了为什么 6.4 那句"★ 最小化投入"必须说清"最小化的是什么"——**
> **★★ 最小化的不是"少花钱"，是"★ 少买那些下一代形态带不走的东西"。**

### 6.7.6 ★★ 三档企业各自的算账要点（补入反例后重写）

**★ 在有了上面那个反例之后，三档企业的差别终于可以落到一句话上：**

```
★★ 小企业（几十人）
   ★ 优势：没有历史包袱，★ 换路线几乎不要成本
   ★ 所以：★ 几乎全部采购，★ 但 ★★ 千万别买"全家桶"

★★ 大型企业（几千人）

   ★ 劣势：★★ 决策周期长、采购流程重
   ★★ ★★ 而这两点加在一起，就是那个反例的成因：
      · 决策周期长 → 从决定到用起来，★ 正好跨过一轮换代
      · 采购流程重 → ★ 采购额随规模膨胀，且难以按场景核减
        ↓
★★★ ★★★ 所以对大型企业，本章真正要说的不是"买不买"，而是：
   ★★★ ★★★ 采购决策的时点，★ 和技术代际的时点，★ 必须放在一起看
   ★★★ ★★★ 而采购流程越长，★ 越要往"★ 买可继承的东西"上倾斜
        ↓
★★ 中型企业
   ★ 优势：★★ 决策快、自建得起
   ★ 所以：★ 先做 1–2 个场景，★ 把投入当"组织能力建设投资"算
        ↓
★★★ ★★★ ★★ 而三个规模档共同的一条：
   ★★★ ★★★ 买的应该是"★ 能被下一代形态继承的东西"，
   ★★★ ★★★ 而不是为了"用起来方便"买的东西
```

## 6.8 本章小结

```
成本五项，其中两项常被漏：
  ③ 数据治理前置投入（不进采购单）
  ⑤ 兜底人工（不进系统，只进排班表）

收益三类：
  提效（易算易做样）、决策（最值钱最难算）、质量（长期化）
  ★ 但收益必须写明"兑现到哪里去"，否则只是理论收益

★★ 本章的骨架：AI 项目的账要算三笔
   第一笔 钱    → 授权费/咨询费/硬件/实施  ↔  人力/时间
   第二笔 能力  → 判断力（选型配置维护）  ↔  兜底（有人负责）
   ★★★ 第三笔 投入风险 → ★ 路线变化时谁买单
   ★★★ 而第三笔只能事后结算——所以只能靠"换掉风险结构"来管

采购三原则：
  ① 从场景倒推采购清单，采购是结果不是起点
  ② 尽量不预先采购产品化平台，除非它是通用基础设施/开箱即用/你自建不起
  ③ 最小化投入，把一部分预算明确投成"组织能力"

★★ 三条判据（连起来读）：
  判据一（6.3.2）：★ 你的组织撑不撑得住"路线一直变"这件事？
  判据二（6.3.2）：★ 这笔钱买的东西，会不会在项目周期内换代？
  ★★★ 判据三（6.7.5）：★★ 这笔投入里，有多少能被下一代形态继承？
     → 可继承 = 数据 + 知识资产 + 团队能力
     → 不可继承 = 平台功能 + 授权 + 定制工作量
     → ★★ 越是在"平台"上花钱，越是在为一次必然的作废付钱
     → ★★ 越是投在"数据、知识、人"上，越是在为下一代存本钱

云与本地：
  不是二选一，是设计数据外发边界
  路由模型的价值不是省钱，是把外发范围切到最小

KPI：
  每个正向指标配一个反向指标
  口径先写下来
  要有"归零"机制
```

**而这一章真正的落点是那一句：**

> **AI 项目最贵的那一项成本，从不出现在预算表里——它叫"数据原本就不干净"。**

## 6.9 金句墙

> **算账不是财务动作，是采购决策动作。**

> **"该不该花这笔钱"，远不如"这笔钱买的东西会不会明年就作废"要紧。**

> **采购是结果，不是起点。删掉一个场景，就该删掉一笔钱。**

> **平台代际短于项目周期时，买平台就是在为一次必然的升级付两次钱。**

> **最小化投入不是少花钱，是少买"可能用得上"的东西——省下的钱，一部分买项目，一部分买组织的 AI 肌肉。**

> **★ 就算你买对了，两年后它也可能变成废品——所以采购决策的真正问题不是"买不买"，而是"这笔钱里，有多少是可以被下一代形态继承的"。**

> **★ 越是在"平台"上花钱，越是在为一次必然的作废付钱；而越是把钱投在数据、知识和人上，越是在为下一代形态存本钱。**

> **模型会过时、平台会过时、场景会过时；"这个团队现在知道 AI 能干什么"不会。**

> **路由模型的价值不是省钱，是把数据外发的范围切到最小。**

> **一个模型看全部、一个模型只看一段，是两种完全不同的合规结论。**

> **写不出"收益兑现到哪里去"，就说明这笔收益在组织层面拿不到。**

> **只有正向指标的 KPI 看板，等于给"做样子"发奖金。**

> **沉没成本是 AI 项目最常见的死法——所以 KPI 必须有归零机制。**

> **AI 项目最贵的那一项成本，从不出现在预算表里——它叫"数据原本就不干净"。**
