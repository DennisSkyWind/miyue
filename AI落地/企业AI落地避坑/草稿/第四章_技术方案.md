## 4.0 为什么"哪个模型更强"是伪问题

技术总监的会议室里，最常出现的第一个问题是：

> **"我们到底用哪个模型？"**

这个问题看起来专业，实际是伪问题。原因是——**它把一个已经基本解决的技术问题，放在了一个还没解决的管理问题前面。**

先把量级摆清楚。一个中等体量的企业把 AI 这件事做起来，钱大致花在三处：

| 支出项 | 量级（泛化） |
|---|---|
| 外部咨询 | 一百万到两百万 |
| 设备购买与硬件算力 | 几百万 |
| 应用实施 | 几十万到一百多万 |

【待核实】以上为作者口述的泛化区间，作者明确要求不写真实情况；是否以"行业量级"形式入书待确认。

在这个量级上，**模型选错与数据用错之间，根本不是一个数量级的损失**。

外部研究给的两条参照口径：一份 2025 年的第三方研究指出，把系统从 80% 提到 95% 质量阈值的工作**几乎全是基础设施与数据工作，不是模型工作**，且**自建方案的失败率约为采购方案的两倍**【待核实】；另一份 2025 年的公开研究显示，**95% 的生成式 AI 试点没有产生可衡量的财务回报**，并且到 2027 年，任务专用小模型在企业部署中将以 3:1 超过通用前沿模型【待核实】。

```
模型之间的差距（年度级，趋于收敛）
      vs
你的数据烂、检索烂、权限没管住（周级，天天疼）

前者一年改一次，后者每一条业务链路都在流血。
```

还有一个更隐蔽的机制。国际学界关于检索增强生成的综述里有一句结论，值得原样记住：

> **Agent 的推理能力，弥补不了不稳定的检索质量。失败往往源于检索覆盖不足、索引构建粗糙、结构化与非结构化知识融合不够。**

翻译成企业语言：**Agent 越强，越会掩盖检索的烂账。**演示越顺，底层数据问题暴露得越晚——而那时系统已经在生产上了。

所以本章不讲模型排名，只讲三棵决策树：**部署形态怎么定、知识与能力怎么搭、工具怎么接**。

> **本章第一性问题不是"哪个更强"，是"哪个你敢让它拿到手"。**

## 4.1 决策树一：私有化 vs API

### 4.1.1 为什么会这样：这是一个假二选一

常见的问法是"我们该私有化还是用 API"。这个问题之所以要改写，是因为它把**连续的风险面**压缩成了一个开关。

真实的分歧点只有两个：

```
问题一：数据能不能出厂？
问题二：模型和算力，谁来养？

"私有化 vs API"只是这两个问题的答案组合，
不是问题的本身。
```

作者在讲采购决策时，给过一条被低估的解法：

> 如果**知识库、数据、文件全部在本地**，大模型获取到的可能都是一些局部或部分的东西，也存在一些问题。
> 但**可以通过切换多模型（使用路由模型），把这个信息分拆到各个板块、各种模型当中来使用**。

这句话的技术含义，本章把它固定成一条设计原则：

> **路由模型在这里的价值不是"省成本"，是"把数据外发的范围切到最小"。**
>
> 一个模型看全部、一个模型只看一段，是两种完全不同的合规结论。

于是"私有化 vs API"的真实解，是**按数据分层的外发边界**：

```
绝对不出厂（商业秘密、未公开研发数据、个人信息） → 本地推理 / 专属实例
可脱敏后出厂（统计口径、已公开法规、通用问答）     → 通用大模型 API
可分片出厂（按板块、按任务切给不同模型）          → 模型网关 + 路由层
```

### 4.1.2 四因子判断表

| 因子 | 问什么 | 指向私有化/自建 | 指向 API/采购 |
|---|---|---|---|
| **数据能不能出厂** | 有多少比例的业务内容必须留在厂内？有没有哪一类是绝对红线？ | 核心业务数据、客户数据、未公开研发数据占多数 | 内容多为公开/可脱敏；或已按分片规则设计 |
| **成本规模** | 调用量与数据留存周期多大？峰值出现在什么时候？ | 高频、持续、批处理型调用 | 峰值集中、低频、波动大 |
| **合规审计** | 有没有需要监管穿透检查的环节？留痕要求到什么粒度？ | 需物理隔离、全链路可追溯、日志长期留存 | 可用云侧合规能力满足，但需确认数据驻留与删除条款 |
| **运维能力** | 有没有能长期维护推理集群、版本升级、容量规划的人？ | **有稳定的运维班组与预算** | 无专职团队，或人手要投到场景上 |

这张表最有用的不是它的结论，是**第四行**。

因为前三行都指向"应该自建"的场景里，只要运维能力那一格是空的，**自建这条路就基本走不通**——外部研究里"自建失败率约为采购两倍"的原因正是"工程基础薄弱"【待核实】。

### 4.1.3 常见错误组合

**错误组合一：合规要求高 + 运维能力弱 → 硬上自建。**

领导说"数据不能出厂"，团队就买了硬件、招了人、上了推理集群。半年后遇到的是：模型升级要停服、显存不够要扩容、推理框架和业务代码耦合到无法迭代、专门养运维的人成了新的成本中心。

**机制**：自建不是一个技术决定，是一个**运维承诺**。签下采购合同那一刻，你同时签下了一份未来三年的设备折旧与人力承诺。

**错误组合二：调用量不大 + 想"一步到位"建私有平台。**

**机制**：规模不匹配时，私有化的单位成本远高于 API；平台的沉没成本会锁死后续每一次技术路线调整。

**错误组合三：把"不可外发"当成"全都不外发"。**

一刀切禁止外发，把本可安全外发的通用问题（写通知、通用问答、格式转换）也拖进自建，成本翻倍。

**机制**：外发风险是**按数据分类**的，不是按公司划线的。

**错误组合四：把 API 当成"零成本、随时可撤"。**

调用量涨、上下文变长、多步 Agent 把一次任务变成十几次模型调用——**Agent 越自主，token 账单越像指数**。

**机制**：成本口径从"每千字"变成"每任务"，而任务长度由编排层决定，不由业务决定。

**错误组合五：先买平台，后定场景。**

作者的态度非常明确：

> **AI 发展速度太快**，从 23 年开始到现在，每年基本上年底年初都会有大的新应用模式出现。假如说企业刚投入，**花 3 个月到半年上线一套 AI 平台，花了大价钱，结果还没用就已经要被淘汰了**，然后又要赶快等着大平台去升级。

由此提炼成一条可当场使用的采购判据：

```
这笔钱花出去，如果明年的范式变了，我损失多少？

  损失接近零     → 买（算力、存储、标准的模型服务接口、可导出的知识库工具）
  损失是重做一遍 → 先别买（把业务逻辑、数据格式、工作流都焊死在一个平台里的那种）
```

**采购是结果，不是起点——你要落实哪些应用场景，就采购哪些。**

### 4.1.4 本节结论

```
先问：有没有哪类数据绝对不能出厂？
  有 → 这些数据走本地，其余按分类走 API + 路由分层
  没有 → API 起步，把省下的运维人力投到场景上

再问：调用规模与运维能力撑不撑得起自建？
  撑不起 → 采购，别自建
  撑得起 → 再问明年的范式变了，这套东西损失多少
```

> **私有化不是安全选项，它是一份运维合同。**
> **一个模型看全部、一个模型只看一段，是两种完全不同的合规结论。**

## 4.2 决策树二：RAG vs 微调 vs Agent

### 4.2.1 三选一其实是一问三答

这条决策树的入口不是"哪个技术更先进"，而是一个具体的问题：

| 你要解决的是什么 | 对应做法 | 判据 |
|---|---|---|
| **知识会变**（法规更新、文件天天改、口径调整） | **RAG** | 知识是否需要在**不重训模型**的前提下更新？ |
| **风格与格式**（输出必须像我们的样子、术语必须统一、格式必须合规） | **微调** | 问题是不是**"模型知道但不会按我们的方式说"**？ |
| **多步自主**（要读多个系统、要判断、要循环、要决定下一步） | **Agent** | 任务是否**需要模型自己决定步骤**？ |

三条判据都指向同一个意思：**先看变化发生在哪一层。**

```
变化发生在「知识」层 → 知识外挂（RAG）
变化发生在「行为」层 → 行为固化（微调）
变化发生在「流程」层 → 流程自主（Agent）
```

### 4.2.2 各自的失败模式

**RAG 的失败模式：不是模型答错，是它根本没查到。**

检索质量是主瓶颈。失败通常来自三处：检索覆盖不足（该用的文档没进索引）、索引构建粗糙（切片切坏了语义，一段话被切成三片）、结构化与非结构化融合不够（台账里的数字和制度里的文字放不到一起）。

**工程上的补救手段（可抄）：**

- **长文档切分策略**：合同、注册申报这类超长材料，要按语义边界切（条款、章节、条目），不要按固定字数硬切；切片要保留"所属文件 + 章节路径 + 页码"，否则引用回不到原文。
- **结构化与非结构化分开处理**：台账、指标走结构化查询，制度文本走语义检索，不要用一个索引硬吞两类。
- **检索策略分场景**：开放式生成推理用宽口径检索，窄口径精确抽取用细粒度检索。
- **引用可追溯**：答案必须能指回原文片段。这不是锦上添花，是 RAG 能不能进生产的门槛——**不能回溯的引用，在审计面前等于没有证据**。

**微调的失败模式：把会变的东西烤进了不会变的东西里。**

```
失败机制一：知识过期
  微调把知识写进权重 → 知识要改，只能再训一次
  → 制度类、法规类知识一进微调，就变成定期重训的债

失败机制二：样本不足与过拟合
  企业里典型的样本分布是"绝大多数正常 + 极少数异常"，
  而异常恰恰是最需要学的

失败机制三：不可审计
  微调后的行为来自权重，很难向审计解释
  "为什么它这次这么判" —— 权重给不出答案，RAG 给得出

失败机制四：版本管理失控
  每次微调产生一个新模型，评估、回归、审批、灰度全要重做一遍
```

**所以微调只在该固化的地方固化**：格式、语气、术语口径、分类边界、判断规则。**不该固化的是事实。**

**Agent 的失败模式：自主性没有配约束。**

同一份国际综述给出的另一条结论是：**Agent 的自主性必须配显式约束。**

```
没有约束的 Agent 典型死法：

① 步骤循环 —— 反复调用同样的工具直到超时，烧钱且无产出
② 权限越界 —— 为了完成任务，把不该读的读了、不该写的写了
③ 错误累积 —— 第一步的小错被当成事实往下推，最后一步已经离谱
④ 目标漂移 —— 没人告诉它"做到什么程度算完成"，它自己定义完成
```

对应的四条硬约束，建议写进架构基线：

| 约束 | 内容 |
|---|---|
| **动作白名单** | 允许调用哪些工具、读写哪些数据域，写死在配置里 |
| **步数与预算上限** | 单任务最大步数、最大 token、最大墙钟时间，超限即停并转人工 |
| **置信度阈值** | 输出置信度低于阈值时，不给结论，转人工复核 |
| **不可逆动作人工确认** | 写回、发出去、提交审批这类动作，必须有人工确认环节 |

### 4.2.3 现实形态：RAG 打底 + Agent 编排 + 少量微调

上面三棵树是分开讲的，落地时几乎不会是三选一，而是三层叠加：

```
┌─────────────────────────────────────────────┐
│  微调层（薄）                                │
│  固化：输出格式 / 术语口径 / 语气 / 判断规则   │
│  只做"怎么说"，不做"知道什么"                │
├─────────────────────────────────────────────┤
│  Agent 层（编排）                           │
│  决定：读什么、调谁、循环几次、何时转人工     │
│  必须配：白名单 + 步数上限 + 人工确认        │
├─────────────────────────────────────────────┤
│  RAG 层（打底）                             │
│  提供：可追溯的事实 + 引用原文 + 实时更新     │
│  必须配：切片策略 + 检索评估 + 引用回链       │
└─────────────────────────────────────────────┘
```

**为什么这个组合是常态，而不是折中？**

因为它把三种"变化"分给了三种"可改的地方"：

```
知识天天变  →  改索引即可，不重训、不重测
行为偶尔变  →  改提示与配置，必要时才微调
流程经常变  →  改编排，改完就生效
```

只有当**行为**这一层需要固化到"每次都稳定复现"时，微调才有不可替代的价值。**微调是把一次性工程投入换成长期稳定性，不是把知识塞进模型。**

> **RAG 负责"知道什么"，微调负责"怎么说"，Agent 负责"先做什么"。**
> **Agent 越强，越会掩盖检索的烂账。**


### 4.2.4 ★★ 企业知识库场景：RAG 的四个死结，与 LLM Wiki 为什么会赢

> **这一节讲的不是"RAG 这个技术不好"。**
> **它讲的是一个更具体的问题：当你要做的不是"检索一堆网页"，**
> **而是"★ 让全公司多个系统共用一套知识"时，**
> **RAG 路线里"★ 自动分段"和"★ 向量库作知识底座"这两个选择会在哪里卡住。**

#### 现象

企业想做知识库，第一反应几乎都是 RAG：文档切段 → 向量化 → 检索 top-k → 拼提示词 → 生成。

流程跑通，演示效果也不错。**但进生产之后，四道坎始终过不去。**

★ 而这四道坎有一个共同特点：**它们都不是"模型不够强"造成的，也不是"检索参数没调好"造成的。** 它们出在流程的最前面——**文档变成向量的那一刻**。

#### ★ 死结一：分段这件事，非人工不可自动化

```
★ 切得自动（按固定字数/按分隔符）：
   → "第三章 第2条 第3款……"被切成两半
   → ★ 条款的上下文断了，检索出来的片段读不懂
   → ★ 表格被按行切开，表头和数据分家

★ 切得人工：
   → 质量确实好
   → ★★ 但文档一更新就要重切
   → ★★ 而企业的制度、标准、模板，是天天更新的
```

★ **本质问题：RAG 把"理解文档结构"这件事推给了切分器，而切分器只会数长度。**

★ 切分器不懂"这是第几款的例外条款"，也不懂"这张表的三列要一起看"。

#### ★ 死结二：前处理同样非自动化

★ 企业的知识不是纯文本流，而是**有结构的文档**：

```
★ 编号条款  →  第一条 / 第一款 / （一）—— 切开后引用链断裂
★ 表格      →  表头与数据分离后，数字失去含义
★ 图表      →  切完只剩一段描述
★ 附件清单  →  变成一堆孤立字符串
```

★ 而 RAG 的输入端期待的偏偏是"一段自洽的纯文本"。**两者的形态不匹配，而且这个不匹配无法靠调参解决。**

#### ★ 死结三：平台迁移难

```
★ 换嵌入模型 → 向量维度变了 → 全量重灌
★ 换向量数据库 → 数据迁移 + 索引重建 + 调参重做
★ 换检索策略（向量 → 混合 → 图） → 又是重灌
```

★ **★ 本质在于：你以为存的是"知识"，其实存的是"向量"。**

★ 向量是**绑死的**：它同时绑定了嵌入模型、维度、切分策略、检索后端。**知识是活的，向量是死的。**

#### ★ 死结四：多系统对接、共用同一套知识库——★ 这一条最要命

```
★ 每个系统各自建一套 RAG → 知识孤岛堆叠
★ 同一份制度，在 5 个系统里有 5 份拷贝
★ ★ 制度更新了，5 个系统要更新 5 次，漏一个就出事
★ 要真共用 → 必须统一切分口径 → ★ 迁就最差的那个系统
```

★ **★ 共用知识库的前提是：知识要有一个★ 不依赖任何系统的形态。**
★ 而向量库天然绑系统——**这条前提，从架构上就不成立。**

★ 所以很多企业的现状是：**知识库很多，知识却很少。**

#### 四个死结的共同根因

> **★ RAG 路线把"知识"提前降维成了"片段 + 向量"，**
> **★ 而企业真正需要的是"★ 结构完整、平台无关、可被人读懂的知识"。**
>
> **★★ 而降维是不可逆的——你没法从一堆向量里还原出那份制度。**

#### ★ 正确做法：LLM Wiki（把知识整理成 Wiki，而不是切成碎片）

★ 机制换了一下：

```
 RAG：   文档 → 【切段】→ 向量化 → 检索碎片 → 拼提示词 → 生成
         ↑ 这一步在"数长度"

 Wiki：  文档 → 【整篇交给 AI 做逻辑整理】→ 结构化 Wiki 页面 → 直接基于页面回答
         ↑ 这一步在"理解内容"
```

★ **★ 核心差别只有一处：分段这件事，从"数长度的人"交给了"能读懂的人"。**

★ 而且这个替换，**一条一条地把四个死结解掉了**：

| ★ 死结 | ★ LLM Wiki 怎么解 |
|---|---|
| 分段非自动化 | ★ 不切段——整篇交给 AI 按逻辑层级重组，**切分由理解内容的一方来做** |
| 前处理非自动化 | ★ 表格、条款、编号被保留在结构化页面里，**上下文完整** |
| 平台迁移难 | ★ Wiki 就是 Markdown/文档，**不绑向量库、不绑嵌入模型**，换平台就是拷文件 |
| 多系统共用难 | ★ 同一份 Wiki 被所有系统读；**共用所需的那个"独立于系统的形态"，Wiki 天然具备** |

#### ★★ 一句必须说清的话：LLM Wiki 不是要取代 RAG

★ 否则这一节会跟 4.2.3「RAG 打底」自相矛盾。准确的说法是：

```
★ LLM Wiki 取代的是 RAG 路线里的两件事：
   ① "★ 自动分段"这个动作
   ② "★ 向量库作为知识底座"这个选择

★ 而检索层用什么，仍然可以按需选：
   · 向量检索 · 混合检索 · 图检索 · 全文检索
   ★ ★ 变的只是"★ 被检索的对象"：
   ★ ★ 从"碎片"变成了"完整页面"
```

> **★ RAG 把知识打碎，Wiki 把知识连起来。**
> **★ 检索的本质，也从"用相似度找碎片"变成了"用逻辑找结论"。**

#### ★★ 一句必须先说清的话：★ 这条路线不是推演，是走过弯路之后的回头路

```
★ ★★ 在做 LLM Wiki 之前，★ RAG 这条路是走过的
★ —— 而且走的是最正统的那种：文档切段、向量化、检索 top-k、拼提示词
        ↓
★ ★★ 演示效果不错，★ 流程跑通了
★ ★★ 但进生产之后，★ 前面那四道坎一道都没绕过去
        ↓
★★ ★★ 而绕不过去的原因，★ 回头看很清楚：
   ★ 不是模型不够强，不是参数没调好
   ★ ★★ 是"★ 文档变成向量的那一刻"，★ 知识就已经被降维了
```

> **★★ 所以这一节的全部内容，是"走过之后写下的复盘"，不是"看论文得出的选型建议"。**
> **★★ 这也是本书少有的、可以讲"我们试过什么、为什么没成"的地方。**

★ **★★ 关于"慢"：慢在哪一段，决定了这笔账划不划算**

★ 这里要说精确，因为很容易被误读。**"慢"和"不慢"，指的是两个完全不同的阶段。**

```
★ 那段"重活"：【知识加工/建库】
   · 逐篇做逻辑整理、生成 Wiki 结构
   · ★★ 这是一次性或低频的活
   · ★★ 但它是【可复用】的：
   ★★ Wiki 建好一次，所有系统、所有查询、所有人都受益
   ★★ 而向量库每换一个模型，就要重来一次
        ↓
★★★ ★★ 而最反直觉的一点在这里：
   ★★ 这一段★ 不需要人来做整理
   · ★★ 整篇文档交给 AI，★ 由 AI 自主完成逻辑整理与 Wiki 页面生成
   · ★★ 人只做一件事：★ 抽检结果对不对
        ↓
★★ ★★ 于是"建库要花多少人力"这个问题，★ 答案比想象中轻得多：
   ★★ 不需要一支队伍去切文档、去写规则、去维护向量
   ★★ 需要的是：★ ★ 建库这件事本身可以交给 AI 去做
        ↓
★★ ★★ 而这恰恰是 LLM Wiki 相对 RAG 少有的、比"快"更重要的差别：
   ★★ RAG 的建库成本在"人"（分段、前处理、每次换模型重灌）
   ★★ Wiki 的建库成本在"★ 让 AI 干一次"（然后人只做抽检）

★ 不慢的那一段：【查询】
   · 不再是"检索碎片 + 拼提示词 + 生成"
   · 而是直接命中结构化页面
   · ★ ★ 查询这一段并不慢——★ 而且答案更准
   · ★ ★★ 需要老实说明：★ 这里没有单独的查询耗时实测数字
   ·   ★ 所以本书只讲机制，不给这个环节编一个秒数
```

★ **★ 算一下总账就清楚了：**

| | ★ RAG | ★ LLM Wiki |
|---|---|---|
| 建库（一次性） | 快（自动切段） | ★ 不慢（★ 整篇交给 AI 自主整理） |
| 换模型/换平台 | ★★ 全量重灌 | ★ 拷文件 |
| 制度更新 | 重切+重灌 | ★ ★ 改一篇页面 |
| 多系统共用 | ★★ 各自一套 | ★ ★ 一份 |
| 查询 | 快但可能是碎片拼凑 | ★ 不慢，且是完整逻辑 |
| ★★ 答案可审计 | ★ 难（片段自动切的） | ★ ★ 有对应页面，可翻可追责 |

> **★ RAG 的成本集中在"第一次"和"每一次变更"；**
> **★ Wiki 的成本集中在"建库那一次"，之后越用越省。**
>
> **★ 而且因为建库这一步本身可以由 AI 自主完成，**
> **★ "建库要投多少人"这个排期问题，在 Wiki 路线上基本不存在。**

#### ★★ 核心判据：快 vs 准，在企业知识场景里根本不是一道二选一

★ 这是本节最重要的一句话，也是很多人选型时真正该问的问题：

> **★ 一个快速的模糊答案，和一个通过逻辑判断的准确答案，哪个更有价值，一目了然。**

★ 再往企业场景推一步，这句话可以变成一个可操作的判断：

```
★ 一个 3 秒给出、但需要用户自己去核实的答案
   → ★★ 用户的真实成本是 10 分钟（还得去查原文）

★ 一个 10 秒给出、但可以直接进流程的答案
   → ★★ 用户的真实成本是 10 秒
```

> **★★ 在企业知识场景里，"快"从来不是第一指标，"能直接用"才是。**
> **★★ 而"能直接用"的判据不是快，是：★ 答案能不能直接引用进文件、直接支撑一个决定。**

★ 而这一层，在受监管的制造企业里还有一道硬门槛：**可审计**。

```
★ RAG 的答案：你很难说清它引用了哪一段
   → 因为片段是自动切的，片段边界本身就没有业务含义
   → ★★ 呼应 4.2.2：★ 不能回溯的引用，在审计面前等于没有证据

★ Wiki 的答案：答案有对应的 Wiki 页面
   → 人能翻、能查、能追责、能更新
   → ★★ 这不是加分项，是能不能进生产的门槛
```

#### ★ 实证：这条路线在本企业的落地结果

★ 研发中心用 **LLM Wiki 形态的知识助手**（知识库 Wiki 化 + 检索问答），实测：

```
┌────────────────────────────────────────────────────────┐
│ ★ 效率侧：提效 20%~30%                                   │
│   → 找资料、查制度、问流程的时间明显缩短                  │
├────────────────────────────────────────────────────────┤
│ ★★★ 质量侧：★ 回答的正确率/准确率提升约 30%              │
│   → 不只是"更快找到"，★ 而是"找到的是对的"              │
└────────────────────────────────────────────────────────┘
        ↓
★★ ★★ 而质量侧这 30%，★ 恰恰是 RAG 路线最难拿到的那一项：
   碎片拼凑出来的答案，"快"但经常"不对"
   ★ 而一旦答案不对，★ 用户还是要回去查原文
   ★★ ★ 于是"快"就变成了"更快地给出一个错答案"
```

★ 而这两个数字的意义不在大小，在于——**它是在"答案能直接用"的前提下拿到的**，而不是靠"回答速度快"堆出来的。

★ **★ 这里要特别指出质量侧那 30% 的分量，因为它推翻了一个常见预期：**

```
★ 很多人以为 RAG 的问题是"检索不准"，
★ 其实在企业制度这个场景里，★ 更大的问题是"检索到了，但拼出来的答案不完整"

★ 拼出来的东西看起来很像答案——因为它确实是从正确文档里来的
★ 但条款的例外、表格的表头、编号的引用链，★ 全都断在半路
        ↓
★★ ★★ 而这种答案最危险的地方在于：
   ★ 它"看起来对" → 用户信了 → 直接抄进文件 → 责任落到人头上
```

★ **★★★ 所以第四章这一节真正要证明的，其实不是"Wiki 比 RAG 快"：**

> **★ 在企业知识场景里，"快"根本不是矛盾的一方。**
> **★ 真正的对手是"★ 碎片拼凑出来的错答案"——**
> **★ 而它之所以能赢，靠的从来不是速度，是"★ 逻辑完整"。**

#### ★ 怎么识别自己在坑里

□ **Q1：我切段是人工还是自动的？** 人工 → 不可持续；自动 → 那我一定切坏过，只是还没发现。
□ **Q2：我能说出"最近一次切坏的是哪一段"吗？** 说不出，说明还没人复核过切分质量。
□ **Q3：换嵌入模型或换向量库，我要重灌多少数据？** 答案是"全部" → 已经绑死了。
□ **Q4：同一份制度在我的系统里有几份拷贝？更新后怎么保证同步？** 超过 1 份 → 迟早出事。
□ **Q5：答案里能点回原文吗？点回去是不是一个完整段落？** 点回去是碎片 → 审计过不了。

★ **★ Q4 和 Q5 是最关键的两问——它们问的不是技术，是"这套知识资产以后由谁维护、能不能被信任"。**

#### ★ 正确做法

```
① 先判断你的知识是不是"有结构的"
   · 制度、合同、标准、手册、模板 → ★★ 天然适合 Wiki
   · 碎片化的 FAQ、客服问答、闲聊记录 → ★ RAG 仍然合适
   ★ 别一刀切，这不是"RAG vs Wiki"，是"知识有结构吗"

② 让 AI 做"整理"，而不是做"切割"
   · ★ 整篇输入，要求它按逻辑层级重组
   · ★ 保留原始出处与位置标注
   · ★ 要它输出人能读懂的页面，而不是向量

③ Wiki 页面必须人可读、可审核、可编辑
   · ★★ 它的产物不是向量，是★ 一份人能维护的知识资产
   · ★ 如果只有系统能读、人看不懂，那它就退化成了一堆换皮的向量

④ 页面必须带出处与版本
   · 能被审计 · 能被追责 · 能被更新
   · ★ 这一条决定了它三年后还在不在

⑤ ★ 把"建库"明明白白算进排期和预算，但别把它算成"一支人力的队伍"
   · ★ 真实成本存在，别装作不是
   · ★★ 但★ 这一段已经可以由 AI 自主完成——所以排期上要算的是
   ·   "让 AI 跑一遍 + 人工抽检"的时间，不是"招人来切文档"
   · ★ 要一起算：它省掉的是"每一次变更都要重来"的成本
   · ★ 呼应第六章：★ 这笔账要算全，不能只算建库那一次
```

#### ★ 本节金句

> **★ RAG 把知识打碎，Wiki 把知识连起来。**
>
> **★ 你以为存的是知识，其实存的是向量。**
>
> **★ 一个快速的模糊答案，和一个通过逻辑判断的准确答案，哪个更有价值，一目了然。**
>
> **★ 在企业知识场景里，"快"从来不是第一指标，"能直接用"才是。**

## 4.3 决策树三：工具接入：MCP 与权限代理

### 4.3.1 为什么工具接入是企业 AI 的真瓶颈

前面两棵树决定模型能做什么，第三棵树决定模型能碰到什么。

而在企业里，**AI 的能力上限几乎从不由模型决定，而由它能安全地调用的工具数量决定**。

问题的起点很朴素：一个企业里有几十个系统——OA、ERP、知识库、合同系统、审批流、数据平台。每个系统的接口、鉴权方式、参数格式、错误码都不一样。

```
接入方式 A：每个工具写一套对接代码
  → N 个工具 = N 份适配代码 = N 套鉴权 = N 套日志 = N 套异常处理
  → 每接一个新工具，成本几乎不下降

接入方式 B：统一协议（MCP）+ 统一网关
  → 每个工具只需按协议声明"我能做什么、需要什么权限"
  → 鉴权、日志、限流、审计在网关统一做
  → 新增工具的成本大幅下降
```

**MCP 协议标准化的意义，不是技术上的优雅，而是三件管理上的事：**

1. **接入成本从"每加一个涨一次"变成"边际递减"**——这是数字化部门能把"工具接入标准"做成公共品的前提。
2. **权限模型可以集中**——否则每个工具各自为政，权限审计永远做不完。
3. **审计留痕可以一次做完**——留痕逻辑写在协议层，而不是散在每个对接实现里。

### 4.3.2 权限代理与审计留痕：受监管制造企业的硬要求

在受监管行业里，工具接入这件事的核心不是"能不能调通"，而是**"调完之后，能不能向第三方证明它做了什么、依据什么、谁批准的"**。

```
没有权限代理：
  AI 直接持有系统账号/密钥，每个系统各自授权
  → 权限授予散落，无全局视图；换人、收回权、临时提权全靠人工逐个系统处理
  → 出事时无法回答"它当时持有什么权限"

有权限代理（统一鉴权网关）：
  AI → 权限代理 → 业务系统
  代理层负责：身份映射、权限收敛（超出数据域即拒）、
              动作分级（读/写/不可逆）、全量留痕
```

**审计留痕要记的不是"调用了接口"，而是这一串：**

| 留痕项 | 回答什么问题 |
|---|---|
| 谁发起的（人或 Agent 身份） | 这是谁的决定 |
| 什么时候 | 能否复盘时序 |
| 调用了哪个工具、什么参数 | 做了什么 |
| 依据哪段知识（原文出处） | 为什么这么做 |
| 返回结果与后续动作 | 造成了什么后果 |

一个通用做法是把日志与业务单据**双向挂钩**：业务单据上能看到是哪次 AI 处理产生的，AI 的日志里也能定位到对应的单据号。没有这个双向索引，审计时就得靠人工翻。

```
审计能力的成熟度阶梯：

  阶段一：只有系统访问日志        → 能查"谁登录过系统"
  阶段二：有 AI 调用日志          → 能查"谁在什么时间问了 AI"
  阶段三：日志与业务单据双向索引  → 能查"这份合同为什么变成这样"
  阶段四：结论可回溯到知识原文    → 能查"依据是哪一条规定"
```

**受监管制造企业的硬要求是第四级。** 前三级只能回答"做了什么"，第四级才能回答"对不对"。

### 4.3.3 这件事归谁：数字化部门的定位

工具接入标准、模型网关、权限与审计代理，是**典型的人人都需要、人人都做不好的公共品**——这正是数字化部门在 AI 时代的位置：

> **公共品提供者**（算力、模型网关、知识库、工具接入标准、权限与审计代理）、**语义与规则的治理者**、**合规守门人**、**转型教练与裁判**。

放到本章的语境里，这四件事有一个统一的解法：**统一管控平面 + 分级部署**。

```
┌─────────────────────────────────────────────┐
│  统一管控平面（服务端，不接触业务数据）        │
│  模型网关与算力配额 │ 策略与技能包下发          │
│  证书/身份/密钥管理 │ 审计采集                 │
│  版本与升级         │ 使用行为统计             │
└──────────┬─────────────────────────┬─────────┘
           │ 策略下发 ↓      ↑ 状态与审计回传
   ┌───────┴──────┐  ┌─────┴────────┐
   │ 部门级：统一   │  │ 高敏感级：专用│
   │ 服务器        │  │ 主机/独立部署 │
   └──────────────┘  └──────────────┘
```

一句话：**数据不出机，管控不脱管。**

**"独立"的准确含义是数据与计算的位置，不是脱离管控。**每一台独立主机都要纳入统一策略：技能白名单、模型版本锁定、证书轮换、审计采集、远程擦除。

【待核实】"高管级助手独立主机部署"目前是作者的方案设想，尚未确认已实际落地，运行形态（是否完全离线、能否访问内网业务系统、模型跑本地还是走内网 API）需作者确认。

> **MCP 解决的是"接得上"，权限代理解决的是"敢让它接"。**
> **审计留痕的终点不是"记下了什么"，是"能回答它凭什么这么说"。**

## 4.4 落地形态三档：内部 Copilot / 流程内嵌 / 对客服务

技术方案定完，最后一层是**这个能力以什么身份出现在业务里**。三档形态，成本与风险逐级递增。

```
第一档  内部 Copilot        人来用，AI 给建议，人来执行
          ↓ 责任在人，成本最低，可以快速铺开
第二档  流程内嵌            AI 在流程里自动跑，人在关键节点审核
          ↓ 责任共担，需要流程改造与留痕
第三档  对客服务            AI 直接面对外部客户
          ↓ 责任外溢，风险最高，合规要求最严
```

### 4.4.1 三档对照

| 维度 | 第一档：内部 Copilot | 第二档：流程内嵌 | 第三档：对客服务 |
|---|---|---|---|
| **人机关系** | 人做，AI 辅助 | AI 跑，流程管，人审核关键节点 | AI 直接对客，人兜底 |
| **典型场景** | 内部知识问答、文档起草、检索 | 合同预审、单据预填、异常提示 | 客服应答、对外咨询、材料生成 |
| **成本结构** | 席位与调用量为主 | 需要系统集成 + 工作流改造 + 留痕 | 全部前置成本 + 高可用 + 冗余 + 持续评测 |
| **主要风险** | 员工不用、答案不可追溯 | 错误被当成事实流入下游流程 | 错误直接外溢到客户与外部承诺 |
| **责任划分** | 人对结果负责 | 人机共担，节点必须有人签字 | 法律责任不可转移，必须有对外口径 |
| **审计要求** | 记录调用与引用 | 记录每一步决策依据、单据流转 | 全链路留痕 + 对外话术版本管理 + 投诉追溯 |
| **推进节奏** | 可以快 | 中速，需跨部门 | 慢，需合规与法务前置 |

### 4.4.2 为什么风险逐级递增

**第一档到第二档，增加的不是技术，是"错误能不能被拦住"。**

Copilot 模式下，AI 给错答案的后果停在屏幕上；流程内嵌模式下，AI 给错答案的后果会**变成一条进入下游的单据**。所以第二档必须补上三样东西：高风险动作的人工确认、置信度阈值转人工、以及从单据回看 AI 判断依据的链路。

**第二档到第三档，增加的不是技术，是"错误能不能被收回"。**

```
错误可逆性：

  内部 Copilot   出错 → 改掉            → 成本：几分钟
  流程内嵌       出错 → 单据要撤回、要走更正流程 → 成本：几天 + 跨部门
  对客服务       出错 → 已发出去的承诺 → 成本：可能要召回、可能要补偿
```

**所以第三档推进慢，不是保守，是数学。**

### 4.4.3 每一档的责任与审计要求

**第一档：内部 Copilot**

- **责任**：使用人对输出负责；系统方对引用可追溯负责。
- **必须有的三件事**：引用可点回原文；不引用就说不知道；使用反馈能回流到知识库维护。

**第二档：流程内嵌**

- **责任**：每个高风险节点必须有人工签字人，**且签字人要知道自己签的是什么**（AI 的依据、置信度、争议点）。
- **必须有的四件事**：AI 判断依据入库；不可逆动作二次确认；错误回流为规则；审计可按单据穿透到 AI 决策。
- **常见失败**：把"人工确认"做成一个点击按钮。**一个不看内容的确认框，等于没有确认。** 这时候要做的不是加提示，而是减少需要人确认的动作数量。

**第三档：对客服务**

- **责任**：法律责任不可转移。AI 的对外输出属于企业行为的一部分。
- **必须有的五件事**：对外话术的版本管理与发布审批；高风险问题（法律、临床、用药安全、价格承诺）的强制转人工与话术白名单；全量会话留痕与投诉可追溯；对外场景专用的模型与评测集；独立团队的抽检机制。
- **受监管制造企业特有的一条（以制药为例）**：涉及产品、适应症、用法用量的问答，**不交给通用模型自由生成**。这类内容要么走审核过的知识条目，要么转人工。

### 4.4.4 一个具体形态：独立部署的敏感场景

在企业内部，还有一类场景既不属于三档，又在三档之间：**敏感岗位的独立助手**。

作者的设计是：模型可使用公司内部资源，但助手主机单独采购、单独部署，以保障隐私性与独立性。这条思路的价值在于把部署形态**做成了可选档位**而不是一刀切——按敏感度分档，避免最严标准套到所有人身上而让成本不可承受。

【待核实】该形态的落地状态、离线程度与内网访问方式待作者确认，详见 4.7。

> **从 Copilot 到对客服务，增加的不是技术，是错误的可逆性。**
> **一个不看内容的确认框，等于没有确认。**

## 4.4.5 ★★ 入口的三个方向：收敛到已有、收敛到新、还是再叠加一个

**★ 前面 4.4 讲的是"这个能力以什么身份出现在业务里"——那是**责任维度**。**
**★ 这一节讲的是完全正交的另一个维度：**用户从哪儿进来**——这是**入口维度**。

★ **为什么必须把这两个维度分开？因为大多数 AI 方案翻车，都是因为把它们混在一起了。**

```
   责任维度：★ AI 是给建议的（Copilot）／★ 参与流程的（内嵌）／★ 直接对外的（对客）
   入口维度：★ 用户从哪个软件点进去

   ★★ 这两个维度可以自由组合，★★ 而且组合数比想象的多
   ★★ 很多团队在讨论"我们要做第几档"的时候，★ 其实真正卡住他们的是入口
```

### 4.4.5.1 三种入口方向

★ **入口策略只有三个方向，而且它们有明确的优劣排序：**

| 方向 | 做法 | 典型形态 | 核心代价 |
|---|---|---|---|
| **① 收敛到已有入口** | 把 AI 塞进用户本来就在用的系统 | 通过 API / MCP 集成进 ERP、CRM、OA | ★ **要改别人的系统**——排期长、跨部门、优先级不在你手上 |
| **② 收敛到新建统一入口** | 把散落的 AI 能力收拢到一个自有入口 | 专用 APP / 内部 AI 门户 | ★ 用户要多装一个；跨组织协作会断链 |
| **③ 再叠加一个入口** | 在现有入口旁边再加一个 | 独立网站、外部 IM 里的助手 | ★ **几乎必然失败**（见 8.5） |

### 4.4.5.2 ★★ 一条规律：叠加几乎必败，收敛才有机会

★ **这张表里最值钱的不是前两行，是第三行为什么会输。**

```
   ③ 再叠加一个入口，为什么几乎必败？

   用户面前同时有：老路（邮件 / Excel / 群 / BI）+ 新入口
        ↓
   ★★ 用户有选择权，★★ 而且老路在好几项上都更省事
        ↓
   ★★ 于是用户的理性选择是：★★ 继续用老路
        ↓
   ★★ 而新入口的"用户数"，★ ★★ 往往只剩项目组和来做演示的人
```

★ **★ 而这正是 §8.5 营销助手失败的完整机制。**

★ **所以这里可以提炼出一条更普适的结论：**

> **★ 入口策略的方向，比入口的形态重要得多。**
> **★ "收敛"（把散落的收成一个）有机会；★ "叠加"（在旁边再加一个）几乎必败。**

★ **换个说法：另开一个入口的风险，★ 来自"选择权"，★ 而不来自"新入口"本身。**
★ **一个唯一的、比老路更省事的入口，和一个可有可无的新入口，是两件完全不同的事。**

### 4.4.5.3 ★ 为什么"收敛到已有入口"（嵌入式）在很多企业推不动

★ **嵌入式（通过 API / MCP 把能力集成进 ERP / CRM / OA）方向是对的——它属于收敛，而且用户零学习成本。**

★ **但它在实践中经常卡死，而卡死的原因很少是技术：**

```
   ★ 你要改的系统不属于你
        ↓
   · 改动的优先级不在对方 KPI 里
   · 对方要评估：会不会增加我的操作量？会不会给我添新的责任？
   · 要排 IT 档期、要走变更流程、要过安全评审
   · 而这些流程通常比业务方的 AI 项目活得更久
        ↓
   ★★ 而业务方的耐心是 3~6 个月
        ↓
   ★★ 于是：★ ★★ 方向正确的方案，死在时间差上
```

> **★ 「方向正确的方案，死在时间差上」——这是嵌入式推广最常见的死法。**
> **★ 而它和 8.5 的死法（方向也错）叠加起来，构成了入口问题的两种极端。**

### 4.4.5.4 ★ 强监管环境下的第三条路：专用 APP

★ **有一类组织，把 ①②③ 中的大部分都堵死了：**

```
   · 通用 SaaS 协作工具不被允许使用（飞书 / 钉钉 / 企业微信等）
   · 内部即时通讯工具本身受强监管，难以扩展
   · 走外部方式（独立网站 / 外部 IM），便利性差、用户触达难
        ↓
   ★★ 剩下的路只有一条：★★ 自建一个专用 APP，
   ★★ 集成企业内部已有的 AI 应用，★ ★★ 解决入口与快速触达问题
```

★ **而这条路的价值，不只是"方便"——它实际上让 APP 承担了三重身份：**

```
   ★★ 专用 APP 的三重身份

   ① 入口     →  解决"用户从哪儿进"和"触达不到"
   ② 权限边界 →  ★ 决定谁能调用哪个 Agent，★ ★★ 这是动态授权的载体
   ③ 审计载体 →  ★ 记录谁的哪一次调用用了哪些知识、★ ★★ 留痕天然落地
        ↓
   ★★★ ★★★ 而第 ②③ 两重身份，★★ ★★ 恰恰是第七章《合规与风险》反复要求的
   ★★★ ★★★ ★★★ 于是它把合规要求从"流程要求"变成了"架构要求"★★
```

★ **这是一个被普遍低估的收益：如果入口是自己建的，那么"按角色授权"和"调用留痕"就不必再靠事后补流程，它们是入口天然带出来的。**

### 4.4.5.5 ★ 必须诚实写出来的代价

★ **专用入口不是免费的，它的代价至少有四项，其中两项是真问题：**

| # | 代价 | 说明 |
|---|---|---|
| 1 | **触达成本从 0 变 1** | 老路是"打开电脑就有"，新入口是"多一个 APP"。★ 在允许使用通用 IM 的企业里这项很致命；★ 在 IM 被禁的环境里，它反而是**唯一成本** |
| 2 | ★ **外部协作会断链** | ★ 客户、供应商、经销商多数仍在钉钉/企微上。★ **一个纯内部的 APP，会把外部信息挡在门外** |
| 3 | ★ **内网与移动端的矛盾** | ★ 专用 APP 若只在办公网可达，手机端装它反而更麻烦——★ 而"快速触达"这个原始目标恰恰依赖手机端 |
| 4 | 运维成本 | 分发、版本兼容、设备管理，都是长期支出 |

★ **第 2、3 两项是这条路真正的难点，也是立项时必须先回答的两个问题（见 4.7 待核实）。**

### 一句金句

> **★ 入口策略的方向，比入口的形态重要得多。**
> **★ 收敛有机会，叠加几乎必败——因为用户永远有选择权。**
>
> **★ 方向正确的方案，也会死在时间差上。**

## 4.5 选型评估表（可直接抄）

技术总监真正需要的是一张能带进评审会的表。下面这张表分三块：先判形态，再判组合，最后判风险。

### 表一：形态判定（四因子，各一行，任意一格为"否"即需复核）

| 因子 | 判定问题 | 本企业结论 | 证据/来源 | 判定人 |
|---|---|---|---|---|
| 数据能不能出厂 | 哪些数据绝对不能出厂？占比多少？ | ☐能 ☐部分 ☐不能 | | |
| 成本规模 | 日均调用量、峰值形态、留存周期？ | | | |
| 合规审计 | 是否需监管穿透检查？留痕粒度要求？ | | | |
| 运维能力 | 谁来维护推理与版本？有几人？ | | | |

> 判定规则：前两项指向自建、第四项为空 → **不自建**，走 API + 数据分层。

### 表二：能力组合判定

| 需求类型 | 判据（问这一句） | 选定做法 | 是否需要微调 | 失败信号 |
|---|---|---|---|---|

> 判定规则：三条都命中 → **RAG 打底 + Agent 编排 + 少量微调**；只命中一条 → 只做那一条。

### 表三：风险与审计清单（上线前逐项打勾）

### 表四：采购项自检（每一条问一句）

| 采购项 | 明年的范式变了，我损失多少？ | 结论 |
|---|---|---|

## 4.6 本章小结 + 金句墙

三棵决策树，压缩成一张图：

```
决策树一：私有化 vs API
  先分数据能不能出厂 → 再算成本规模 → 再看合规审计 → 最后看运维能力
  结论形态：数据分层外发 + 路由，不是全上云，也不是全本地

决策树二：RAG vs 微调 vs Agent
  知识会变 → RAG；风格格式 → 微调；多步自主 → Agent
  现实形态：RAG 打底 + Agent 编排 + 少量微调
  ★ 例外（4.2.4）：★ 企业多系统共用一套知识时，
    "自动分段 + 向量库作底座"这两个选择会被四个死结卡住
    → 换成 LLM Wiki（整篇逻辑整理成 Wiki 页面）
    ★ RAG 把知识打碎，Wiki 把知识连起来

决策树三：工具接入
  MCP 标准化 → 接得上；权限代理 + 审计留痕 → 敢让它接
  分级部署 + 统一管控 → 数据不出机，管控不脱管

落地形态：内部 Copilot → 流程内嵌 → 对客服务
  成本与风险递增的真正变量，是错误的可逆性
```

**本章真正的产出不是结论，是三个提问顺序。**技术总监往后接到的任何技术方案，都可以拿这三句话去问：

```
第一句：这份数据，能不能出厂？
第二句：这份知识，会不会变？变了要不要重训？
第三句：这个 Agent，能碰到哪些系统？谁替它守着权限？
```

**金句墙**

> **企业 AI 技术选型的第一性问题，不是"哪个更强"，是"哪个你敢让它拿到手"。**

> **私有化不是安全选项，它是一份运维合同。**

> **一个模型看全部、一个模型只看一段，是两种完全不同的合规结论。**

> **采购是结果，不是起点——你要落实哪些应用场景，就采购哪些。**

### 4.1.4 本节结论

```
先问：有没有哪类数据绝对不能出厂？
  有 → 这些数据走本地，其余按分类走 API + 路由分层
  没有 → API 起步，把省下的运维人力投到场景上

再问：调用规模与运维能力撑不撑得起自建？
  撑不起 → 采购，别自建
  撑得起 → 再问明年的范式变了，这套东西损失多少
```

> **私有化不是安全选项，它是一份运维合同。**
> **一个模型看全部、一个模型只看一段，是两种完全不同的合规结论。**

> **RAG 负责"知道什么"，微调负责"怎么说"，Agent 负责"先做什么"。**

> **Agent 越强，越会掩盖检索的烂账。**

> **MCP 解决的是"接得上"，权限代理解决的是"敢让它接"。**

> **从 Copilot 到对客服务，增加的不是技术，是错误的可逆性。**
