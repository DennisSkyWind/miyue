## 7.0 这一章不讲"合规很重要"

前面六章讲怎么把 AI 用起来，这一章讲怎么不把自己送进去。

在企业里，合规的重要性从来不需要论证——需要论证的从来是"我们做的这件事到底算不算数"。所以这一章只回答一个问题：

> **哪些动作，会让你在签字的那天晚上睡不着？**

夜里睡不着，通常不是因为系统崩了，是因为白天签了四个字：同意、确认、已阅、准予。签完才发现，下面压着的东西当时没看清。

## 7.1 AI 输出的合规地位：AI 辅助 vs AI 决策

### 现场画面

流程跑顺了。AI 提取要素、标注风险、生成报告，人看一眼、点同意，单子往前走。季度汇报数据很好看。

某天一批文件里出了一份问题。追溯时流程图上写着：

```
上传 → [AI 审核] → [人工审核] → 归档
                 ↑ 这一步到底是谁？
```

问到人，答复是"系统是这么判的"。

**"系统是这么判的"，是企业 AI 项目里最贵的七个字。** 它意味着：当时签字的那个人，其实不知道自己签了什么。

### 两种模式，必须提前定死

在受控场景里（GMP/GxP 相关要求覆盖的计算机化系统场景【待核实】），AI 参与业务动作只有两种姿势。区别不在技术，在人的动作。

| 维度 | 模式 A：AI 出草稿，人签字 | 模式 B：AI 出结论，人复核 |
|---|---|---|
| AI 的产出物 | 结构化草稿、要素提取、风险标注、候选条款 | 判定结论、处置建议、评分 |
| 人的动作 | 从零审阅、改写、签字 | 复核通过 / 否决（全量或抽样） |
| 责任落点 | 签字的人 | 签字的人（复核人同担） |
| 主要失效方式 | 人偷懒，签得比原来还快 | 复核流于形式，变成橡皮章 |

> 两种模式的差别不在 AI 强不强，在"人"这一步有没有真的发生动作。模式 A 是"人变懒"，模式 B 是"人假装在管"。

### 责任不能转移给模型

模型不会签字，不会接到检查组的问询，不会在纠纷中承担损失。只要业务动作最终落到某个人的名字上，责任就在那个人身上——不管结论是模型算的、检索的，还是拍脑袋来的。

```
责任链只有三种形态：

  ① 人签字 → 责任在人（正常）
  ② 人没签字，系统自动执行 → 责任在流程设计者 + 系统所有者
  ③ 人签字了，但人不知道 AI 说了什么 → 责任还是在人
```

第三种最危险，因为它**形式上完全合规**：审批记录齐全、签名齐全、时间戳齐全，只有内容是空的。

### 具体怎么做

**第一步：给场景分级，不给工具分级。** 同一个模型，用在"抽取合同要素"和"判断供应商资质是否合格"上，风险差着量级。分级按业务后果分。

| 级别 | 定义 | AI 的角色 | 强制人工动作 |
|---|---|---|---|
| L1 提示级 | 不改变业务动作 | 起草、归纳、提示 | 引用式使用，注明来源 |
| L2 建议级 | 影响业务动作但不自动生效 | 打分、排序、风险标注 | 逐条判断（模式 A） |
| L3 判定级 | 直接决定流程走向 | 分类、路由、拦截 | 复核 + 留痕（模式 B） |
| L4 受控级 | 涉及 GMP/GxP 受控数据与受控文档 | 原则上不做 | 需质量部门单独批准【待核实】 |

**第二步：签字人必须是自然人，且有资质。** 质量体系里的签字看的是这个人有没有被授权做这个判断。AI 团队没有这个授权，业务部门的人有。

**第三步：审批意见禁止出现"AI 建议已确认"这种写法。**

```
不推荐：✗ "经 AI 审核无异常，同意。"  ✗ "系统显示通过。"  ✗ "已阅。"

推荐：  ✓ "已核对第 3、7、12 条与合同原件一致；AI 标注的第 9 条风险不成立，理由：附件三已约定。"
```

第二种写法把"确认"变成盖章动作。审计和检查问的从来不是"你确认了吗"，是"你凭什么确认"。

## 7.2 数据不出厂与个人信息边界

### 现场画面

某部门为提高效率，把一批历史文档喂给外部大模型做分析，结果确实有用。

一周后有人问：那些文档里有多少是受控文件？涉及多少客户个人信息？供应商那边留多久？训练了没有？

三个问题一个都答不上来。**答不上来不是因为团队不负责，是因为这些数据在流出之前从没被人分类过。**

### 数据分级：三档

分档依据是"这份数据如果泄漏，第一层伤害是谁"。

| 档位 | 判定标准 | 典型内容 | 处理方式 |
|---|---|---|---|
| **绝对不进** | 泄漏即造成不可逆损失 | GMP/GxP 受控数据（工艺参数、批记录、检验数据、偏差与质量事件记录）【待核实】；客户与患者个人信息；未公开合同、价格、专利、研发路线 | 不得进入任何外部模型/API；仅限本地私有化部署并白名单授权 |
| **需脱敏** | 脱敏后可用，价值保留 | 员工与经销商联系信息、金额类字段、客户名称、内部编码、日志参数与返回值 | 去标识化、掩码、哈希、分桶、金额泛化；规则与结果留痕 |
| **可进模型** | 本来就是公开的 | 公开法规文本、行业报告与新闻、公开的药品备案与说明书信息 | 可直接使用，仍需登记用途与来源 |

分档是全章最容易被跳过、也最不能跳过的一步，跳过的代价通常半年后才结算。

**具体怎么做**：让数据 owner 按三档给自家表打标，产出一张字段级的"数据分级台账"，一行一个字段，一列一个档位。台账不复杂，但它是后面所有事情的地基。

### 数据在哪、谁能看：用真实表结构说

抽象讲"数据安全"没人记得住。看一眼真实系统里数据长什么样就记住了。某大型药企销项与进项系统几十张表、几百个字段，挑几张：

| 表 | 字段 | 内容 | 敏感判断 |
|---|---|---|---|
| 客户信息表 | 纳税人识别号、地址电话、开户行、账号 | 企业客户主体信息 | 需脱敏 |
| 客户信息表 | 证件类型、证件号码（个人客户必填）、联系人手机 | 自然人身份信息 | 绝对不进 |
| 全电发票主信息表 | 购买方经办人证件号码、经办人联系电话 | 第三方自然人身份信息 | 绝对不进 |
| 发票主信息表 | 合同号、收款人、复核人、开票人 | 合同关联与责任链 | 需脱敏 |

看出两件事：**个人信息不在一个叫"个人信息表"的地方**，它散在发票表、客户表、进项转出表里，字段名叫"经办人证件号码""联系人手机"——所以分级要落到字段级；**真正值钱的不是那串证件号，是它和其他字段拼起来的那张画像**——所以脱敏的难点在组合。

### 内部数字员工的权限边界

某大型药企《数字员工管理指南》里，把数字员工分成两类，边界划得很清楚：

| 维度 | 数字员工A（内部知识管理型） | 数字员工B（外部创作服务型） |
|---|---|---|
| 数据访问 | 企业信息系统、数据库、质控文档 | 公开行业报告、新闻资讯、创意平台 |
| 敏感操作 | 需双人授权（数字化中心 + 业务部门） | 内容发布前需经品牌部审核 |
| 网络边界 | 禁止访问互联网，数据交互仅限企业内网系统 | 可访问公开网络资源，但需过滤敏感信息 |

这张表可以直接抄进自家制度：它把"哪些数据出厂"变成每个机器人身上的一条属性。三条硬规则随之而来：保密型禁止走公网；创作型只许访问公开资源且输入侧过滤敏感信息；保密数据操作需双人授权。

### 外部数据与第三方预测的边界

很多场景里，模型要靠外部数据补齐内部缺的那一块——公开的药品备案信息、行业趋势、第三方预测结果。这类数据可以用，但它的**权威性不能等同于内部数据**。

外部数据有三个坑：时效（公开信息比内部台账旧，冲突时以谁为准）、口径（第三方定义与内部不一致，混着算结论就是垃圾）、责任（出了错，提供方不承担你的业务责任）。

所以：外部数据只能做参考输入，不能做唯一依据；结论必须落回内部可追溯来源；第三方预测可以参与排序，不能参与最终判定。

公开知识的更新节奏也要写进机制。AI 陪伴产品这类知识密集场景里，公开医学与药品知识库采用"每日增量 + 季度全量 + 高风险知识由专业人员复核"的组合【待核实】——值得抄到任何依赖外部知识的场景。

## 7.3 审计留痕

### 现场画面

检查组来了，要三月份某次合同审核的证据：谁上传的、哪个版本模型处理的、输入是什么、输出是什么、谁复核的。

IT 查了一圈：OA 有上传记录，日志系统有一半操作记录。但"用的哪个模型版本""提示词长什么样""AI 原始返回是什么"这三样，一个都没有。**这批业务从头到尾无法自证。**

### 留痕要回答的五个问题

一次 AI 参与的完整动作，必须能回答：

```
谁   在何时   调了哪个工具（版本、配置）   取了什么   返回了什么   谁确认了
└──────────── 这五问缺一，就不算留痕 ────────────┘
```

对应到字段是四类：

| 类别 | 记什么 | 缺了会怎样 |
|---|---|---|
| **主体** | 账号 ID、姓名、部门/租户、IP、终端标识 | 追不到人 |
| **时间** | 请求时间、耗时、关联追溯 ID | 时间线断链 |
| **工具与输入** | 服务/接口/模型版本、请求参数（脱敏后）、提示词模板 ID、检索命中文档 ID | 只能证明"用过 AI"，不能证明"AI 看了什么" |
| **输出与处置** | 返回值/结论、置信度或风险等级、是否采纳、采纳与否决的修改记录 | 能证明过程，不能证明"人做了什么" |

这套字段不是凭空设计的。某大型药企销项系统里的一张第三方服务监控日志表已经很接近：操作人、精确到毫秒的操作时间、请求参数、返回值、追溯 ID、来源 IP 与终端、成功失败标识、异常编码与描述、执行耗时。

**这张表可以直接当模板。** 差别在于：它记的是"某系统调了某个接口"，AI 场景要扩成"某人把哪段输入喂给了哪个版本的模型，拿回什么结论，采没采纳"。

### 为什么"日志留存"是供应商条款里最该看的一条

因为除了日志，你手上什么都没有。

```
「使用先进的大模型技术」   → 不可验证，不构成约束
「将保存调用日志」         → 有约束，但没写留多久、存哪、能不能删
「完整保存请求与响应，期限不少于 N 年，企业可随时导出；
  终止后不得删除，删除须取得企业书面同意」 → 这才是能拿去和法务谈的条款
```

三条理由：

**第一，日志在谁手里，谁就有解释权。** 供应商说只保留 30 天，那第 31 天以后发生的事，你连自证的机会都没有。

**第二，日志和训练数据是两回事，很多条款把它们混在一起。** "可能使用交互数据改进模型"和"保存交互日志供客户审计"是两句完全不同的话：前者要明确拒绝，后者要明确要。

**第三，日志留存期要覆盖追溯期。** 制药场景里数据与记录保存有明确年限要求【待核实】，审计日志保存期不得短于业务数据，否则记录还在、日志没了，等于缺了一半。

### 具体怎么做

1. **自建留痕，不能靠供应商的"后台有日志"。** 必须能一键导出、格式稳定（结构化，不是截图）、能按人/时间/案件号检索。供应商后台的日志，永远拿不出来。
2. **日志要能拼成完整链路。** 用追溯 ID 把"上传 → 解析 → 调用模型 → 返回 → 人工复核 → 归档"串成一条线。断链的日志在检查面前等于没有。
3. **不可篡改。** 关键操作日志做哈希存证或只追加写入，保留删除标识但不物理删除。日志的价值全部来自"它没被改过"。
4. **敏感操作双人授权。** 保密数据操作需双人授权（数字化中心 + 业务部门）；对外发布内容需业务归口部门审核。
5. **人员流动时回收权限与代码。** 转岗、离职同步回收账号、服务器权限、代码仓库权限。AI 项目里个人的代码和提示词沉淀着业务逻辑和上下文，跟着人走比跟着系统走危险。

## 7.4 幻觉的风险控制

### 现场画面

AI 给出一条非常专业的意见。条款号、章节号、金额、日期，全是齐的。法务看一眼，说"确实是这样"，签了。

后来核对原件，发现那条根本不是合同里的条款——是模型自己编的。但它编得太像了：编号格式对，语体对，前后文接得上。

**幻觉最危险的地方不是它瞎编，是它编得像真的。**

### 四个可执行的机制

#### 机制一：强制引用

每条结论必须带来源，且来源是**可点开验证的具体对象**——条款原文 + 章节位置 + 文档 ID，或知识库条目 ID。**这条结论如果没法在 10 秒内找到出处，就不该出现在报告里。**

```
不接受：✗ "根据相关规定，赔偿上限不得超过合同总额的 30%。"  → 「相关规定」点不开。
接受：  ✓ "赔偿上限：合同第 12.3 条，'乙方累计赔偿不超过合同总价的 20%'（合同 v3 第 14 页）"
```

#### 机制二：无来源即拒答

做成系统硬约束，而不是靠提示词求模型"讲实话"。

拒答不是失败，是功能。要让模型学会三种输出：有来源的结论（附引用）、有来源的疑问（"知识库中没有 X 的规定，需 X 部门确认"）、以及无来源（"我不知道"）。

第 ③ 种如果被当成低质量回答去调参，模型很快会学会把"不知道"伪装成"知道"。所以必须在训练/调优阶段允许"不知道"是有价值的输出。

#### 机制三：置信度阈值

低于阈值的内容不自动流转，转人工。阈值按场景标定，不能照抄别家。素材里出现过"置信度低于 85% 自动触发人工复核"的写法，也有通过法规知识库检索增强压低幻觉率的做法【待核实】——这些数字要确认是否实测。

阈值的**用法**比取值更重要：它不是用来筛掉低置信内容，是决定"这一条要不要占用一个人 5 分钟"。高置信 + 低影响自动通过；低置信 + 低影响只做标记；**低置信 + 高影响必须有人看**——风险集中在这格。

#### 机制四：人工确认点设在哪个环节

这是四个机制里最容易做错的一个。

**错的做法**：把确认点设在最后——流程末端加一个"AI 已审核，请确认"的按钮，这是给橡皮章发工资。

**对的做法**：确认点设在**不可逆动作之前**，以及**低频但高后果的判断上**。

| 判断类型 | 例子 | 确认点设在哪 |
|---|---|---|
| 可逆、批量、低后果 | 格式整理、要素提取、摘要 | 不设，异常时抽查 |
| 可逆、高频、中后果 | 合同风险标注、报销单初审 | 抽样复核 |
| **不可逆、低频、高后果** | 放行受控文件、对外发布、改主数据 | **动作发生前逐条确认** |
| 不可逆、高频、中后果 | 自动路由、拦截、任务分配 | 规则先行 + 定期复盘 |

> **确认点要卡在"错了就收不回来"的那一步前面，不是在"结果已经出来了"的那一步后面。**

### AI 生成代码：静态扫描查不出的那一类风险

传统代码检查能查漏洞，查不出"逻辑对不对"。AI 生成的代码更容易出现**语义正确但业务错误**的静默错误——字段名对、逻辑通顺，但算出来是错的，静态扫描基本无效。

补法只有两个：**影子运行**（用真实数据副本跑一遍，不写入生产）和**与现有系统对账**（差异逐条看）。这属于"业务验收"，不是"代码审查"，要分开做。

## 7.5 供应商与模型的风险

### 四个问题，签合同前必须问出来

| 问题 | 问不出答案的后果 |
|---|---|
| **数据是否用于训练？** | 喂进去的合同、客户数据成了别人的模型参数，且不可撤回 |
| **日志留存多久？** | 出事之后无法自证（见 7.3） |
| **模型下线后数据怎么办？** | 服务终止时，文档、日志、向量索引是否删除，删除有无凭证 |
| **换版本后行为漂移怎么管？** | 同一场景上周结论正确，这周变了，没人知道 |

第四个最容易忽略，也最难事后补救。

### 行为漂移：版本一换，之前验过的全部作废

模型换版本不是"小版本优化"。同一份合同、同样的提示词，新旧版本输出可能明显不同，准确率、周期时长、输出格式都可能变。

```
三个月后可能处在这种状态：验收报告写的是 v1 的表现，生产跑的是 v3，
没人知道 v2 到 v3 改了什么，出事时团队内部对"这算不算问题"没有共识。
```

**具体怎么做：**

1. **锁版本。** 生产环境的模型版本固定并写进部署配置，升级走变更流程。模型升级不是运维操作，是变更。
2. **建回归集。** 攒一批固定的、带标准答案的测试样本（覆盖高风险场景即可）。每次版本变更全量跑一遍，比对差异。
3. **差异必须人工看一眼。** 差异清单逐条确认"改进还是回归"，只看平均准确率会掩盖单场景的严重退化。同时保留旧版本一段时间，出现争议时要能复现"当时那批结论是怎么来的"。

### 合同里必须写死的五条

这五条建议直接交给法务落条款。

| # | 条款 | 必须写清的点 |
|---|---|---|
| **1** | **数据不得用于训练** | 覆盖人工标注、人工反馈、评测数据；"改进服务质量"不属于例外；训练数据不得回流客户环境 |
| **2** | **日志留存与可导出** | 留存期限（不少于企业业务数据保存要求【待核实】）、日志范围、结构化可导出的格式、企业随时索取权、终止后的处置与删除凭证 |
| **3** | **服务终止后的数据处置** | 全部数据（含文档、向量索引、缓存、备份）在期限内删除；提供书面删除证明；企业有权委托审计 |
| **4** | **版本变更的通知与回归** | 重大变更提前通知期；变更后提供回归测试结果；企业有权在约定窗口内要求暂停升级 |
| **5** | **数据位置与跨境** | 存储与处理位置；未经书面同意不得跨境；分包商清单及同等义务传递；审计配合义务与响应时限 |

> **第五条里的"分包商清单"不要漏。** 今天直接签的供应商，明天可能把推理转给第三方。这不是假设，是行业常态。

## 7.6 风险清单模板（可直接抄）

用法：每个 AI 场景立项填一份，填不满的不许上线。这是本章唯一"拿来就用"的东西。

| # | 风险项 | 触发信号 | 处置动作 | 责任部门 | 状态 |
|---|---|---|---|---|---|
| 1 | 受控数据流入外部模型 | 出网请求含受控文档 ID | 阻断 + 清理 + 上报 | IT + 质量 | ☐ |
| 2 | 个人信息出厂 | 输入含证件号、手机号、账号 | 阻断 + 脱敏回补 + 评估 | 法务 + IT | ☐ |
| 3 | AI 结论被直接执行 | 流程无人工确认记录 | 停用自动执行，降级为建议 | 业务 + IT | ☐ |
| 4 | 结论无引用来源 | 抽样引用缺失率超阈值【待核实】 | 退回重做 + 加校验规则 | AI 团队 | ☐ |
| 5 | 人工复核橡皮章化 | 复核意见为固定套话 | 改逐条确认 + 修改留痕 | 业务 | ☐ |
| 6 | 审计日志缺失或断链 | 无法还原五问 | 补建字段 + 追溯 ID 串联 | IT | ☐ |
| 7 | 日志留存期短于业务保存期 | 供应商留存期 < 企业追溯期【待核实】 | 改条款，或本地镜像留存 | 采购 + IT | ☐ |
| 8 | 模型版本漂移 | 生产版本 ≠ 验收版本 | 锁版本 + 回归集 + 差异评审 | AI 团队 | ☐ |
| 9 | 供应商数据用于训练 | 条款未禁止或表述宽泛 | 合同加条款 + 关训练开关 | 采购 + 法务 | ☐ |
| 10 | 服务终止后数据残留 | 合同无删除义务与凭证条款 | 补条款 + 退出时核查 | 采购 + IT | ☐ |
| 11 | AI 代码静默逻辑错误 | 与现有系统对不上但无报错 | 影子运行 + 对账 + 抽验 | AI 团队 + 业务 | ☐ |
| 12 | 权限随人流动外流 | 离职后权限未回收 | 回收纳入离职清单 | IT + HR | ☐ |

三条用法：前 5 项是"上线前必须有答案"的；第 6~12 项是"运行中要监控的"，要有责任人和巡检频率；数据分级台账与外部数据依赖这两项最容易跳过。

## 7.7 本章小结

这一章讲"绝对不能干"，但能落地的其实是"必须先干"。

```
7.1  先定场景级别，再定工具。签字的永远是人。
7.2  先做数据分级，再谈数据出厂。分级落到字段级。
7.3  留痕要能回答五问，日志必须在自己手里。
7.4  幻觉靠机制，确认点卡在不可逆动作之前。
7.5  合同写死五条，版本漂移靠回归集管。
7.6  风险清单先填前五项，填不满不上线。
```

> **合规不是拦住 AI 的门，是让 AI 敢往深里做的地板。**
> 这四件事做实了，业务部门才敢把更大的活交给 AI；不做，第一个季度就会有人因为一次"系统是这么判的"而绕开系统。

### 金句墙

1. **"系统是这么判的"，是企业 AI 项目里最贵的七个字。**
2. **模型不会签字，所以责任永远在签字的人身上。**
3. **审批意见写"AI 审核无异常"，等于把确认变成盖章。**
4. **数据分级不落到字段级，就等于没分级。**
5. **个人信息不在"个人信息表"里，它在"经办人证件号码"字段里。**
6. **日志留存期短于业务保存期，等于业务记录只留了一半。**
7. **除了日志，你手上什么都没有——所以日志必须自己导出。**
8. **确认点要卡在"错了就收不回来"的那一步前面；模型换版本不是运维操作，是变更。**
