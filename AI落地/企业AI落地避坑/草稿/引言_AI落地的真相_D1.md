## 0. 开篇：三年里，AI 大多没做成

> **这一节是这本书为什么存在的答案。** 下面三条"真相"是它的内容，这一节是它的立场。

### 先看两组数字

同一家企业，同一年的时间轴上，躺着两组完全不同的数字。

```
┌─ 第一组（推出来的）────────────────────────────────┐
│   培训累计                        近 600 人次          │
│   数字员工大赛                    三十余支队伍、一百五十余人  │
│   最终胜出                        10 支队伍         │
│   AI 创研参与总人数               两百余人              │
│   数字员工平台登录 / 调用          四千余次 / 两千余次    │
│   成熟度自评                       从近乎零起步，一年内进入第二档          │
│   ★ 最终真正落地的场景             3 个              │
└────────────────────────────────────────────────────┘

┌─ 第二组（扎出来的）────────────────────────────────┐
│   合同智审                        四大合同类型全部上线│
│                                  ★ 全公司覆盖       │
│   印章识别                        合同审阅部门落地   │
│                                  ★ 可复制          │
│   产出                            1350 小时/年      │
│                                  50%~96% 效率提升  │
│                                  漏检风险降 30%+   │
└────────────────────────────────────────────────────┘
```

**★ 这两组数字之间的落差，就是这本书的全部主题：**

> **培训拉来了人，人变多了，场景没变多。**
>
> **而两个被"扎"出来的场景，拿出了可核算的年度效益。**


### 先说清楚一件事：这不是我们一家公司的故事

有读者会问：**这些坑，是你一家公司没做好，还是行业里都这样？**

**答案是行业里都这样。** 因为制造业的业务链条几乎不随规模和技术路线变化：

```
   研发 → 采购 → 生产 → 库存 → 质量 → 销售
        ↓
★ 不管是精密生产、流程生产还是离散生产，这六个环节都在
   而 AI 在每个环节遇到的问题结构，也是共通的
```

**所以这本书写的不是一家公司的私有经验，而是六个环节各自的"AI 适合度"：**

| 环节 | AI 适合度 | 典型结局 |
|---|---|---|
| 研发 | 差（验证周期太长） | 试点悬空 |
| **采购** | **最好（规则明确、文档密集）** | **最容易先成功** |
| 生产 | 差（实时与完整互斥） | 卡在数据侧 |
| 库存 | 中 | 卡在口径统一 |
| 质量 | 中（责任不可转移） | 必须配套留痕与签字设计 |
| **销售** | **差（口径在人脑、入口在别人地盘）** | **典型失败场景** |

**★ 而由此得出的一条普适结论，是这本书最想留下的东西之一：**

> **AI 落地的顺序，不该从"最痛的地方"开始，而该从"规则最明确的地方"开始。**
>
> 因为"痛"不等于"适合"——最痛的地方，往往同时是口径说不清、入口改不动、效果验不了的。


### 那为什么没做成？

如果你在企业里负责过 AI，你大概率经历过这样的一年：

```
年初：定了目标，要推 AI
春天：办训练营，做大赛，收集需求，报规划
夏天：立项了几个场景，平台上线了，助手发下去了
秋天：开会问进度——"用得怎么样？"
       "挺好的，大家都在用。"
年末：算账，算不出 ROI
       → 明年：目标再定一遍，人再办一遍
```

**这个循环里，最贵的不是钱，是一整年的注意力。**

而这个循环之所以会重复，通常不是因为这一年没努力，而是因为**没有人记录失败**：

```
成功的部分有汇报材料
试错的部分只有几句"还在推进"
半失败的部分没人愿意讲——因为讲出来像甩锅
彻底失败的部分干脆从记录里消失
        ↓
★ 于是每一年都是崭新的开始，每一年都在重新踩同一批坑
```

### 这本书想说的是：失败的部分才是资产

**市面上的 AI 落地书几乎都在讲怎么做成。** 讲怎么做成的书有一个共同的特点：

```
它们的成功案例，往往来自同一批人——
  有人懂技术，有人有数据，有人有决策权，还有人愿意试错
        ↓
★ 于是读者读完的问题不是"我该怎么做"
   而是"他们有我没有的条件"
```

**而这本书讲的是没做成的那些**，包括：

- 一个功能做出来了，用户没有来的营销助手
- 一个试过了、推了、但没继续用的智能问数
- 一批"计划做"至今躺在清单上的 46 个场景
- 一堆上线了但一个流程都没改的助手
- 以及——**两个真的做成的，和它们做成的那个共同点**

**★ 全书的核心命题只有一句：**

> **AI 落地失败，不是努力不够，是"推"与"扎"的资源配比错了。**
>
> **推的产出是声量，扎的产出是数字。而绝大多数企业，把绝大部分资源花在了推上。**

### 这本书不写什么

```
❌ 不写模型科普        —— 你可以在任何地方查到
❌ 不写厂商对比        —— 明年就不准了
❌ 不写"如何做好 AI 转型"这类宏大叙事
❌ 不把失败包装成"虽然没做成但意义重大"
        ↓
★ 尤其最后一条是本书的纪律：
   失败要讲失败，但要讲清楚代价和结论
   —— 否则这本书就成了一本自我安慰读物
```

### 那这本书写什么

```
第一章   五个坑：为什么大部分项目在开头就埋雷
第二章   场景选择：别先问能做什么，先问值不值得做
第三章   数据准备：把数据治理翻译成 AI 能听懂的话
第四章   技术方案：三个决策树，不追最新
第五章   五步法：从决定做，到真的被用起来
第六章   算账：成本五项、收益三类，以及"失败的代价"
第七章   合规与风险：哪些事绝对不能干
第八章   ★ 真实复盘：两年两阶段、一个失败、一个半失败、两个真成功
第九章   数字员工：把 AI 变成岗位，而不是工具
附录     七个可以直接抄走的模板
```

**★ 如果你只有 30 分钟，请直接读第八章。**

**★ 如果你正负责一个正在推进的 AI 项目，请读第五章的止损条件。**

**★ 如果你正在纠结"要不要做这个场景"，请读第二章和第三章的判断表。**

### 三个可以带走的自查问题

这本书很长，但如果你只记住三件事，就记住这三个问题：

```
① 我这个场景，如果做砸了，代价是多少？
   —— 代价可控，就试；代价不可控，先别动

② 我做这件事，是为了让更多人知道，还是为了让某个数变好？
   —— 后者才是产出数字，前者只是产出声量

③ 这个场景做成了，能复制到下一个部门吗？
   —— 不能复制就不是成果，是表演
```

### 最后一件事：关于时间

```
2025 年是广度年。学会试，试了 近 600 人次，落地 3 个场景。
2026 年是深度年。合同智审全公司覆盖，印章识别进了合同审阅部门。
        ↓
★ 从"试"到"扎"，中间隔的不是时间，是
   —— 你有没有把去年那些没成的事，认真记下来
```

**而这正是这本书存在的理由：把那一年没记下来的东西，现在记下来。**

## 0.5 这本书想解决什么问题

这几年，几乎每家企业都在谈 AI。

有的在买模型，有的在建算力中心，有的在开"AI 专项行动"会议，有的在给员工发提示词模板。热闹是真热闹。但如果你问一个 CIO 或者数字化总监："你们公司去年上的那个 AI 项目，现在还在用吗？"——十有八九会得到一个含糊的回答。

不是他们不想说清楚。是真说不清。

因为从一开始，就没有人算过这笔账。

我做过二十年企业信息化，做过数据治理体系，也参与过 AI 相关规划的落地与评估。看了太多企业上 AI 的路径——**技术上没有一家是输在模型不够强的，输的都是别的地方**。输在选错了场景、输在数据根本不能用、输在组织不配合、输在做完了没人说得清省了多少。

这四个"输"里面，没有一个跟"模型不够强"有关。

所以这本书的立场很明确：

> **别人教你怎么把 AI 用起来，我告诉你为什么你的 AI 用不起来，以及在出事之前先做什么。**

这本书不教你写提示词，不给你工具测评，不做模型对比。它写给的是这样一类人：35 到 55 岁，企业的 IT 负责人、数字化总监、CIO 助手，来自国企、央企、制造业、制药这类数据敏感、流程沉重、层级复杂的组织。他们不缺技术科普，缺的是**在有限预算和有限权威下做决策的依据**。

先说清楚一件事：这不是一本让人兴奋的书。企业 AI 落地的真实过程，坦白说，大部分时候是憋屈的、憋屈的、慢的、经常令人沮丧的。但只有把这层滤镜去掉，你才能看见真正决定成败的那几件事。

## 1. 真相一：技术不是瓶颈，数据是入场券

### 现象

一个常见的场景是这样的：企业上了大模型，买了算力，搭了平台，做了个知识问答助手，上线仪式很风光。然后业务部门用了两次，发现答非所问，就再也不用了。

而技术团队的第一反应是：模型不够强，换个更强的模型试试。

### 为什么会这样

因为在 2023 到 2026 这几年，"模型能力"是整个市场最响亮的叙事。发布会、跑分、榜单、多模态、推理能力——每一次迭代都有明确的、可量化、可截图传播的进步。相比之下，"数据"这件事既不性感也不能立刻演示。

但只要把 AI 落地拆开看，结论是绕不开的：

```
当 AI 落地企业时，真正有价值的是四样东西：

  ① 数据    ← 一切的基础
  ② 流程   ← 最终也是数据
  ③ 知识   ← 最终也是数据
  ④ 规则   ← 最终也是数据

关键洞察：不管怎么分类，流程、知识、规则
最终在数字化系统里，都是「数据」的形式呈现
```

**AI 转型要回答的三个问题**：

```
问题 1：数据是什么？
问题 2：关联关系是什么？
问题 3：规则在哪里？

结论：
如果没有数据治理
连数据都说不清
AI 转型就是空谈
```

请注意这三个问题的顺序。它们不是三个并列的技术问题，是一条**因果链**：你没法在不知道"数据是什么"的情况下回答"关联关系是什么"；也没法在不知道"关联关系是什么"的情况下指望模型替你找到"规则"。

这不是 AI 时代的新问题。这是企业信息化二十年来的老问题——只不过以前叫"数据标准不统一""主数据不一致""报表对不上账"，现在换了个名字叫"AI 效果不好"。

### 怎么识别自己在坑里

三个自测问题，任何一个答不上来，你大概率就站在坑边上了：

**① 你能不能用一句话说清，这个 AI 项目要吃的是哪几份数据？**

如果答案是"各个系统的数据"——你不知道。你需要精确到：哪个系统、哪张表、哪个字段、多少数据量、多久更新一次。

**② 这些数据有没有主人？**

不是"谁在维护"这种笼统的说法，而是：当这份数据的口径被质疑时，**谁有权拍板说"以我为准"**。一份没有主人的数据，喂给模型就是在赌。

**③ 业务方说"我们要 AI 帮我们做预测"，你能问出"预测什么、依据什么、错了谁负责"吗？**

如果对方只想要一个"智能"的结果，不想要这三个答案，那这不是一个能落地的需求。

### 正确做法

不是"先做数据治理再上 AI"——这句话太绝对，而且会让很多企业直接放弃。正确的说法是：

**只治理 AI 马上要吃的那一口。**

不要为 AI 治理全公司的数据，只治理 AI 马上要吃的那一口。选定了场景，就沿着这个场景的数据链路往前追：需要什么 → 从哪来 → 现在什么状态 → 谁负责 → 多久能改好。把这口"数据"治理干净，比治理一万条无关数据更有价值，也更快能拿出成果。

这一点我在《数据治理实战》里已经完整讲过（详见该书引言与第二章）——治理方法论的细节那里写得更全，本书只讲 **AI 语境下的差别**：AI 不需要"干净的数据"，它需要"说得清的数据"。

> **AI 吃进去的是数据，吐出来的是责任的具象化。**

## 2. 真相二：阻力不是技术，是政治

### 现象

技术方案评审通过了，预算批了，项目启动了。然后推进到一半就推不动了。

数据要不出来。业务部门说"这个数据涉密"。要人配合，部门负责人说"我们人手不够"。要改流程，流程归另一个部门管，改动要先过他们的会。半年过去，试点没跑起来。

会开了一堆，PPT 做了几十页，就是没有进展。

### 为什么会这样

因为大家把这件事当成了技术问题，而它其实是**权责问题**。

先看一组对比，这是我在数据治理里反复验证过的：

```
主数据治理为什么阻力不大？

因为主数据是"别人的数据"
  各部门用别人的数据
  用好了，大家都受益

比如：
  组织架构主数据 → 各部门都要用
  客户主数据     → 销售、市场、客服都要用
  供应商主数据   → 采购、财务、仓库都要用

结论：主数据治理，各部门都能受益，阻力自然不大
```

反过来，真正的阻力在哪里？

```
┌──────────────────────────────────────┐
│         一线业务数据和实际业务数据       │
│      （这些数据掌握在业务部门手里）      │
└──────────────────────────────────────┘

这些数据的特点：
  代表部门的业绩
  代表部门的责权
  代表部门的价值
  动了这些数据 = 动了部门的"蛋糕"
```

AI 项目要吃的，恰恰多是第二类数据。为什么？因为有价值的 AI 场景，几乎都长在业务的痛点上——那是业务自己的数据。而业务自己的数据，动了就是动了它的蛋糕。

所以阻力有明确的四个来源：

**阻力一：部门不愿公开数据。**
典型心态是"这些数据是我们部门的核心竞争力，一旦公开，其他部门都能看到我们的业绩，那我们还有什么话语权"。深层是：数据透明 = 业绩透明 = 压力透明。某些部门宁愿数据不准，也不愿透明。

**阻力二：数据/IT 部门不愿放权。**
"如果数据都归业务部门管，我们数据管理部门的价值在哪里？"担心职能被架空、价值被边缘化。这种心态不只是业务部门有，IT 部门自己也有。

**阻力三：工作方式被迫改变。**
很多部门习惯用 Excel 管数据、习惯手工台账、习惯"我说了算"的数据。改用系统的代价是：要学新东西、要守新标准、要放弃旧习惯。这是最不政治、也最真实的阻力。

**阻力四：责权博弈与再分配。**
AI 的本质是**重分配**。谁原来做这件事，现在 AI 做了，那个人干什么？谁原来签字担责，现在 AI 出了错谁担？——**AI 不是解放工具，是权责重分配工具。** 所有绕不开的责任问题，都会变成阻力。

### 怎么识别自己在坑里

**① 你的项目要的数据，是不是"某个部门的核心业绩数据"？**

是的话，阻力已经写在数据属性里了。不要以为是沟通问题。

**② 你的立项方案里，有没有"业务部门在项目里承担什么"这一节？**

如果只有 IT 部门在干活，业务只在最后验收——那不是协同，那是让业务替你的项目背锅。业务一旦意识到这一点，就会用最省力的方式让它黄掉。

**③ 你有没有算过：这个 AI 上了以后，谁的岗位/考核会变？**

这个问题如果连你都不敢在方案里写，那阻力一定会在中途冒出来，而且会以"技术问题"的面貌出现。

### 正确做法

**先做"能让人少干活的"，不做"能让人被考核的"。**

第一个 AI 场景，务必选业务部门**自己都嫌烦**的事——那种没人愿意干、干了也没人夸、但确实消耗人力的活。这类场景里，业务的收益是即时的、个人的、不涉及谁被替代，所以阻力最小。

同时，把使用者变成标准共建者，而不是被规范的对象。培训会开完没人提问，往往不是因为满意，而是因为提问等于承认自己干不好。

> **员工不抵触 AI，抵触的是用 AI 之后自己没价值了。**

### 一个可以立刻用的判据

如果你要在几个候选场景里挑，可以用一个非常朴素的判断：

**这个场景要吃的是"自己的数据"还是"别人的数据"？**

- 用**自己的数据**补自己的短板 → 阻力大（动了自己的蛋糕）
- 用**别人的数据**补自己的短板 → 阻力小（大家都受益）

这就是为什么同一个企业内部，做"跨部门信息汇总"类助手通常比做"本部门数据深度分析"更容易推起来——虽然直觉上前者听起来更复杂。

## 3. 真相三：没人算过账，所以项目没法活过第一年

### 现象

项目做完了，验收的时候很顺利。演示很漂亮，指标很好看。

然后就没有然后了。

没有进入常态化运营，没有算过这笔投入值不值，第二年预算收紧的时候，第一个被砍掉的就是它。半年后有人问"我们不是有 AI 吗"，谁也说不清那个东西现在还在不在用。

### 为什么会这样

因为 AI 项目的成本结构，和一般的信息化项目不一样。

一般的信息化项目，成本是**可见的、一次性的、可预测的**：买软件、招外包、三个月上线。AI 项目的成本有一大块是**隐性且持续的**：

```
AI 项目的成本（不完整版）：

  ① 算力 / 部署      ← 私有化 or API
  ② 模型调用与微调   ← 用得越多越贵
  ③ 数据治理前置投入 ← 最常被漏算，也最贵
  ④ 人员与培训       ← 贵，且不体现在预算表里
  ⑤ 错误处理与兜底人工 ← 模型必然会错，这笔账没人算
```

第③和第⑤两项，是绝大多数 AI 项目在立项时完全没有的。

第③项容易被理解：数据本来就脏，把数据治理做干净，这是一笔前置投入。这笔钱花得值不值，要看没有它 AI 的效果会不会归零。

第⑤项几乎总是被漏掉：**模型会出错，而出错的处理成本是持续的。** 一个准确率 85% 的助手，剩下 15% 的错误谁来兜？这些错误会进入流程、进入文档、进入客户的感知里。你不去算这笔账，它就以"用户不信任这个工具"的形式收场。

### 怎么识别自己在坑里

**① 你的立项文档里，有没有"什么都不做的现状基线"？**

这是最要命的一条。没有基线，就没有对照，就没有 ROI。所有人都在说"引入了 AI 之后效率提升明显"，但"明显"是相对什么？没有基线，提升就无从谈起。

**② 你的收益侧写的是"人时节省"还是"人的感受"？**

"体验更好""效率提升""智能化水平提高"——这些都不是指标。指标必须是：某个流程的周期从 X 缩到 Y，某类错误从 N 件降到 M 件。

**③ 你的项目有"运营负责人"吗？上线之后谁维护提示词、修数据、盯效果、处理投诉？**

如果没有，说明这个项目在你心里是个一次性交付物。而它实际上是一个**需要长期供养的系统**。

### 正确做法

**立项的时候就把账算出来，哪怕算得粗。**

收益分三类，三类都得算：

- **提效类**：人时节省。多少人、每天省多少分钟、折成年化人力。
- **决策类**：风险降低、决策提速。避免了一次什么事故、少了几轮评审。
- **质量类**：差错减少、合规事件减少。药企和制造业里，这一类的价值经常被低估——但它往往最大。

成本侧则必须把第③项"数据治理前置投入"写进去，并且明说它是**沉没但必要**的。

> **AI 项目最贵的那一项成本，从不出现在预算表里——它叫"数据原本就不干净"。**

> **算不出账的 AI 项目，本质上是一笔由未来偿还的贷款。**

## 4. 顺序搞反了，比做错了更贵

上面三个真相合起来，指向一个更根本的问题：**大多数企业把顺序搞反了。**

```
常见路径（问题路径）：

  想上 AI → 选模型 → 搭平台 → 找场景 → 补数据 → 发现效果差
                                              ↑
                                        成本已经沉下去了

推荐路径：

  找场景 → 补那一口数据 → 选技术 → 小步试点 → 算账 → 推广
```

看起来只是顺序调了一下，后果差很远。问题路径里，你在还不知道数据能不能用的时候，就已经把算力、平台、人力投进去了。等发现效果不行，损失已经发生，而且大部分是沉没成本。

### 一个可借用的成熟度分档

判断一家企业现在该不该上 AI、先上多少，可以套用数据治理的成熟度分档逻辑：

```
L0  数据没有主人，口径靠人脑
    → 这个阶段谈 AI 是危险的。先治数据。

L1  数据有标准有主人，但没进平台，靠人搬运
    → 仍然先治数据。可以做"内部试验"，但别承诺产出。

L2  数据基本就绪，平台可用，有运营机制
    → 可以试点，选一个业务部门自己都烦的场景。

L3  治理常态化，数据资产可发现可复用
    → 才适合规模化推广和多场景铺开。
```

这个分档的用处不在于给企业贴标签，而在于**避免在 L0/L1 阶段做 L3 的承诺**。很多项目的失败，是立项时就许了一个 L3 的收益，而组织实际还在 L1。

### 关于"AI 转型三问"的一个补充

前面提到的三问——数据是什么、关联关系是什么、规则在哪里——还有一个前置问题经常被跳过：

> **你不可能在没看过全量数据之前，就宣布哪些数据是重要的。**

这句话原本是讲主数据治理的：主数据不是选出来的，是摸出来的——你得先盘清家底，才知道哪几个域是真正的核心。同样的道理在 AI 场景选择上成立：**你不能先决定"我们要做智能质检"，再去想数据从哪来。** 很多时候盘一遍数据域，会发现真正值钱、且技术已经够用的场景，跟你一开始想做的完全不是一回事。

> **抄别人的顺序，等于抄了别人的前提条件。**

        场景 → 数据 → 试点 → 上线 → 运营

**如果你正在做一个 AI 项目的立项**，先跳到第六章，把账算一遍。算不下去就先别立项。

## 6. 写在最后

我不打算在这本书里告诉你 AI 有多神。

模型会变强，会变得更让人惊艳，这几乎肯定会发生。但模型变强这件事，和你企业里那个 AI 项目能不能活过第一年，是两个几乎不相关的问题。

企业 AI 落地的真实战场不在模型能力上。它在三个更朴素的地方：

**你选的场景对不对。**
**你吃的数据干不干净。**
**你算没算过那笔账。**

这三件事，20 年前叫信息化选型和数据治理，20 年后叫 AI 落地。名字换了，规律没换——甚至变得更硬了，因为这次的赌注更大、期望更高、失望也更快到来。

而所有关于 AI 落地的智慧，最终都会落到一个很朴素的地方：**你必须真的懂你所在的组织，才能把它推下去。** 这一点，没有任何模型能替你做。

> **AI 项目死得最多的地方，不是模型不够强，是没人算过这笔账。**
