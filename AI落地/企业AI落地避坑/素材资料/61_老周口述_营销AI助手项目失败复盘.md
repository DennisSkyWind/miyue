## 一、原始口述（逐字保留，仅做断句）

> 做杂的 AI 项目太多了，比如关于营销方面的。当时是给营销一线做的一个小助手，主要分有 3 个方面的内容：一个是制度政策解读；第二个是销售政策以及相关的销售方案的解读；还有产品信息等等的，这个属于知识库。
>
> 第二个就是数据方面的，就是希望销售一线能够随时包括他的管理层能够查到自己的销售实时销售数据。这样一个场景实际上呢，当时营销部门与 IT 部门进行合作共同研发。但是后来呢，就发现就是存在一个问题，功能是做出来了，但后面数据不完整，或者是数据呢不能够满足业务的需求。就算 AI 把功能实现了，最终也没有产出用户喜爱的。
>
> 同时呢，还有第二个问题呢，就是客户端接入的问题。销售人员并不习惯使用一些公司里特有的一些工具，而更喜欢像微信啊这些东西。而在公司里呢，又禁止对于公司的数据呢传输到像微信这些软件上，也存在着导致他出错、出问题。

---

## 二、拆解：这是一个"两块内容、两种失败"的案例

```
┌─ 内容一：知识库（制度政策解读 / 销售政策与销售方案解读 / 产品信息）
│   → 文档类，相对可控
│
└─ 内容二：数据（销售一线 + 管理层随时查自己的实时销售数据）
    → 数据类，本案例真正的失败点
```

**失败点一（数据侧）**：功能做出来了，但数据不完整、或数据不满足业务需求 → 用户不喜爱 → 场景没有跑起来。

**失败点二（入口侧）**：客户端接入问题——销售一线不习惯用公司特有工具，更习惯个人社交软件；而公司禁止公司数据传到这类软件 → 合规红线与真实工作流错位 → 导致出错、出问题。

## 三、★ 案例的关键结构（本书最需要的那个"双失败"模型）

```
        知识库部分                数据部分
           │                        │
      文档检索问题              口径与完整性问题
      （可解，但需治理）        （难解，且要业务参与）
           │                        │
           └────────┬───────────────┘
                    ↓
        ★ 失败点二：入口（客户端接入）
                    ↓
      一线不在公司工具里工作 → 公司数据又不允许进个人社交软件
                    ↓
        ★ 合规正确的路径 ≠ 真实工作的路径
                    ↓
                 场景失败
```

**★ 这个案例最有价值的地方：它同时暴露了"数据不ready"和"入口不对"两类失败，而且两者互相掩护。**

- 如果只有数据问题，用户会说"查出来的数不对" → 明确的反馈，容易修
- 如果只有入口问题，用户会说"我不会用" → 明确的反馈，容易修
- **但当两者同时出现时，用户给不出有效反馈**——因为他自己也说不清是"数不对"还是"不顺手"，最后的表现就是"不用"。**而"不用"是最难诊断的失败。**

## 四、★ 本案例可直接入书的机制解释（作者可再校正）

### 4.1 数据侧为什么会不满足业务

```
一线的"我的销售数据"要的是什么？
  · 我的业绩（口径 A：结算口径 / 口径 B：发货口径 / 口径 C：回款口径）
  · 我的过程（铺货、动销、库存、拜访、订单）
  · 我的对比（同比、环比、达成率、排名）

而系统里天然躺着的是：
  · 结算口径的发货明细
  · 批次的销售订单
  · 月度汇总表
        ↓
★ 三个错位：
  ① 口径错位 —— 他要"我的数"，系统给的是"业务的数"
  ② 颗粒错位 —— 他要过程与对比，系统给的是明细与汇总
  ③ 时效错位 —— "实时"与"完整"在多数系统里互斥
        ↓
★ 于是 AI 助手实现了"查询功能"，但查出来的东西不是他要的
   ↓
   而"查出来不对"的系统，用户会立刻弃用
```

**★ 关键判断（本书可署名的一条）：**

> **数据类 AI 场景的第一性问题不是"能不能查"，是"查出来的数是不是他心里的那个数"。**
>
> **而"他心里的那个数"，在两个系统之间对不齐之前，IT 是查不出来的——因为它只存在于业务的口头习惯里。**

**补充判断（★ 本案例给出的最重要的一条）：**

> **"要实时"和"要完整"，在多数企业系统里是互斥的两个要求。**
>
> **谁先承认这一点，谁就能把需求谈下来；谁都不承认，双方就会在验收阶段互相指责。**

### 4.2 入口侧为什么会出问题

```
一线的真实工作入口是什么？
   群消息、单聊、随手截图、语音 → 而这些大多在个人社交软件里
        ↓
公司系统要求他们去：OA / 客户端 / 门户 / 自建 App
        ↓
★ 两个事实：
   ① 一线没有"为了查个数而切换工作环境"的习惯
   ② 公司红线：公司数据不得外传到个人社交软件
        ↓
★ 于是唯一的合规路径，恰好是最不顺手的路径
        ↓
一线要么不用；要么绕过（截图转发、私下问 IT 手动出数）
   → 两种都对应"出错、出问题"
```

**★ 关键判断（本书可署名的一条）：**

> **一线不用你的工具，不是因为懒，是因为你的工具不在他的工作流里。**
>
> **而当合规红线把"唯一正确的路径"和"最顺手的路径"分开时，失败的不是用户，是设计。**

### 4.3 ★ 这两条合起来，才是这个案例真正的教训

```
如果只修数据 → 入口还是不顺手 → 仍然不用
如果只修入口 → 数据还是不对 → 用一次就弃用
        ↓
★ 真实的失败往往不是"一个原因"，而是"两个半原因"
   而"用户说不上来为什么不用"的那一半，通常是入口那一半
```

## 五、可直接引用的做法（本书给出的解法方向）

### 5.1 入口：不要让一线迁就系统，改"结论找人"

```
❌ 错误做法：做客户端 / 做门户 / 要求一线登录系统查数
   → 入口之争永远赢不了

✅ 做法：数据留在系统里，结论送到人所在的通道
   · 企业内 IM 机器人（不外传原始数据，只推结论与摘要）
   · 定时简报（日报/周报主动送到群）
   · 异常提示（不查不问，只在异常时主动出现）
   ★ 核心转变：把"入口之争"降级为"触达方式之争"
```

### 5.2 合规：改的应该是数据形态，不是红线

```
公司红线（数据不得外传个人社交软件）不必动，也不该动
        ↓
能动的是"外传什么"：
   · 只推结论、不推原始明细
   · 只推脱敏/聚合后的摘要
   · 关键数据留在企业内 IM 通道内，不落到个人设备
        ↓
★ 这一条同时回应第七章 7.2 的"数据分级"：
   分级不是"禁止外传"，是"决定外传的形态与颗粒度"
```

### 5.3 数据：先对口径，再谈实时

```
第 1 步  口径对齐会（营销 + IT 双方各出 5 个高频指标）
          逐个定唯一算法，并写下来（第三章的数据可用性清单）
第 2 步  只做营销最痛的 3 个指标，不做"全量实时"
第 3 步  先切"查询"，不做"智能分析"——先让数可信
第 4 步  数据可信之后，再谈 AI 能不能给结论
```

### 5.4 ★ 止损条件（本案例应该早点有）

```
试点 4–8 周，若同时出现：
   · 主动使用率 < 30%
   · 数据类请求的满足率 < 50%（用户问的数，系统给不出来）
        ↓
★ 结论：先回去治数据与入口，不要继续加功能
   加功能会掩盖数据问题，而不是解决它
```
